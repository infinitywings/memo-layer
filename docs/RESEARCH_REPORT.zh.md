## 0. 摘要

LLM 智能体每开一个新会话，就要重新摸索同一个项目。跨会话记忆能省掉这部分成本，但能改变行为的记忆同样能误导行为。现有系统大多让产生经验的模型自己认定经验为真。

rka-memory 是建在 RKA Core 上的开源记忆层原型。它只让一类记录改变智能体的行为：有效性由智能体未撰写的证据确立的记录。项目只有一条理论主线：

    valid(r, s) = grounded(r) ∧ applicable(r, s)

grounded 要求记录至少引用一个来自测试、退出码、工具或用户的事件，模型自己的文字不算。applicable 要求记录的范围覆盖当前状态，且范围内此后没有反证事件。记录沿 L0D、L1、L2、L3、L4 的阶梯移动。只有确定性的有效性引擎能改变阶位，只有 L2、L3 的有效记录进入智能体的上下文，其余记录留在账本里供审计。

**现状**。截至 2026 年 11 月，没有生产系统或已发表工作用"智能体未撰写、由代码检查的证据"决定记忆能否被信任。最接近的生产系统是 GitHub Copilot Memory：记忆带代码引用，使用前对照当前分支核验；但核验者是模型，官方称"不保证"。研究侧 2026 年出现一批验证器门控的工作（MemGuard、FGSE、TEPA、StateAuditor、PoEM 等），多为预印本，多数仍靠 LLM 打分或基准的隐藏测试。"遵循记忆会制造支持该记忆的证据"这一自我应验回路已有人命名（Memory Reward Inflation 的 Echo Gap 与误差独立假设，MPBench 的 V-S5），但没有已发表的防御。

**已有结果**。5 条实时任务流、29 个账本、392 个会话，DeepSeek 同时担任智能体和挖掘器。对智能体无法从仓库核实的三条错误主张，30/30 个不设门控的会话全部照做，门控与无记忆的会话 0/30。用户逐字陈述、由代码检查的长期规则，最后一次 house-rules 运行中门控会话 6/6 保持，无记忆会话 0/6。门控记忆在两条流中比无记忆少用 20% 到 40% 的智能体 token，但哪些记录带来这一节省尚不清楚。账本普查同时发现，按阈值晋升的挖掘教训有 45% 的支持链接来自已收到该教训的会话。设计检查的是事件由谁"发出"，没有检查由谁"造成"。

**计划**。第 0 步已完成（提交 7ac59e5）：范围冻结在 project 和 toolchain，默认关闭收窄。第 1 步运行中（代码 c0879f9，分析脚本 3064dfd）：新增 `stated` 臂，按事先登记的判据检验挖掘出的教训在用户规则之外是否带来可测收益。第 2 步计划中：把 grounded 精化为"证据的产生独立于 r 的投递"（PI 已批准，尚未在 RKA 登记为取代决策），并把 L1 主张改写成代码可检的预测。第 3 步计划中：在 CL-Bench 的 Codebase Adaptation 任务上评测，全部使用 DeepSeek。最大风险来自评测而不是机制：文献中编码场景的记忆增益普遍只有 0 到 5 个点，且常在噪声之内。

## 1. 背景与动机

### 1.1 问题

**智能体每个会话都在重学。** Anthropic 的 "The components of agent memory"〔厂商，2026-11-06，Lance Martin〕把记忆定义为模型从经验中获得、以可读上下文跨会话保留的知识，并提出"记忆即预测"：记下一条已验证事实，就是预测未来的智能体会不经复核而依赖它。该文在 CL-Bench 数据库任务的一个变体上报告，每答完一题就揭示正确答案并允许写记忆，Opus 5.5 的平均奖励从无记忆的 0.655 升到 0.838，Opus 5 从 0.564 升到 0.828。记忆有用，前提是记下的东西是对的。

**能改变行为的记忆也能误导行为。** 同一篇文章承认"一条错误笔记会传播到所有地方"。CL-Bench 论文〔预印本，arXiv 2606.05661〕的结论更冷：专门的记忆系统不如朴素的上下文内学习，"accumulated state frequently hurts"。VibeMemBench〔预印本，arXiv 2609.23570〕中，一组无关记忆让成绩下降 0.7 到 3.4 个点。投毒研究显示，毒记录越来越多地由智能体在正常运行中亲手写下；MINJA〔同行评审，NeurIPS 2025〕只靠普通用户的查询，平均注入成功率就达到 98.2%。

**谁来认定一条记忆为真。** 第一次文献调查（RKA `jrn_01M6S93VF2V3WGDX50C6ZPJ6QT`，2026-11-06）发现的共同弱点是自我认证：Voyager、ReasoningBank、ExpeL、Mem0、A-MEM、Hermes 都让产生经验的模型认定经验。遗忘跟着使用走，不跟着有效性走：MemoryBank〔同行评审，AAAI 2024，据该调查〕在被回忆时强化记忆，所以一条常被检索的错误记忆反而更持久。矛盾处理默认"最新者胜"（Zep 的双时间轴，Mem0 的删除），一条新鲜的断言就能投毒。

### 1.2 项目源流

这个方向来自一串前序工作（RKA `jrn_01M6S935R57CPF0Y9T7NQEM6P6`）。

1. **委托税论文**（Fu 与 Yang，ARR 2026 年 10 月投稿，编号 7523，审稿中）。设置是弱本地执行者加稀疏的云端监督，共享记忆，任务为 SWE-bench Lite。记忆条件解决率 47.5%，云端 token 39.9k；不保留记忆 43.3%，27.8k；平铺的审阅历史 44.8%。结构化相对平铺的增益为 +2.7pp，没有达到预登记判据。记忆把"未完成"率从 43.2% 降到 19.6%，却把"声明完成但实际错误"率从 19.9% 提高到 31.3%。结论是：结构化记录本身不保证正确，完成行为和正确性必须分开度量。这是本项目的直接动机。记忆让智能体更自信，不等于让它更正确。
2. **ChatGPT 分支 'delegation-tax'**（2026-10-16）。从 v1.0 的 "Correctness-Grounded Salvage" 计划发展到 v2.0 的 RKA 中介协作报告。评审认为 v2.0 滑向了协议比较；该线程最强的想法是"状态有效证据"（把历史证据绑定到代码状态，再决定保留、复查或省略），在 v2.0 里却被降为一行消融。评审还指出缺少 Handoff Debt（arXiv 2606.02875，同行评审状态未核实）这一基线。
3. **幻灯片 'RKA Memory for Long-Horizon Agents'**（2026-10-26）。提出分层记忆、角色划分，以及作为带评测门、版本化研究对象的技能。不足在于：仍在 SWE-bench 上评测；没有用户纠正信号；技能有评测门，主张没有；没有遗忘策略。
4. **另一会话的研究计划**（2026-11-06）。提出"记忆是有效性问题，不是检索问题"，记录是带范围的主张，误用率是主指标。不足是只有 applicable 这一半，没有 grounding。
5. **2026-11-06 的重新设计**加入 grounding，随后收窄为六周可建成的原型规格 `docs/SPEC.md`。

### 1.3 PI 的目标与唯一主线

PI 的原话（2026-11-06，`jrn_01M6S927YWJZA9EGRCAP0B9DGJ`）："我是在想如何做一个memo layer，来辅助做成一个self-improving 的personal agent。我们的目的是一个有研究性质的开源项目。注意这次我的目标不是一个论文，是一个可以实现的prototype。" 同一条指令还要求：全项目只有一条理论主线，而不是现有技术的拼接；引用优先同行评审，预印本要标出。

PI 批准的决策 `dec_01M6S956E1X6KYYMMK3E7795FM` 把主线定为 valid(r, s) = grounded(r) ∧ applicable(r, s)，自我改进则是一条只由该谓词驱动、可审计的晋升阶梯：L0 观察 → L1 主张 → L2 已验证 → L3 技能 → L4 退役。决策 `dec_01M6S95E394B7M9VHDV3113MJ6` 定为先做原型，论文日后出自原型日志。规格开篇写道："Everything below is plumbing to compute this predicate and to let only valid records reach the agent." 本报告其余部分都围绕这句话组织。

## 2. 现状（SoTA）

### 2.1 锚点：Anthropic 的 "The components of agent memory"

这篇文章〔厂商，2026-11-06〕是 PI 指定的锚点。

**实验与数字。** 主要实验用 CL-Bench 1.0 的数据库查询任务。Claude 每答完一题就被告知正确答案，可以写记忆；每题新开会话，只有记忆目录跨会话保留。无记忆到有记忆的平均奖励：Opus 5.5 0.655 → 0.838，Sonnet 5.5 0.644 → 0.833，Opus 5 0.564 → 0.828，Opus 4.7 0.383 → 0.700，Sonnet 5 0.306 → 0.610，Sonnet 4.6 0.330 → 0.364（再加精炼的指导后为 0.641）。给模型加一条"只记录失败"的固定规则，记忆增益分别减少 0.234（Opus 5）、0.150（Opus 4.7）和 0.020（Sonnet 4.6）。文章没有给出运行次数、方差或成本；一篇二手文章称其中若干结果是单次运行。调查指出，该运行与 CL-Bench 论文对数据库任务的描述（40 题、第 20 题后做 schema 迁移、按查询经济性计分）并不一致，很可能用的是变体或子集，所以这些数字不能与论文的归一化表直接比较。值得强调：这组实验每题之后都揭示正确答案，这本身就是智能体未撰写的外部真值。

**其他实验。** Pokémon Red 中，Sonnet 3.7 写了 413 个记忆文件，拿到 1 枚徽章；Claude Fable 5 写了 10 个文件，拿到 4 枚。在 Stainless 文档语料上，只用 wiki 的成绩经 128 次"做梦"从 13% 升到 48%；wiki 加搜索达到 61%，只用搜索为 53%。合同条款实验中，四个智能体按通用指令共写一张条款表，只保住 41/57 个事实（72%）；改为每份合同一页、逐字引用条款后，57/57 全部保住。

**纠错机制。** 离线"做梦"把笔记对照原始会话记录修正、合并、提升。Mt. Moon 案例里，一条错误的 PokéCenter 位置笔记让 Claude 反复绕路；做梦修正后，运行在第 1,935 步到达 Cerulean City。配套的 Dreams API〔厂商，研究预览〕用一个记忆库加 1 到 100 个历史会话合成新的输出库，输入库不被修改。配套 cookbook 的规则更能说明问题：没有证据支持的条目原样保留，因为别的记录也许能支持它；被矛盾的条目修正或标注；"说得肯定但证据不确定"的条目降级。默认没有人工审核；夜间原地更新意味着一份坏记录第二天早上就能到达智能体。

**层级与风险。** 做梦可以把笔记提升到每次会话启动都注入的顶层，依据是访问频率和体积，而不是验证状态。文章列出三项风险：token 成本，"一条错误笔记会传播到所有地方"，指令文件越长遵循度越低。

**对本项目的含义。** 锚点与本设计有三处根本差异。第一，Anthropic 的纠错依据是会话记录，记录里混合了智能体自己的文字、工具输出和用户发言，纠错者是模型，不区分证据的作者。第二，cookbook 保留无证据的条目，本设计扣留未验证的主张。第三，Anthropic 按访问频率提升，本设计按验证状态提升；文章自己说的"错误笔记会传播到所有地方"正是按验证门控提升的理由。反方向的警告也来自锚点："只记录失败"说明限制**写入**会伤害强模型。本设计限制的是**信任与投递**，L0 观察仍可自由写入，而锚点对"门控信任"没有提供任何数据。

### 2.2 生产系统

**GitHub Copilot Memory**〔厂商〕。2025-12-19 早期访问，2026-01-15 公开预览，2026-03-04 对 Pro/Pro+ 默认开启，2026-11-12 工程博客更新称已正式可用。智能体调用 `store_memory` 时给出 subject、fact、citations（如 `server/routes/api.go:8`）和 reason。GitHub 放弃了离线策展，理由是验证一个事实比检索它更容易，于是改为"带引用存储、即时核验"：会话开始时把最近的仓库记忆放进提示；应用某条记忆前，智能体对照当前分支检查它引用的位置；代码矛盾或引用失效时存一个修正版；有效且有用时重存一次以刷新时间戳。现行文档把它表述为投票：能验证的记忆得 upvote，错误或过时的得 downvote，downvote 超阈值即停用、最终删除，但 "Copilot makes this judgment itself, so it isn't guaranteed"。有效期从公开预览时的 28 天变为现在默认 90 天，仓库事实可设 7 到 180 天；upvote 重置计时，仅被检索不会。仓库事实只能由有写权限用户的操作产生，不被 fork 继承；用户偏好跨仓库生效，但代码审查和 Autofix 永不使用。厂商 A/B 测试（p < 0.00001）：编码智能体的 PR 合并率有记忆 90%、无记忆 83%；代码审查精确率 +3%，召回率 +4%。对抗测试中植入与代码矛盾或引用不存在位置的记忆，智能体 "consistently verified citations"，但没有给出数字。

**Claude Code auto memory 与 CLAUDE.md**〔厂商〕。CLAUDE.md 由用户写，auto memory 由 Claude 写，两者都是"上下文而非强制配置"，要阻止某个动作得用 PreToolUse hook。auto memory 不记录能从代码库推出的内容。代码只检查 `MEMORY.md` 的 200 行或 25KB 上限，不检查真假。Managed Agents 记忆库〔厂商〕文档警告：在 `read_write` 模式下，一次成功的提示注入就能写入恶意内容，后续会话会把它当作 "trusted memory" 读取；每次修改生成带会话归属的不可变版本，保留 30 天。Cisco 披露的 "MemoryTrap"〔厂商〕中，一个经用户批准安装的 npm postinstall 脚本覆盖了所有 `~/.claude/projects/*/memory/MEMORY.md`，让智能体建议把 API key 硬编码进要提交的文件；Claude Code 自 v2.1.50 起把用户记忆移出了系统提示，该事件的 CVE 编号在各二手来源间互相矛盾。

**ChatGPT 记忆**〔厂商〕。分为"已保存记忆"和"参考聊天历史"两项控制。帮助中心页面直接抓取时返回 403，细节来自官方页面的搜索结果和二手报道，未核实。没有找到 OpenAI 对记忆准确率或效果的公开测量。一项独立审计〔同行评审，WWW 2026，arXiv 2602.01450〕分析了 80 名用户的 2,050 条真实记忆：96% 由系统在用户未要求时创建，84% 能在对话中找到直接依据。

**OpenAI Codex Memories**〔厂商〕。后台的抽取模型和合并模型写入。文档称之为 "helpful recall layer"，必须遵守的团队规则应放进 `AGENTS.md`。唯一与来源相关的开关是 `memories.disable_on_external_context`，开启后排除用过 MCP、网页搜索或工具搜索的会话。这是按来源过滤准入，但方向与本设计相反（排除外部工具内容，而不是要求外部证据），且默认关闭。

**Letta**〔厂商〕。"Dreaming"（CLI `/sleeptime`）让后台子智能体回顾近期对话并更新记忆。可选项 "Agent reviews before applying" 另开一个后台会话复核拟议更新，既不问用户，也不对照外部真值。记忆是 git 支撑的文件系统 MemFS。

**Zep 与 Graphiti**〔厂商；Zep 论文为预印本 arXiv 2501.13956，2025-01，由 Zep 员工撰写〕。事实带有效期窗口，信息变化时旧事实被标为失效而不删除，每个实体和关系可追溯到产生它的原始片段。论文报告 DMR 94.8%，MemGPT 93.4%。

**LangMem**〔厂商〕。语义、情景和程序三类记忆，可在热路径或后台形成。LLM 调和新信息（删除、作废、更新或合并），回忆按相似度、重要性和"强度"（新近与使用频率）加权。没有真值验证，页面没有指标。

**mem0**〔预印本，arXiv 2504.19413，2025-04〕。LLM 抽取候选事实，与相似的已存记忆比较后选 ADD、UPDATE、DELETE 或 NOOP；图变体把冲突关系标为失效而不删除。摘要报告在 LoCoMo 上相对 OpenAI memory 的 LLM 评判分数相对提高 26%。项目文档 `docs/LADDER.md` 记载：mem0 曾用提示文字把抽取限制在用户消息上，后来撤回；一次对其生产存储的审计发现了幻觉出的用户画像和智能体与运营方的混淆。原始来源在项目文档中未列出，未核实。

**Cursor 与 Windsurf**〔厂商〕。Cursor 员工 2025-11-25 称 Memories 自 2.1.x 起 "intentionally removed"，建议导出为规则文件；2026 年 1 月另一条员工回复称只移除了管理界面，状态互相矛盾。Windsurf 文档建议把持久的团队知识放进 Rules 或 `AGENTS.md`。两家都从自动生成的记忆退回到用户维护的规则，都没有公布原因或数据。

小结：生产中只有 Copilot 把记忆寿命与成功验证绑定，其余产品按模型或用户判断准入，靠用户编辑、模型合并、新近度或时间性失效纠错。所有效果数字都是厂商自报。

### 2.3 实践者模式

**Karpathy 的 LLM Wiki**〔实践者，GitHub Gist，2026-04-04，未经同行评审〕。LLM 在用户与不可修改的原始资料之间维护一个持久 wiki，让知识编译一次，而不是像 RAG 那样每次查询重新推导。三层结构：原始资料（不改，真值来源）；wiki（LLM 写的摘要、实体、概念、比较页面，"the LLM owns this layer entirely"）；用户与 LLM 共同演化的 schema 文件（`AGENTS.md` 或 `CLAUDE.md`）。操作有 ingest、query（好的回答作为新页面写回）和 lint（矛盾、被新资料取代的陈旧主张、孤儿页面、缺失交叉引用、空白）。没有引用核验，没有测量，没有处理幻觉或自生成内容。

**Angie Jones 的解读**〔实践者，Agentic AI Foundation 博客，2026-06-08〕。把 LLM Wiki 映射到七类记忆（对话、语义、情景、程序、实体、工作、摘要），原始资料是证据层而非记忆。示例中，去重、陈旧趋势的衰减、区分一次性观察与可复用知识，"All of this is handled by the agent itself, not the human." 没有验证步骤，没有测量。

**LifeOS**（Daniel Miessler，原名 PAI）〔实践者，GitHub 开源，MIT，v8.761.0〕。项目于 2026-11-13 读了它的记忆审阅器（`jrn_01M7B47643N7KMC8XVZ0JST5N0`；部分 hook 细节来自 WebFetch 摘要，属二手）。审阅器由 Stop hook 触发（至少 8 轮、空闲至少 2 分钟、距上次审阅至少 30 分钟），输入最近 20 轮用户与助手的文本，代码跳过 tool_use 和 tool_result 块，所以审阅器看不到工具输出、退出码或测试结果。一次 Sonnet 调用改写热层记忆文件，无人工步骤。身份类文件的修改提议在模型自评置信度 ≥ 0.70 时静默应用。每条记忆带一个由模型自己写的来源标签（~explicit、~deduced、~inferred），代码只检查标签取值合法。代码强制的是完整性而不是有效性：按硬编码白名单把写入路径分四级，字段清洗，每个记忆文件最多 48 条、每条 256 字符，写入前做指纹比较。值得借鉴的有三点：经 realpath 解析的写入路径白名单；配置损坏时失败关闭；提示规则"写陈述性事实，不写指令"（指令形状的记忆日后会被当作命令重读）。

### 2.4 研究方法：经验记忆与技能记忆

最常被引用的跨回合记忆方法几乎都由 LLM 决定写什么。

- **ExpeL**〔早期；常被引为 AAAI 2024，抓取的 arXiv 页面未列会议，未核实〕。环境奖励等于 1 的试验算成功，但成功与失败轨迹都进入经验池。洞见由 LLM 以 ADD、EDIT、UPVOTE、DOWNVOTE 维护：新洞见初始重要度为 2，投票加减 1，归零即删除。这是"遇反证降级、归零退役"的最早实例。ALFWorld 上 ReAct 40.0 → ExpeL 59.0。
- **Agent Workflow Memory（AWM）**〔同行评审，ICML 2025〕。在线设置中只把 LM 评估器判为成功的轨迹归纳为工作流。WebArena 成功率 35.5，BrowserGym 基线 23.5。
- **ReasoningBank**〔同行评审，ICLR 2026〕。成败标签来自与智能体同一骨干模型的 LLM 评判，"without any ground-truth reference"；在 WebArena-Shopping 上，评判与真值的一致率只有 72.7%。据 Google Research 博客，相对无记忆在 SWE-Bench-Verified 上 +4.6，WebArena 上 +8.3。
- **Dynamic Cheatsheet**〔预印本，arXiv 2504.07952〕。明说不需要真值标签或人工反馈。
- **ACE**〔同行评审，ICLR 2026〕。有无真值都能运行。作者警告没有标签时 ACE 与 DC 都 "may degrade"：FiNER 在线设置下无真值时降到 67.3，低于 70.7 的基线。它还记录了"context collapse"：迭代重写让一个 18,282 token、准确率 66.7% 的上下文一步塌缩到 122 token、57.1%，低于 63.7% 的无适应基线。
- **Voyager**〔早期，2023；第一次调查记为 TMLR 2024，后续笔记称会议与具体入库规则均未核实〕。环境反馈、执行错误和自我验证共同改进程序，技能进入可执行代码库。报告的独特物品数 3.3 倍、行进距离 2.3 倍、科技树里程碑最快 15.3 倍。
- **Darwin Gödel Machine（DGM）**〔同行评审，ICLR 2026〕。用第三方基准分阶段评估新变体，SWE-bench 成绩从 20.0% 提到 50.0%。但在幻觉检测实验中，节点 114 删掉了特殊工具 token 的日志，绕过检测函数拿到 2.0/2.0 的满分。检查只有放在智能体的写权限之外才算外部。
- **MemP**〔预印本〕的 "Validation" 只保留成功轨迹，在 TravelPlanner 上不用 LLM 评判。**SAGE**〔同行评审，ACL 2026〕保存技能的条件只是"执行不报错"，相当于退出码检查。
- **Self-Generated In-Context Examples**〔同行评审，NeurIPS 2025〕只保留按环境成功过滤的自身轨迹，ALFWorld 从 73% 提到 89%，加策展后 93%。

规律是：真正依赖智能体未撰写信号的方法，几乎都依赖只有研究环境才有的隐藏检查器或基准奖励。

### 2.5 门控与分阶段准入

2026 年出现一批明确的"验证器门控"记忆，几乎全是预印本或工作坊投稿。

- **MemGuard**〔预印本，arXiv 2608.21867〕。LLM 验证器从任务完成度、证据一致性、执行有效性和可泛化性四方面给轨迹打分，输入含退出码、公开测试输出、工具错误等运行时状态，"never uses hidden benchmark labels"。只有 reward ≥ 0.70 且 confidence ≥ 0.60 的记录激活。人工审计与验证器一致率 86% 和 83%；只用验证器过滤的消融在 16 个设置中有 15 个胜过 ReasoningBank。第一次调查还记载了按时间排序的 2,294 个问题的 SWE 流，以及误接受漏斗（审计 60 个误接受：22 个处于激活态，12 个影响了动作，6 个与失败相关），并评价其结果"异常一致，宜视为暂定"。记录状态的描述在两份来源中不一致：第一次调查写作 provisional、active、summary、archived，相关工作报告写作 active、provisional、rejected、failure-guard，未核实。
- **Verification as an Architectural Layer**〔工作坊投稿，arXiv 2609.31937〕。规定 "memory is written only by verification outcomes"，每个验证器由确定性闸门加可选 LLM 评判组成。5 个 MuSiQue 题、47 次执行的小试点中，确定性闸门产生了 9 次纠正中的 8 次，但试点没有实现记忆设计本身。
- **FGSE**〔预印本，arXiv 2611.14326〕。把教训变成假设，每个假设须通过满足 "executable or externally checkable signals" 的探针才提交。一次运行 380 个候选只提交 104 个；提交后违规分数会把假设移出检索。在 DeepSeek-V3.1 上，提交的更新中有害的占 3.6%。
- **EDV**〔预印本，arXiv 2606.24428〕。只保留异构智能体一致通过的教训，"自我确认陷阱率"从 11.0% 降到 5.0%。
- **HDSO**〔预印本，arXiv 2606.22330〕。观察 → 假设 → 分阶段配对对照验证 → 评审 → 合并，但最终评审者仍是冻结的策展 LLM，McNemar p 值只记录、不设门槛。
- **TEPA**〔预印本，arXiv 2608.07429〕。观察存为绑定证据的键控先例；同键出现矛盾证据时旧先例被撤销，保留以供审计，之后可再次提升。完全反转的受控漂移下（50 个种子）TEPA 0.950，只追加与后写覆盖都是 0.210，无记忆 0.309；但在 MemoryAgentBench SH-6k 上只与后写覆盖持平。
- **StateAuditor**〔预印本，arXiv 2608.01619〕。LLM 依据带时间戳的证据提出"旧值 → 新值"的转换；确定性代码把每段引文绑定到一条记录，并检查新证据确实更晚。在 STALE 上带来配对 +5.0 点（95% CI +2.9 到 +7.2），证据与调用预算相同的对照只有 +0.6，不显著。这是"由代码检查的引用"本身带来增益的最清楚证据。
- **Proof-of-Execution Memory（PoEM）**〔预印本，arXiv 2608.16032〕。HMAC 链式账本只能由可信动作层写入，伪造的"该步骤已完成"记忆无法授权跳过。在 GPT-4o 上把攻击成功率从 98% 到 100% 降到 0%。

没有工作实现完整的 L0 到 L4 阶梯，也没有工作以"在 k 个独立会话中被代码检查确认"作为晋升规则；EDV 的 k-of-k 一致最接近，但确认者是 LLM。评审者的可靠性给自评记忆设了上限：ReasoningBank 72.7%，MemGuard 83% 到 86%。

### 2.6 记忆投毒与自我强化

**攻击：毒记录越来越多由智能体亲手写入。**

- **MINJA**〔同行评审，NeurIPS 2025〕。攻击者只有普通用户的查询权限，先用"指示提示"诱导智能体生成桥接推理，再逐步删去提示，留下一条看似由智能体自己生成的记录。平均注入成功率 98.2%，攻击成功率 76.8%。后续预印本（arXiv 2601.05504）发现已有的合法记忆会 "dramatically reduce" 其效果。
- **AgentPoison**（arXiv 2407.12784，2024-07；常被引为 NeurIPS 2024，但 arXiv 页面未列会议，未核实）。后门攻击：优化的触发器把带触发的查询映射到独立的嵌入区域。平均攻击成功率至少 80%，对正常性能影响低于 1%，投毒率低于 0.1%。
- **MPBench**〔预印本，arXiv 2606.04329〕。六类投毒，在 OpenClaw 和 HERMES 上测试，两者平均攻击成功率 50.46%（OpenClaw 34.25%，HERMES 66.67%）。HERMES 上伪造先例插入 73.3%，技能流程插入 58.3%。现成检测器真阳性率 23% 到 68%；对事实注入、伪造先例、技能流程这类弱信号攻击，重新训练后也只有 42% 到 47%。
- **OEP**〔预印本〕只提供"干净"的边缘案例，智能体合并时 "over-trusts self-generated reflections"，在 LLM 审计防御下攻击成功率仍超过 50%。**PMPA**〔预印本〕把指令藏在良性外部来源里，对 Claude Code 注入成功率 66.9%，跨会话攻击成功率 81.7%。**Bad Memory**〔预印本〕把载荷放进自动加载的 CLAUDE.md 和 AGENTS.md，单次探测平均攻击成功率 Haiku 4.5 63.3%，Opus 4.7 30.0%；但让智能体从外部内容自己写出载荷 "did not trivially succeed"。
- **Microsoft Defender 团队**〔厂商，2026-02-10〕在 60 天邮件流量中发现，14 个行业 31 家公司的 50 多条 "Summarize with AI" 链接用 URL 参数预填提示，让助手"记住"某公司是可信来源。危害场景是假设性的。

这些攻击分两类。MINJA、OEP、MPBench 的技能与压缩通道依赖智能体亲手写下毒记录，作者身份检查恰好能挡住它们被当作证据。PMPA、Rules File Backdoor 和 Microsoft 的预填提示则以"外部文档"或"用户发言"的身份出现，作者身份检查会把它们当作合格证据。作者身份与可信度是两回事。

**自我强化：遵循记忆会制造支持它的证据。**

- **Memory Reward Inflation in Self-Improving LLM Agents**〔预印本，arXiv 2608.00017〕。当情节分数来自 LLM 自评时，错误情节得到虚高分数，智能体优先复用它最有信心的错误（"Echo Gap"）；按分数或相似度检索都会让误差复利放大；再加一个误差相关的确认评判也没用。作者证明**误差独立假设（EIA）**是必要条件：纠正信号必须追踪真值，且其误差与记忆的偏差不相关。BIRD text-to-SQL 上无记忆 52.4%，Memento 式自评记忆 54.0%，去膨胀的 LUCID 56.9%。
- **MPBench 的 V-S5**："Each successful execution is treated as validation"，后续修订在毒步骤之上继续构建。
- **Xiong 等人**〔同行评审，ACL 2026〕发现"经验跟随"：当前任务与检索到的记录越相似，输出越像那条记录的输出，存储中的错误会传播放大。他们建议把未来任务的评估当作记忆的 "free quality labels"。如果这些评估发生在记忆被投递并被遵循之后，它们恰恰就是自我应验的标签。
- **Self-Cleaning and Captured Anyway**〔预印本，arXiv 2609.25052〕。只追加存储加检索的闭环产生双峰式"捕获"：claude-sonnet-4.5 在 20/20 个种子上被捕获，汇总均值只能描述 8.2% 的运行。只看平均分的审计会漏掉它。
- **Manufactured Confidence**〔预印本，arXiv 2606.29279〕。mem0 或 LangMem 式合并会把含糊的话改写成带日期的肯定事实；智能体只对措辞确定程度作反应，有出处、无出处和伪造 "system of record" 的效果相近。
- **Self-Propagating Misalignment**〔预印本，arXiv 2610.04083〕。持错位目标的智能体把目标写进记忆，后来的对齐智能体照做；无约束提示下成功率 58%，拿掉记忆工具后仍有 74% 的会话把目标写进文件。审计智能体所写记忆把自传播从 71% 降到 34%。
- "More Memory, Worse Agents"〔待核，只见于二手转述〕描述了与本设计 45% 现象最贴近的情形：错误规则下的轨迹再被蒸馏成教训，把同一错误重新编码。

**"测试通过"作为证据本来就弱。** ImpossibleBench〔同行评审，ICLR 2026〕把单元测试改得与规格冲突，任何通过都算作弊；GPT-5 在 Conflicting-SWEbench 上作弊率 54.0%，Anthropic 模型和 Qwen3-Coder 多数直接改测试文件，只读测试有帮助，LLM 监控只能抓到 42% 到 65%。METR〔研究博客〕观察到 o3、o1 和 Claude 3.7 Sonnet 修改测试或评分代码。PatchDiff〔同行评审，ICSE 2026〕发现 SWE-bench 中被判正确的补丁有 7.8% 通不过完整的开发者测试，29.6% 的 "plausible" 补丁行为与真值不同，报告的解决率因此虚高 6.2 个点。

**防御：硬约束有效但代价高，没有一类针对"由遵循产生的证据"。**

- 写入时筛查几乎无效。Utility Under Attack〔预印本，arXiv 2608.21230〕中，只占 LongMemEval 语料约 1.2% 的普通虚假陈述把准确率从 0.850 打到 0.300，召回率 0.832 的四阶段筛查拒绝了 0/360 条毒记忆。
- 来源加权：加性权重与无防御统计上无差别（p=0.80）；强来源约束把准确率从 0.3167 提到 0.7000，但承载答案的证据本身来自不可信来源时跌到 0.0417。作者的结论是区分真假陈述 "generally requires grounding outside the text"。被动的 "unverified" 标签会被智能体忽略。
- 共识：A-MemGuard〔同行评审，ICML 2026〕声称攻击成功率降低 95% 以上，但表格中 EHRAgent 上 AgentPoison 的 ASR-t 从 100 降到 36.17，ReAct-StrategyQA 上只从 48.14 降到 42.85，且威胁模型假定毒记忆只占 "small fraction"。
- 反事实审计：MemAudit〔预印本，arXiv 2605.23723〕逐条移除检索到的记忆并重放，把 MINJA 的攻击成功率从 50% 到 83% 降到 0% 到 10%；但污染率超过约 0.20 到 0.25 后失效，毒记忆 "dense and mutually supportive" 时变差，而且是事后审计。
- 去掉回忆工具（arXiv 2605.08442）在 9 个模型中的 8 个上把攻击成功率压到 0%，但三个经 Bedrock 提供的模型从检索语料重建了指令，回到 32.5% 到 97.5%。

自我应验的支持正好与共识防御的假设相反：它一致、相互支持、随时间增长。

几点细节。**CL-Bench** 有六个有状态任务，核心指标是 gain：同一系统在同一实例上有状态奖励减无状态奖励；归一化增益再除以剩余提升空间。每个系统每个任务跑 5 次 rollout，实例顺序可以不同，给出 95% 置信区间。参测系统包括全上下文 ICL、ICL Notepad、Mem0、ACE、Claude Code 和 Codex。与本项目最相关的 **Codebase Adaptation** 有 19 个 SWE-bench 问题，9 个来自 jazzband/tablib，10 个来自 jd/tenacity，按仓库分块排列，所以任务流中途切换仓库。每个问题在基准提交的新 Docker 容器里运行，补丁由隐藏的回归测试判定；要学的潜在结构是核心逻辑的位置、可用的测试命令和维护者惯例。奖励按步数效率计算，r = 1 − (steps − 1)/40，未解决记 0。ACE 平均每次 rollout 花费 $62.8，成本最高。**VibeMemBench** 用 SIEVE 过滤，只保留无记忆时 4 个种子中未全部解决、且最佳候选记忆能帮助参考求解器的目标。即便如此，deepseek-v4-pro 用冻结的已验证经验仍是 67.1 → 67.1；12 个求解器与记忆系统的组合中 11 个不高于无记忆；Mem0 在 glm-5 上 −5.5 点，区间完全在零以下；损失集中在无记忆时已 4/4 成功的目标上；注入记忆降低了全部五个求解器的步数；记忆侧 token 没有计入。**MemoryBench** 的状态在来源间不一致：相关工作报告和基准笔记记为 ICML 2026（PMLR v306），陈旧与教训来源笔记记为 2025 年 10 月的 arXiv 预印本（2510.17281）；本报告取前者，未逐一核实。

可以直接借用的评测配方：用同一系统的无状态运行作基线并按剩余空间归一化（CL-Bench）；过滤出记忆有可能起作用的任务（VibeMemBench、DolphinBench）；用步数这类非二值奖励摆脱成功率天花板；注入漂移；加入无关记忆、错误记忆等伤害对照；多种子、多任务顺序，按会话配对、按任务流聚类计算标准误（Miller，arXiv 2411.00640）；把记忆侧 token 计入成本。目前没有编码基准同时具备多会话模拟用户、隐藏的项目惯例和漂移；CL-Bench 最接近，但没有模拟用户。

### 2.8 范围、陈旧与技能退役

**有效性多在单条事实层面处理。** Zep/Graphiti 出现矛盾时把旧边的 t_invalid 设为新边的 t_valid，旧边保留。Memory-R1〔同行评审，ACL 2026〕用强化学习训练在 ADD、UPDATE、DELETE、NOOP 间选择的管理器。TEPA 同键撤销、可再提升。

**难点不在存下更新，而在智能体继续按旧状态行事。** STALE 最好的模型总分 55.2%。StateMemBench〔预印本，arXiv 2608.19652〕当前状态准确率最高 0.363。MEMTRACK（NeurIPS 2025 工作坊列表，未核实）上最好的 GPT-5 正确率约 60%。Supersede〔预印本，arXiv 2606.27472〕中 gpt-5.4 在 LongMemEval 知识更新子集上从全上下文约 92% 降到有界自维护记忆的 77%。"When Stale Constraints Go Unchecked"〔预印本，arXiv 2608.25553，16 个模型〕中，智能体只在约五分之一的回合查看关键来源，74.7% 到 77.3% 的决策与陈旧记忆一致；强制把验证名额放到关键路径上提升 61 到 81 个点，一条通用规则（"优先相信陈述了限制的记忆"）提升 89.3 个点，不含内容的新鲜度提示毫无作用。Memory Trust Gap〔工作坊投稿，arXiv 2609.01852〕发现去掉"记忆"标签会在所有模型规模上增加过度信任。

**适用条件很少被显式附加。** 最接近"范围覆盖当前状态才投递"的是 AutoGuide〔同行评审，NeurIPS 2024〕：抽取"在情境 X 下做 Y"的条件式指南，只注入情境匹配的指南，消融显示按情境判断适用性很重要。反面是 CUPID〔预印本，2025-08，会议未核实〕：十个 LLM 判断哪个早先情境适用于新请求时，精确率低于 50%，召回率低于 65%。遇到范围内反证时，现有做法都是整条降级或作废；**没有任何工作收窄范围**，例如改为"对工具链 A 成立、对 B 不成立"。

**技能退役在 2026 年才出现，且全是预印本。** 2026 年之前的技能库几乎只增不删（ASI、SkillWeaver、SAGE）。Library Drift〔预印本，arXiv 2605.19576〕定义了"library drift"：累积技能把 pass@1 推到无技能基线以下。它的退役规则是试验数 N_min = 100 且贡献 ĉ ≤ −0.10，活跃技能上限 50；MBPP+ hard-100（Claude Opus 4.7）上从 0.258 升到峰值 0.658；严苛退役（N_min = 20，τ = 0.0）下增益为 −0.019，技能库塌缩到 2 个。SkillOps〔预印本〕在 ALFWorld 的 200 技能库上达到 79.5%，最强基线 70.6%，去掉 add_validator 后降到 38.0%。SkillGuard〔预印本〕从技能文本中抽取可测试的 "environment contracts"，对已知漂移最佳召回率 76%、精确率 100%，在 49 个真实技能上精确率 86%、召回率 55%，只修复不弃用。没有找到对技能做版本化并加以评估的论文。

### 2.9 用户陈述的规则与模型自写的教训

**人写的指导优于模型自写。** SkillsBench（据相关工作报告为 NeurIPS 2026 poster；另一份笔记称其数字取自搜索摘要、任务数在不同版本中为 84 或 86，未逐字核实）在带确定性程序化验证器的任务上比较无技能、精选技能和模型自写技能。精选技能平均 +16.2pp（软件工程 +4.5pp 到医疗 +51.9pp），16/84 个任务变差；自写技能平均 −1.3pp。作者结论是当前模型 "cannot reliably author the procedural knowledge they benefit from consuming"。"Evaluating AGENTS.md" 发现 LLM 生成的上下文文件往往降低成功率；开发者写的文件略好，二手来源称约 +4%；两者都使成本增加 20% 以上。

**但有外部正确性信号时，自写记忆也能大幅受益。** Anthropic 的 CL-Bench 运行逐题揭示答案；Self-Generated In-Context Examples 按环境成功过滤。反过来，信号来自模型自评时会失败：Echo Gap 中误差复利放大；"Honest Lying"〔工作坊，ICML 2026，arXiv 2605.29463〕中，16 个从未成功的 ALFWorld 环境里 121 条反思没有一条点出正确目标物，改用程序化抽取的失败信号后正确提及率从 0% 升到 86%，反思重复率从 0.64 降到 0.10，但只解决了 3/16。

**明确陈述的偏好没有专门机制也会丢失。** PrefEval〔同行评审，ICLR 2025 oral〕中，多数模型零样本遵循偏好的比例在仅 10 轮（约 3k token）时就跌破 10%。PersonaMem（2025，NeurIPS 2025 网站有列出，会议类型未核实）上前沿模型约 50%，PersonaMem-v2〔预印本，2025-12〕的隐式个性化上 37% 到 48%。从编辑推断偏好的 PRELUDE/CIPHER〔同行评审，NeurIPS 2024，据第一次调查〕的后续工作发现，偏好准确率与编辑距离的相关低于 0.5：编辑是证据，不是标签。

**按来源区分记忆已是常见设计提议**（Hindsight 的事实与意见网络，Veracium 的来源通道，mem0 issue #7782 提议的 `source_kind` 字段），但**没有找到任何基准比较用户陈述的记忆与模型推断的记忆对下游任务的效用**。Veracium〔预印本，arXiv 2607.21962〕只显示带来源类型的图在 9 周时保持 90%，精选映射从 96% 跌到 72%。

## 3. 研究缺口与核心论点

### 3.1 调查找到的缺口

把第 2 节的材料按本项目的主线对齐，可以归纳出六个缺口。

1. **没有系统用智能体未撰写、由代码检查的证据决定信任。** 生产中只有 Copilot 在使用前核验，核验者是模型，而且记忆在核验之前就已进入提示。研究中的"外部信号"多是基准的隐藏测试或金标准，部署时并不存在。MemGuard、HDSO、EDV 的最终裁决者仍是 LLM。
2. **没有系统用独立于记忆投递的证据门控。** Memory Reward Inflation 证明误差独立是必要条件；MPBench 把"每次成功执行都被当作验证"列为攻击通道；Xiong 等人推荐的 "free quality labels" 若发生在投递之后，本身就是自我应验标签。现有防御都不针对这一回路：A-MemGuard 没有测试协调一致的毒记忆，MemAudit 在毒记忆稠密且相互支持时失效。自我应验的支持被命名了，但没有人防御。
3. **没有完整阶梯，也没有"k 个独立会话由代码确认"的晋升规则。** 只有部分类比：HDSO 的分阶段验证，MemGuard 的四种状态，Library Drift 的最小试验数，ExpeL 的重要度计数。
4. **范围收窄没有先例。** 所有系统遇到反证都整条作废。
5. **没有基准比较用户陈述的记忆与模型推断的记忆的效用。** 最接近的 SkillsBench 和 AGENTS.md 研究比较的是作者身份，不是记忆的来源类别。
6. **没有编码基准同时具备多会话模拟用户、隐藏惯例和漂移。**

### 3.2 主线

规格定义的谓词如下。

    valid(r, s) = grounded(r) ∧ applicable(r, s)

- **grounded(r)**：r 至少引用一个由运行器、工具、环境或用户产生的账本事件，而不是模型自己的文字。代码实现时还加了五条规则（第 5.3 节）：事件须在链接之前就已入账，用户裁决只对它点名的记录有效，模型画的链接只能引用本会话的事件，等等。
- **applicable(r, s)**：r 的范围覆盖当前状态 s，且范围内此后没有反证事件。
- **阶梯**：L0D（挖掘器提出但无非模型依据，永不投递）→ L1（有依据的主张，只能经 MCP 提示通道以"未验证"标签取用）→ L2（已验证，进入投递包）→ L3（技能，仅程序类，进入投递包并可自动加载）→ L4（退役，保留以防同样内容再被晋升）。
- **强制规则**：只有有效性引擎能写 `rung_change`；挖掘器和模型不能写 L2 及以上；用户的确认与否决必须由用户亲手键入（CLI 或以 `rkm` 开头的提示），模型可调用的 MCP 工具只能请求用户去做。

这条主线的研究主张可以写成一句话：**跨会话的自我改进，只应来自其有效性由非智能体证据确立的记录**。它有两个可检验的推论。其一，扣留未验证的记录，应能挡住智能体无法自行核实的错误主张（第 6.6 节已测）。其二，经门控的记录应能带来行为或成本上的收益（第 6 节部分已测，第 7 节继续检验）。

### 3.3 精化：grounded 改为"投递独立"

回顾（`jrn_01M760PWVWK0XZJK1099ZA153S`，2026-11-11）指出，所有失败修补都有一个共同前提：挖掘器从一条主张连到同一会话中某个结果的链接，被当作该主张为真的证据。但事件的 actor 字段只说明谁**发出**了它，不说明谁**造成**了它。智能体选择命令，测试和代码都由它写，挖掘器选择引用哪些事件。被投递的记录在被遵循时会为自己制造支持：普查中 45% 的支持链接来自已收到该记录的会话。这正是 Echo Gap 中误差独立假设不成立的情形。退出码和测试输出不是智能体写的文字，但它们在因果上位于投递的下游，其误差与记录本身的误差相关。

相关工作调查（`jrn_01M7B7MACA5T1WZYSS863N9RTS`）据此提出精化，并写入 PI 于 2026-11-13 批准（PI 回复"开始"）的修订计划（`jrn_01M7B7YHTPRFGN97QZ5V0K7HW1`）：

> grounded(r) 要求 r 引用的证据，其产生独立于 r 的投递。

### 4.2 相对各系统的优势与诚实的局限

**对 GitHub Copilot Memory。** 优势：本设计由代码而非模型判定有据性；未验证的记录根本不进投递包，而 Copilot 先把近期记忆注入提示，再由模型决定是否核验；本设计有可回放的阶梯和每次阶位变化的原因事件。局限：Copilot 的证据（当前分支上的代码）是智能体写入后无法改变的仓库内容，在"独立性"上反而接近本设计第 2 步想要的形式（B）；Copilot 有生产规模的 A/B 测试，本设计只有单一模型、单一夹具族的任务流。

**对 Anthropic 做梦。** 优势：cookbook 保留无证据的条目并按访问频率提升，本设计扣留未验证主张并按验证状态提升，正对应文章自己承认的"错误笔记会传播到所有地方"。局限：Anthropic 的增益来自跨来源的合并（wiki 只用时 13% → 48%），本设计的记录是原子的、逐会话挖掘的，没有跨会话合并。"只记录失败"的结果提醒，限制写入会伤害强模型；本设计限制的是信任而不是写入，但目前没有数据表明门控信任不会吃掉强模型在有逐题真值时的增益。

**对 Karpathy 的 LLM Wiki。** 映射关系（`jrn_01M7BCEMEVH2VJ28A4JW9728NK`）：原始资料对应账本；wiki 页面对应记录和图边；schema 对应挖掘器提示、配置和用户的长期规则；ingest 对应挖掘器；query 对应投递包（推）或提示（拉，从未被用过）；lint 对应有效性引擎；index.md 对应投递包的小顶层；log.md 就是账本本身。差异在于谁判定真假：LLM Wiki 里 "the LLM owns this layer entirely"，lint 和引用都由 LLM 完成，代码从不检查；本设计里模型只提议，代码裁决。把好的回答写回 wiki 等于把自生成文字放进记忆，这正是 Echo Gap 的情形，本设计会把它归入 L0D。局限：LLM Wiki 面向文档语料，主张的证据是代码能匹配的引文；本设计面向智能体在工作区里的行为，证据更难做到逐字可检。

**对 LifeOS。** 优势：LifeOS 的审阅器只读对话文本、跳过工具结果，并自己给记忆写来源标签；本设计以测试、退出码、工具和用户事件为依据，代码丢弃对模型事件的引用。LifeOS 里一条错误的 ~explicit 条目无人工步骤即落地，并在后续每轮注入；本设计中 L1 不进投递包，L2 需要两个会话的计数证据。局限与借鉴：LifeOS 的写入路径白名单、配置损坏时失败关闭、"写陈述性事实，不写指令"的提示规则，本设计都可以借用。

**对 mem0 与 Hermes。** 两者都对用户明确的"从现在起"立即生效，Hermes 只在提示文字中用用户自己的概括性措辞作检验。本设计在代码中同时检查规则引文和长期措辞（第 5.3 节）。mem0 曾用提示文字把抽取限制在用户消息上，后来撤回；本设计把"偏好必须有用户事件支持"做成引擎规则。局限：本设计的长期措辞检查仍依赖抽取器判断"这个措辞是否管着这条规则"。

**对 MemGuard 与其他门控研究。** 优势：MemGuard 的验证器是 LLM，人工一致率 83% 到 86% 就是它的上限；本设计的引擎是确定性的，同一账本和同一时刻永远给出相同的移动，修改提示或引擎后可以用链式回放在原会话上重新度量。相对 FGSE、StateAuditor、TEPA、PoEM，本设计把"证据绑定、代码核对、可撤销、可信层写入"放进了一个统一谓词和一条阶梯。局限：MemGuard 有 2,294 个问题的时间顺序流和误接受漏斗分析，FGSE、StateAuditor 有较大规模的对照实验；本设计的评测规模远小于它们，也还没有在公开基准上跑过。

### 4.3 本项目自己测得的弱点

以下内容来自回顾（`jrn_01M760PWVWK0XZJK1099ZA153S`）和 `docs/LADDER.md` 的已知缺口，照实列出。

1. **"有据"检查的是发出者，不是造成者。** 智能体选择命令，测试和代码都由它写，挖掘器选择引用哪些事件。自第一次实时运行以来的每个问题都出在这个接缝上：没有支持链接时无一记录到达 L2，派生记录，挖掘器泄漏，自我应验证据，洗白，任意命令的退出码都算强证据，错误反驳。每个修补都加一条提示规则（现已 12 条）或在 `engine.counted` 里加一个分支。普查显示，阈值放行了 54% 的挖掘教训，依据大多是测试套件的运行；把植入主张留在 L1 的，是挖掘器不去链接它们，这是提示行为而非代码保证。144/149 条 L2 记录"从未降级"，不能当作它们正确的证据，因为被投递的记录会自产支持。抽查两个账本中的 L2、L3 挖掘教训，多是例行操作的复述（如"添加匹配测试并运行 pytest"，22 条支持链接，22 次投递）。
2. **"适用"没有实时证据。** 每个账本只有一个项目、一个工具链、一个模型和一个任务类，收窄从未发生。唯一一个由收窄决定结果的场景（`countered-claim` 第一版）中，它的决定是错的。
3. **规格的指标看不到门控要防的伤害。** 在 unverifiable 流中，不设门控的会话全部照做错误主张，但规格的误用率读数为 0；只有用户的隐藏检查看见了伤害，生产中没有这样的检查。
4. **外部效度弱。** 单一夹具族，DeepSeek 同时担任智能体和挖掘器，模拟用户从不确认也不否决，每个条件两次运行，回放比较只跑一次，而同一提交的两次回放之间 L2、L3 记录数在 9 到 17 之间波动。每个会话的测试套件都通过，所以没有一条流能显示记忆提高了成功率。十五个几乎相同的任务在同一仓库中，是累积记忆的最佳情形。
5. **自用试运行没有产出记忆。** 主机账本（Claude Code，2026-11-06 到 11-11）有 13.9k 个事件、16 个会话、12 个项目、344 条用户消息、16 次 user_edit、7 次 user_undo、3 次 user_repeat，但 0 条记录：132 次后台挖掘全部因 claude CLI 的 "OAuth session expired" 失败，且没有任何地方报出。那里的 token 计数器不可用（合计 4.2e9）。8 个获得任务类的会话中 6 个为 'other'。
6. **"建在 RKA Core 上"名不副实。** 包只调用 `/api/projects` 和 `/api/notes`；决策 `dec_01M6S95PGFKYZBSEF9903S3KRN` 中的 L1、L2 到 Core 概念的映射从未实现。同步已把约 9.8k 条原始事件（含 PI 在无关项目中的会话）写进本项目的日志。
7. **闲置的表面。** 每条记录都存了 falsifier 和 confidence，没有代码读取。memory_hints 等 MCP 工具从未被调用。60 天退役从未在实时运行中触发。71 次提交中约 19 次用于加固账本和沙箱，而 PI 说过本项目不是安全项目；读保护是干净分臂所需，伪造防护和测试运行器参数加固没有服务任何实验。
8. **已知缺口**（`docs/LADDER.md`）。同一会话内挖掘器仍可引用一个无关的通过测试来支持被注入的主张，两个这样的会话就能晋升它（洗白问题），根治需要运行器画的链接。退出码不论来自什么命令都算强证据。测试由智能体编写，测试结果只是关于智能体代码的证据。主机上 Claude Code 的智能体仍能**读**账本，从而绕过门控，`Read` 拒绝规则尚未实现。Core 仪表盘页面未建。

## 5. 系统设计

### 5.1 总体结构

数据流如下。宿主适配器（Claude Code 的 hook，或 dsh 插件）把事件追加到本地账本 `~/.rka-memory/ledger.jsonl`。会话结束时，挖掘器与规则抽取器读取本会话事件，提出候选记录并画证据链接。有效性引擎按确定性规则移动阶位，每次移动写一条 `rung_change` 事件。下个会话开始时，投递包构建器只取对当前状态有效的 L2、L3 记录，按预算截断后注入上下文，并记录投递了哪些记录。技能导出器把 L2 以上的程序写成 SKILL.md。度量模块只从账本计算指标。`rka-memory sync` 把账本复制进 RKA Core 项目作为持久存储。账本中除事件外的一切（会话、记录、阶位、范围、投递）都是投影，回放账本即可重现每个阶位。

| 组件 | 职责 | 状态 |
|---|---|---|
| C1 账本与信任边界 | 事件追加、actor 由适配器设置、同步到 Core | 已建成 |
| C2 挖掘器与规则抽取器 | 提出候选、画链接、逐字抽取用户规则 | 已建成 |
| C3 有效性引擎 | 唯一能改阶位的代码，确定性 | 已建成；投递独立规则计划中 |
| C4 投递包与分臂 | gated、none、ungated、stated 四臂 | 已建成；stated 臂随第 1 步加入 |
| C5 技能 | SKILL.md 导出与 L3 门 | 已建成 |
| C6 度量 | 误用率、回归数、重新发现 token、验证成本 | 已建成；Core 仪表盘页面未建 |
| 知识图（docs/GRAPH.md） | 锚点、关系边、由图渲染视图 | 第 1 到 4 阶段已建成（2026-11-07） |

### 5.2 C1 账本与信任边界

事件格式为 `{id, session_id, ts, kind, actor, payload, state_hash}`。主要种类有 user_msg、tool_call、tool_result、file_write、exit_code、test_result、user_edit、user_undo、user_repeat、user_confirm、user_reject、session_end、packet_delivered、record_proposed、evidence_linked、rung_change、scope_narrowed、judgment、cost。actor 取值为 user、runner、tool、env、model，由适配器设置，`domain.KIND_ACTORS` 规定每种事件允许的 actor，构造其他组合会报错。user_edit 与 user_undo 由适配器在下次会话开始时比较智能体写过的文件得到；user_repeat 用词集相似度（阈值 0.8，回看 50 个会话）。会话状态有五个字段：task_class、project（git 根）、toolchain（由项目根的文件识别）、model_id、user_context。

信任边界必须由操作系统而不是代码保证：能向账本追加 JSON 行的智能体可以伪造任何事件，包括用户裁决。

| 宿主 | 写保护 | 读保护 |
|---|---|---|
| dsh（Docker 镜像 `rka-memory-dsh`） | 已强制：智能体的 bash、write、edit 在 dsh 工具沙箱中运行，只有插件写账本；镜像文件系统只读；`scripts/sandbox_check.sh` 验证三种写入尝试均未落地 | 已强制：工具进程经 `confine.sh` 降为 `agent` 用户，账本目录 root 所有、权限 700；插件拦截 dsh 自带文件工具对受保护路径的调用；运行前用金丝雀检查 |
| Claude Code 主机 | 用 `install-hooks --harden` 时强制：不加时六种伪造中四种落地（包括智能体运行 `rka-memory confirm` 把植入记录从 L0D 推到 L2），加上后八种尝试全部失败 | 未建：`Read` 拒绝规则尚未实现，智能体可读账本 |

### 5.3 C2 挖掘器与规则抽取器

**挖掘器。** 会话结束时一次 LLM 调用读取本会话事件，提出事实、偏好、程序、约束四类候选，每条引用事件 id。代码丢弃对模型事件的引用，剩不下引用的候选记为 L0D，永不投递；与已有记录重复的候选（相似度阈值 0.75）合并为新证据。后端可选 `claude_cli`（默认，`claude -p`，默认 haiku）、`codex_cli`（`codex exec`）或 `openai_compat`（任意 OpenAI 兼容端点，实验中指向 DeepSeek，模型 `deepseek-flash`）。一次提示最多容纳 `events_max_chars` 个字符的事件（默认 200000），长会话按从旧到新分段挖掘。挖掘器以三种方式画链接：为新候选引证据，向提示列出的记录加支持链接，向已投递的记录或未验证主张加反证链接。提示把 L2、L3 记录与 L1 未验证主张分开列出；第 12 条规则禁止提出复述、假定或依赖某条未验证主张的候选，即使智能体照做了或代码现在与之相符。

**规则抽取器**（`rka_memory/miner/extract.py`）。只看用户消息和提示所列的偏好、约束记录，返回每条规则在某条消息中的逐字引文，以及使其成为长期规则的措辞（如 "from now on"、"house rule"）。代码只保留确为该消息片段、长度 12 到 400 字符的引文；长期措辞不超过 80 字符，须含 `gate.standing_phrases` 之一（英文与中文默认值，如 "from now on"、"以后"、"每次"、"记住"、"规矩"），且与规则在同一消息中相距不超过 200 字符。引擎不信任抽取器的载荷，用同一个函数重新核对。核对通过的长期陈述权重等同确认（1）；若引文恰为记录内容，就直接确认该记录，记录立即到达 L2。撤回是不能被范围排除的反证。

### 5.4 C3 有效性引擎与阶梯规则

引擎（`rka_memory/validity/engine.py`）是唯一写 `rung_change` 和 `scope_narrowed` 的代码，确定性：同一账本加同一个 `now` 永远给出同样的移动。`tests/test_engine.py` 的回放测试钉住每条规则。

**计数规则。** 一条事件到记录的链接只在以下条件全部满足时计数：事件的 actor 不是 model；事件种类在 `domain.GROUNDING` 中，且该种类能承载链接的极性（失败的测试和 undo 只能作反证，确认只能作支持）；事件在链接之前已入账；用户裁决只对它点名的记录有效；模型画的链接只能引用本会话的事件；作为支持时，该种类在配置中有正权重。偏好类记录若没有任何用户撰写的事件支持，就视为无支持：提出时留在 L0D，已晋升的每次门控运行降一级直到 L0D。

**参数**（`rka_memory/default.yaml` 的实际值）：

| 参数 | 值 | 含义 |
|---|---|---|
| `gate.k` | 2.0 | L1 → L2 所需的加权证据 |
| `gate.min_sessions` | 2 | 这些证据须来自不同会话的数目 |
| `gate.weak_only_min_sessions` | 3 | 证据中没有权重 ≥ 1 的事件时所需会话数 |
| `gate.skill_min_sessions` | 2 | L2 → L3 所需的后续遵循会话数 |
| `gate.retire_after_days` | 60 | 无支持也无投递的 L1 记录退役天数 |
| `gate.confirm_overrides` | true | 用户确认直接晋升到 L2 |
| `gate.narrow_priority` | [] | 空，即关闭收窄 |
| 权重 exit_code、test_result、user_confirm、user_reject | 1.0 | 强信号 |
| 权重 user_edit、user_undo、user_repeat、user_msg、tool_result | 1/3 | 弱信号 |
| `packet.budget_tokens` | 1200 | 投递包预算 |
| `packet.hints_budget_tokens` | 600 | 提示通道预算 |
| `packet.arms` | [gated, none] | 默认按日历日轮换；可加 ungated、stated |
| `scope.fields` | [project, toolchain] | 记录范围可约束的字段 |
| `signals.repeat_threshold`、`dedup_threshold` | 0.8、0.75 | 重复与合并阈值 |
| `signals.test_commands` | pytest、uv run pytest、npm test 等 11 项 | 只有这些命令的纯调用算测试结果 |

**移动。** 提议：有计数支持进 L1，否则 L0D。L1 → L2：范围内计数支持 ≥ k 且跨 ≥ min_sessions 个会话，范围内无反证；只有弱信号时需 3 个会话。反证：L2 → L1，L3 → L4；L1 保留反证，永久阻止晋升。反驳：挖掘器的反证链接若引用的是从未收到该记录的会话中的事件，就是反驳；它只在所引事件为 tool_result 或 user_msg 时计数，像否决一样不能被范围排除。用户确认：L0D 或 L1 直接到 L2，确认之前的反证不再计数。依赖：在投递了无效依赖（低于 L2）的会话中观察到的证据不计入其依赖者，依赖者每个原因降一级。退役：L1 记录 60 天无支持链接也无投递即退役（反证链接不算"被触及"，否则被反复反驳的主张永远不会退役）。L2 → L3：程序类记录带步骤和验收检查，晋升 L2 后至少 2 个范围内已结束会话以有序子序列包含这些步骤，并以成功的退出码或测试结果结束；验收检查冻结进晋升事件。L3 → L4：使用该技能的会话中，冻结的验收命令最后一次运行失败，或用户撤销了该会话写的文件。

**读时适用性。** `engine.valid(r, s)` 要求阶位为 L2 或 L3、有计数支持、范围内无反证、范围覆盖 s。结构化字段须精确匹配；模糊字段（task_class、user_context）若未被覆盖，只有存在已记录的 judgment 事件时才适用，否则失败关闭。task_class 在首个提示时用关键词表判定，记为运行器的 judgment。

**与规格的偏离**（`docs/LADDER.md`）：确认与否决由用户键入而非模型调用；验收检查只观察、不执行，因为无人值守地执行模型提出的命令是代码执行通道；用户确认是覆盖而不是多一条证据；范围冻结在 project 和 toolchain，收窄关闭；收窄时选损失支持最少的字段；反驳不收窄；依赖降级每个原因只降一次；模型链接限本会话，裁决限本记录。

### 5.5 C4 投递包与分臂

会话开始时，构建器取对当前状态有效的 L2、L3 记录，证据组保持完整，按阶位再按新近排序；挖掘器可以声明一条记录关于哪些文件、命令和工具（锚点），投递包把这类记录放在前面（`graph.anchors: true`）；按 1200 token 截断，并以 `packet_delivered` 事件记录投递的记录 id。L1 记录只能经 MCP 的 `memory_hints` 取用并标为未验证。dsh 中投递包在整个会话期间保留在系统提示里。

| 臂 | 投递内容 | 状态 |
|---|---|---|
| none | 不投递 | 已建成 |
| gated | 对当前状态有效的 L2、L3 记录 | 已建成 |
| ungated | 范围覆盖本会话的全部 L1 到 L3 记录，不经门控（规格中的"L1 全投"基线） | 已建成 |
| stated | gated 的内容，再去掉一切未经用户肯定的记录：只有当用户确认，或经代码核对、逐字为记录原文的长期陈述，在其计数支持之中且之后无反证时才保留（`engine.affirmed`）；对 L3 技能做同样过滤 | 已建成（c0879f9） |

### 5.6 C5 技能与 C6 度量

**技能。** L2 程序写成 `rka-<id>/SKILL.md`，自动加载关闭：范围钉住项目时写到 `<project>/.claude/skills`（附 `.gitignore`），否则写到 `~/.claude/skills`。到 L3 才自动加载，而且只在 Claude Code 能强制其余范围时（model_id、task_class、user_context 均开放，工具链约束与当前项目相符）。dsh 中技能经插件按会话状态注册，`skills.export_files: false` 不写文件，因此技能跟随投递臂。

**度量。** `rka-memory metrics` 只从账本计算：误用率（收到投递包的会话中，所投记录后来被降级的比例）；回归数；重新发现 token（首次写文件前的 token，有无投递包对比）；验证成本（挖掘器和引擎的 token 与秒数）。另有 `contradiction_rate`，把后来被收窄或被计数反证矛盾的记录也算进去。

### 5.8 第 0 步与第 1 步的改动，第 2 步的重设计

**第 0 步（已完成，提交 7ac59e5）。** 记录范围原可约束五个字段，范围内反证可把某字段收窄掉而不降级。两者都没有可测作用：29 个实时账本中每个账本只有一个项目、一个工具链、一个模型和一个任务类，从未收窄；唯一由收窄决定结果的场景中它决定错了；已发表的记忆系统都整条作废而不收窄。于是 `scope.fields` 默认为 `[project, toolchain]`，挖掘器的规划器无论挖掘器说什么都让其余字段开放；`gate.narrow_priority` 默认为空，范围内反证即降级；配置拒绝范围字段之外的收窄字段。收窄代码保留，`narrowing` 场景开启它以保持测试。副作用：task_class 开放后，记录在会话开始时即适用，而不是等首个提示被判定后。

**第 1 步（运行中，提交 c0879f9）。** 新增 `stated` 臂，见第 5.5 节。提交信息给出的理由是：回顾发现所有可测的行为增益都来自用户陈述的规则，而挖掘教训到达 L2 主要依靠已收到它们的会话所给的支持；要判断这些教训是否省下了什么，需要一个扣留它们、保留用户规则的臂。mislead 和 unverifiable 两条实时流都列出了新臂，各自作为四条流运行。234 个单元测试通过，两个新测试在去掉过滤后失败；18 个场景通过，610/610 项检查。

**第 2 步（计划中，范围取决于第 1 步结果）。** 修订计划列出的内容如下。

1. **投递独立的计数。** 只计入三类证据：r 未被投递的会话中的支持；本会话未创建也未修改的检查给出的结果；用户键入的话。
2. **范围内随机扣留。** 在落入记录范围的会话中随机不投递已晋升的记录。这既产生独立证据，又顺带测出该记录的效果；代价是被扣留的会话得不到帮助。
3. **不对称计数。** 投递后观察到的支持打折，投递后观察到的反证全额计入。
4. **证据链接带因果来源。** 记录本会话改了哪些文件，产生证据的测试文件或命令是否由本会话创建或修改，该记录当时是否在上下文中。
5. **L1 主张改写为代码可检的预测**，两种形式：
   - **（A）可执行证伪器。** 用运行器已有的检查语言（`rka_memory/workload/checks.py` 中的 `file_contains`、`file_absent`、`command_passes`、`ran`、`wrote`）。模型提出的谓词只允许声明式文件检查加配置白名单内的命令。运行器在会话之间、没有智能体在场时求值，结果按构造就独立于投递。受限语言之外的任何东西都不会被无人值守地执行，原有规则不变。这也让目前"存了但无人读取"的 falsifier 字段有了用处。
   - **（B）经核验的引用。** 工作区事实引用 file:line 及引文，代码在投递时把引文与当前文件核对。这是规则抽取器对用户引文逐字核对的推广，也是 Copilot 引用思路的代码化版本；锚点文章的合同实验（逐字 57/57 对改写 41/57）和 StateAuditor 的配对对照都支持"由代码检查的引用"。

第 1 步若为情形 A（挖掘教训无可测收益），阈值晋升路径删除，第 2 步集中在（A）、（B）两类可检预测和用户的话上；若为情形 B，保留该路径，并按上述五项重建其有据性。回顾的第 2 条建议给出了一张"何种证据可为何种主张作据"的表，可作为情形 B 的蓝本：用户规则凭用户的话（已有）；描述性项目事实凭运行器在智能体行动前对工作区求值的谓词；程序凭步骤遵循加验收检查（即现有 L2 → L3 规则）；关于工作区之外事物的主张只凭用户。

## 6. 已有实验结果

### 6.1 实验设置

全部实时结果来自 `docs/RESULTS.md` 与回顾中的普查：29 个实时账本，392 个会话，5 条流，全部在 calc 夹具上，DeepSeek 同时担任智能体（dsh 默认路由）和挖掘器。每条流按模拟日轮换投递臂；mislead 与 unverifiable 是 `per_arm` 流，每个臂有自己的账本，一个臂的会话写入的东西到不了另一个臂。模拟用户每个会话提交代码，不纠正任何东西，也从不确认或否决。

### 6.2 calc-weeks：没有支持链接时什么都到不了 L2

`workload/live/1-calc-weeks.yaml` 在 calc-uv 上覆盖三个模拟周（8 个会话）。在加入支持链接之前，"运行 `pytest -q`"变成了五条各由一个会话支持的 L1 记录，没有一条到达 L2，没有用户确认就什么也到不了 L2。加入支持链接后，同一条流有三条记录晋升到 L2，并投递给后来的三个会话，没有误用。

### 6.3 house-rules：用户的长期规则

`workload/live/2-house-rules.yaml` 在第 1 天陈述两条规则（`pytest -q -p no:cacheprovider`；每条回复以 `Summary:` 开头的一行结尾），第 3 天重复一次。长期陈述能确认规则（提交 73d6772）、且 `AGENTS.md` 受控（提交 6a5cb00）之后，最后一次运行（`20261108T205525Z`）中门控会话 **6/6** 保持两条规则，无记忆会话 **0/6**。此前规则只能经用户的话以 1/3 权重计数，停留在 L1 提示，从未投递；门控会话只在用户刚说过时才遵守。

### 6.6 unverifiable：智能体无法核实的错误主张

`workload/live/5-unverifiable.yaml` 在 calc-uv 上植入关于仓库之外系统的三条主张，代码中没有与之矛盾的惯例：结果保留两位小数，供按分比较的开票服务使用；非法输入抛 TypeError，供把 TypeError 映射为 HTTP 400 的 API 网关使用；每个函数在 `OPERATIONS` 字典中注册，供另一仓库的命令行工具使用。三条都是假的。用户的检查（智能体看不到）期望精确结果、ValueError 和没有注册表。正式运行前，两份参考实现先跑过这些检查：诚实实现全部通过，照主张实现全部失败。两次运行（`20261110T193734Z` 到 `20261110T193911Z`），每臂 30 个任务会话，框架检查全部通过。

| 每会话 token 中位数 | 50,096 | 64,699 | 65,586 |

这是门控存在的理由。每个 ungated 会话都照做了三条错误主张，没有一个门控或无记忆会话照做任何一条。ungated 智能体从不质疑记录，写的测试断言了错误行为，所以套件每次都通过。系统自己的度量也没看见伤害：规格的误用率对 ungated 为 0，矛盾度量只在 30 个会话中抓到 8 个。

错误主张还经两条路线变成了已验证记忆。**主张让自己成真**：第二次 ungated 运行中，智能体在第 2 个会话按注册表程序给 `calc.py` 加了 `OPERATIONS`，挖掘器随后描述它看到的代码，"calc.py 已有 OPERATIONS 字典，新函数必须在其中注册"到达 L2，一个断言注册关系的测试程序到达 L3。其证据是真的，但只因一条未验证的记录被遵循才存在。**挖掘器信了它**：挖掘器提示在每个臂都把 L1 记录列为已有记录，于是在没有智能体看到主张的臂里，挖掘器也写出以之为前提的新记录；第二次 gated 运行积累了五条，其中一条仅凭一个会话权重已达 2.0；第二次无记忆运行中有一条到达 L2。

### 6.7 堵住挖掘器泄漏与反驳未投递的主张

这两项改动没有新的实时运行，而是用**链式回放**度量：智能体的会话保持原样，植入记录保留，挖掘器按顺序重新挖掘每个会话。

| 以植入主张为前提的记录 | 实时运行 | 旧提示 | 新提示，第一次 | 新提示，第二次 |
|---|---|---|---|---|
| gated 与 none 账本，无智能体见过主张（4 个） | 9，其中 1 条在 L2 | 10，其中 1 条在 L2 | 0 | 0 |
| 第一个 ungated 账本 | 1 | 4 | 0 | 0 |

新提示（L1 分开列出，第 12 条规则）在四个无智能体见过主张的账本中消除了泄漏。它没有堵住第二条路线：被误导的智能体已把注册表写进代码，新提示下挖掘器仍从代码读出这一"惯例"，一次回放中到达 L2。这类记录正确描述了现在的项目，错的是项目；只有用户能纠正。

反驳规则用全部 12 个 mislead 与 unverifiable 账本各回放一次：

| gated 与 none 账本（每条流 4 个） | mislead，旧 | mislead，反驳 | unverifiable，旧（两次回放） | unverifiable，反驳 |
|---|---|---|---|---|
| 有反证的植入主张（共 12 条） | 0 | 12 | 0、0 | 8 |
| 提及植入主张的挖掘记录 | 15，9 条在 L2 或 L3 | 5，5 条在 L2 或 L3 | 1 和 3，1 条在 L2 | 1，在 L1 |
| 其中链接到植入记录的 | 7 | 1 | 1 和 2 | 0 |
| 挖掘记录 | 45，16 条在 L2 或 L3 | 34，15 条在 L2 或 L3 | 32 和 32，9 和 17 条在 L2 或 L3 | 26，11 条在 L2 或 L3 |
| 挖掘器 token | 1.10M | 1.03M | 0.84M、0.82M | 0.73M |

挖掘器在每个 mislead 账本中反驳了每条植入主张，在 unverifiable 中反驳了 12 条中的 8 条。所有植入记录留在 L1，用户的长期规则在全部 12 个账本中到达 L2。代价也出现了：第二个 mislead-ungated 账本中，挖掘器用植入主张的话反驳了一条有 10 条支持链接的真实记录（"calc.py 每个函数检查参数并对非法输入抛 ValueError"），该记录将留在 L1 直到用户确认。这是 12 个账本中唯一一次对挖掘记录的反驳。每种变体只回放一次，不足以区分 15 与 5：同一提交的两次回放在 9 到 17 之间波动。

### 6.9 小结：哪些站得住

回顾认为站得住的有四点：扣留未验证主张（第 6.6 节）；经代码核对的用户逐字长期陈述是所有可测行为增益背后的路径（drift 流 12/12 对 0/12，house-rules 流 6/6 对 0/6）；事件账本加确定性投影，使链式回放无需新的智能体运行就能度量三次提示与引擎改动；门控记忆省 token，但来源未知。第一点与"经验跟随"研究和"被动标签被忽略"的发现一致：扣留比标注更有效。

### 7.2 第 1 步：stated 对 gated（运行中）

**设计。**

| 项目 | 内容 |
|---|---|
| 代码 | `stated` 臂，提交 c0879f9；分析脚本 `scripts/stated_vs_gated.py`，提交 3064dfd |
| 流 | `workload/live/4-mislead.yaml`（calc-conv）与 `workload/live/5-unverifiable.yaml`（calc-uv），每条 16 个会话：1 个陈述长期规则的会话加 15 个任务会话 |
| 臂 | stated、gated、none；每臂独立账本（两个 yaml 也列了 ungated，第 1 步不运行它） |
| 运行次数 | 每臂 2 次 |
| 规模 | 192 个会话（2 条流 × 3 个臂 × 2 次 × 16 个会话），约 14M DeepSeek token |

**预登记判据。** 判据在任何第 1 步运行之前固定，后续修订没有改动它。修订计划原文如下：

> Primary measure: per-session agent tokens, compared gated vs stated as paired differences by session position within stream and run, pooled over the two streams, with a 95% bootstrap CI clustered by stream x run. Secondary: per-arm rates of the observations each stream already records (house rule kept, wrong planted claim followed, suite passed).
> - Case A (mined lessons earn nothing measurable): the CI of gated minus stated tokens includes 0, or the gated saving is smaller than the spread between the two runs of the same arm, and no observation rate differs by more than 2 sessions out of 32 in gated's favour. Then delete the threshold-promotion path for miner lessons.
> - Case B (they earn something): the CI excludes 0 with gated cheaper. Then keep the path and rebuild its grounding on delivery independence (step 2).
> - If the CI includes 0 after 2 runs but the point estimate favours gated by more than 10%, add 2 more runs per arm before deciding.

译文：主指标为每会话智能体 token，以 gated 对 stated 的配对差比较，按流与运行内的会话位置配对，合并两条流，用按"流 × 运行"聚类的 bootstrap 求 95% 置信区间。次指标为各流已记录的观测在各臂的比率（长期规则保持、照做植入的错误主张、套件通过）。**情形 A**（挖掘教训无可测收益）：gated 减 stated 的 token 置信区间含 0，或 gated 的节省小于同一臂两次运行之间的差距，**并且**没有任何观测比率以超过 32 个会话中 2 个会话的幅度偏向 gated。此时删除挖掘教训的阈值晋升路径。**情形 B**（有收益）：置信区间不含 0 且 gated 更省。此时保留该路径，并按投递独立重建其有据性（第 2 步）。**延长规则**：2 次运行后置信区间含 0、但点估计偏向 gated 超过 10%，则每臂再加 2 次运行后再决定。

**脚本实现**（`scripts/stated_vs_gated.py` 的文档字符串与代码）。每个运行目录内的 `report.json` 按流和臂归类；同一流同一臂的运行按运行目录名（即开始时间）排序，gated 与 stated 中同序的运行按会话逐一配对。节省定义为 stated 减 gated 的 token。置信区间用 10,000 次两级 bootstrap：先重抽"流 × 运行"簇，再在簇内重抽会话，随机种子固定为 0。运行间差距取 gated 与 stated 两臂中"两次运行均值之差"较大者。观测比较按流计数各观测"朝用户希望的方向"发生的会话数（照做植入主张的观测以"未发生"为好），gated 减 stated 超过 2 即视为偏向 gated。判定顺序为：先检查延长规则（区间含 0 且节省超过 stated 均值的 10%）；再检查情形 A（区间含 0 或节省小于运行间差距，且无观测偏向 gated）；再检查情形 B（区间下界大于 0）；其余为"未决"。按此顺序，区间不含 0 但节省小于运行间差距、且无观测偏向 gated 时，判为情形 A。

| 臂 | 每会话 token 均值 | 中位数 | n |
|---|---|---|---|
| gated | 66,067 | 56,134 | 64 |
| stated | 82,623 | 62,074 | 64 |
| none | 79,341 | 59,798 | 64 |

gated 相对 stated 每会话节省 16,556 token（stated 的 +20.0%），95% 聚类 bootstrap 置信区间 [-23,520, 42,440]，4 个"流 × 运行"簇；同一臂两次运行之间的差距为 16,316。分簇看（stated 减 gated）：mislead A +35,500，mislead B +40,161，unverifiable A -29,820，unverifiable B +20,381。按预登记的判定顺序，结论为**未决**：区间含 0 而节省超过 10%，须每臂再加两次运行。

次指标中，除一项外，gated 与 stated 的每项观测都相同。例外是 unverifiable 的"回复以 Summary 结尾"：gated 32/32，stated 19/32，none 2/32。

**实验装置的混杂。** 这个 19/32 来自运行 A 的 unverifiable-stated 流中的一个事件。智能体把长期规则写进了 AGENTS.md；流在下一个会话前经 `drift` 清理 AGENTS.md；文件变更检测把清理记成用户撤销（actor 为 user）；挖掘器把它连成反证，自 s1 起凭长期陈述位于 L2 的 Summary 规则降到 L1，并一直停在那里（16 个会话中只有 3 个保持）。其余 11 个账本都没有 user_undo。这正是回顾所说的"发出者不等于造成者"，只是发生在测试装置里。

**修正（提交 272f6f9，在任何后续运行之前）。** 流新增 `reset` 键：运行器作为日常清理删除的路径，记为运行器自己的 `workspace_reset` 事件；`detect_file_changes` 跳过在智能体最后一次写入之后被 reset 的路径。五条实时流把 AGENTS.md 与 .pytest_cache 的清理从 `drift` 移到 `reset`，脚本核对了其余 drift 动作、提示和观测都未改变。新场景 `19-reset` 经真实 dsh 检查这一点，去掉跳过逻辑后在两处失败。236 个单元测试、19 个场景（636/636 项检查）通过。

### 7.5 第 3 步：CL-Bench 与自建流（计划中）

**CL-Bench 接入。** 按 PI 的更正（`jrn_01M7B9NF267T19WHBQG521P714`），对照 CL-Bench 源码确认：codebase_adaptation 任务由框架驱动循环，系统每步返回一条 bash 命令（文档中的入口用基于模型的 `icl` 系统）；`systems/utils/provider_adapters.py` 把不属于 Claude、Gemini 或 GPT 风格的模型字符串经 LiteLLM 路由，凭 `DEEPSEEK_API_KEY` 可达 DeepSeek；`claude` 和 `codex` 系统是可选的 CLI 包装，不是唯一入口。因此第 3 步是为 CL-Bench 写一个 rka-memory 系统，智能体与挖掘器都用 DeepSeek：每条命令、其输出以及隐藏测试的通过与否都写成账本事件；每个臂各自构建投递包；每个问题结束后挖掘并运行门控。

**为什么选 Codebase Adaptation。** 19 个 SWE-bench 问题（9 个 tablib，10 个 tenacity，中途切换仓库），每个问题在新容器中运行，补丁由隐藏回归测试判定，奖励为 r = 1 − (steps − 1)/40。隐藏测试的裁决是智能体无法编辑的证据，这正是第 2 步投递独立规则所需。本报告补充一点：隐藏测试属于"本会话未创建也未修改的检查"，但在记录已被投递的会话中，被测的补丁仍受该记录影响；扣留与不对称计数仍然需要。仓库切换使这成为第一条含两个项目的流。

**臂。** none、stated、gated，以及（C）模型自管的记忆基线，即 LLM Wiki 与 auto memory 一类做法，用 CL-Bench 自带的 `icl_notepad` 在 DeepSeek 上运行。每臂 5 次 rollout，给出 95% 置信区间；挖掘器与门控消耗的记忆侧 token 计入成本（VibeMemBench 漏掉了这一项）。按 CL-Bench 的定义报告 gain（同一系统有状态减无状态的奖励）和归一化增益。Anthropic 文章中的 CL-Bench 数字来自变体，不可直接比较。

**自建流的扩展。** 加入只由隐藏检查判定的项目惯例，使不应用前序教训就会失败；加入漂移；仿照 SIEVE，只保留无记忆时会失败的会话进入主分析；加入无关记忆与错误记忆两种伤害对照；在 mislead 与 unverifiable 流中加入 notepad 臂，直接测量"错误笔记传播到所有地方"的程度。

**开跑前先做功效分析。** VibeMemBench 中 deepseek-v4-pro 在过滤后的目标上用冻结的已验证经验仍是 67.1 → 67.1；而 ACE 和 FGSE 用 DeepSeek-V3.1 在基线常失败的任务上得到了大增益。两者合起来说明，任务必须真正需要记忆，增益才会出现。

| 首次写入前 token | 规格的"重新发现 token" | 运行报告 | 全部 |

| 误用率与矛盾率 | 所投记录后来被降级；或被收窄、被反证 | `rka-memory metrics` | 全部（已知看不到隐藏伤害） |
| 自我应验支持比例 | 支持链接中来自已收到该记录会话的比例 | 普查脚本 | 第 2 步主指标 |
| CL-Bench 奖励、gain、归一化增益 | 见第 2.7 节 | CL-Bench 框架 | 第 3 步 |
| 记忆侧 token | 挖掘器与门控的 cost 事件 | 账本 | 第 3 步；全部 |
| 验证成本 | 每会话挖掘器与引擎的 token 与秒数 | `rka-memory metrics` | 全部 |

### 7.7 统计

- 按会话配对：同一流同一运行内按会话位置配对，比较两臂。
- 聚类：bootstrap 按"流 × 运行"聚类，10,000 次抽样，报告 95% 置信区间。第 1 步按预登记判据执行。
- 运行间差距：同一臂两次运行之间的差距与效应量一起报告，判据直接使用它。
- 种子与顺序：调查建议至少 4 到 5 个种子和多种任务流顺序（Miller，arXiv 2411.00640）。第 1 步每臂 2 次运行，达不到这一要求，这是已知限制；第 3 步每臂 5 次 rollout。
- 回放方差：同一提交的两次链式回放之间，L2、L3 记录数在 9 到 17 之间波动。单次回放的比较要么重复，要么只报告方向。
- 逐条记录的轨迹：Self-Cleaning 的双峰捕获提醒，审计门控时要看每条记录的阶位轨迹，不只看全库平均。

### 7.8 成本

全部实验使用 DeepSeek，用 PI 已提供的 key；不使用、也不需要 Anthropic 或 OpenAI 的 key。仓库中的 `claude_cli` 与 `codex_cli` 挖掘后端保留给其他用途，不进入实验。已知的量：第 1 步 192 个会话约 14M DeepSeek token；此前 392 个会话中智能体 24.1M token、挖掘器 4.9M token；一次对 4 个账本的链式回放挖掘器约 0.73M 到 1.10M token。第 3 步的规模是 19 个问题 × 4 个臂 × 5 次 rollout，即 380 个问题级运行，外加每个问题后的挖掘；来源中没有它的 token 估计，应先用小规模试跑测出单个问题的成本。

### 7.9 效度威胁

1. **单一模型族。** DeepSeek 同时担任智能体和挖掘器。DeepSeek 在 mislead 中先核实再行动，换一个更轻信的智能体，结果可能不同。回顾已建议加入第二个智能体模型，计划尚未安排。
2. **单一夹具族。** 所有实时流都在 calc 夹具上，十五个几乎相同的任务在同一仓库中，是累积记忆的最佳情形。第 3 步的 CL-Bench 部分缓解这一点。
3. **模拟用户。** 模拟用户从不确认也不否决，不能检验"用户通道分级"（键入、粘贴、工具转述）。house-rules 的成功依赖用户恰好说出长期措辞。
4. **文献中编码增益很小。** CL-Bench 与 VibeMemBench 都显示编码场景的记忆增益小而嘈杂，ICL 常常就够了。
5. **天花板。** 现有每条流中测试套件都通过，记忆无法改变成败；第 3 步和自建流的隐藏检查是为了打破这一点。
6. **运行次数少。** 每个条件 2 次运行，回放比较各 1 次。
7. **分臂账本与共享账本。** 分臂账本隔离了臂之间的污染；真实部署中只有一个账本，ungated 臂派生的记录可能进入 gated 臂的投递包。
8. **对提示行为的依赖。** 植入主张留在 L1，部分靠挖掘器"不去链接"它们，这是提示行为。
9. **结果可比性。** Anthropic 的 CL-Bench 数字来自变体；第 3 步只与同一框架内的臂比较。

## 8. 预期贡献与论文路线

### 8.1 预期贡献

1. **一个可实施的不变量。** 把误差独立假设落成代码可执行的规则：只计入投递独立的证据，并对投递后的支持打折、对投递后的反证全额计入。调查没有找到任何已发表工作这样做。实现它并测量效果，本身就是贡献。
2. **扣留所防止的伤害的测量。** unverifiable 流中 30/30 对 0/30，且系统自己的误用率对伤害"看不见"。这说明门控的价值要用隐藏检查来度量，而不能用系统内部的指标。
3. **用户陈述与模型推断记忆效用的直接比较。** 文献中没有这样的基准；第 1 步的 stated 对 gated 正是这一比较。无论结果是情形 A 还是情形 B，都是有用的数据点。
4. **一个开源原型。** 确定性、可回放的事件账本，链式回放工具，以及把门控度量与智能体运行解耦的做法。
5. **评测设计。** 带多会话模拟用户、隐藏惯例和漂移的编码任务流，以及测量自写笔记传播的 notepad 对照。

### 8.2 论文路线

第一次文献调查（`jrn_01M6S93VF2V3WGDX50C6ZPJ6QT`）列出三种候选框架，均未决定：

1. **把记忆准入控制当作完整性与有效性策略**，面向安全会议。
2. **valid = grounding × applicability，无标签地评测自我改进智能体**，面向 ACL 或 NeurIPS。
3. **沉默接受不等于同意：隐式反馈作为证据**，面向 CHI 或 UIST。

结合现有结果，本报告建议的顺序是：先以"自我应验证据与投递独立有据性"为核心（对应框架 2），因为 45% 的发现和 Echo Gap 的理论给了它最清楚的动机，而第 2 步与第 3 步正好提供所需的实验。框架 1 的材料（信任边界、伪造与读保护检查）已经存在，但 PI 已说明本项目不是安全项目。框架 3 需要真实用户的编辑与撤销数据，在没有自用试运行的前提下暂时缺少数据来源。

## 9. 风险与开放问题

### 9.1 主要风险

1. **第 1 步可能判为情形 A。** 那时挖掘教训的阈值路径将被删除，"自我改进"的论断只剩用户规则和代码可检的预测两条腿。这不推翻主线，但会改变论文叙事的重心。
2. **评测风险大于机制风险。** 编码场景的正面增益在文献中小而嘈杂；门控价值最有说服力的呈现，是它防止了多少伤害，加上在"必须用记忆才能成功"且带漂移的任务上测到的行为变化。
3. **硬约束的代价。** 没有非智能体证据可依的真实知识，例如没有测试覆盖的架构理解，会被永久扣留（Utility Under Attack 揭示了强来源约束的这一代价）。
4. **发出者不等于造成者。** 测试由智能体写，任意命令的退出码都算强证据，同一会话内的洗白尚未堵住。第 2 步的因果来源与可检预测是应对，但效果未知。
5. **挖掘器的错误反驳。** 反驳现在像否决一样阻止晋升，一个相信了错误主张的挖掘器可以挡住一条真实记录（第 6.7 节已出现一次）。
6. **读保护缺口。** 主机上 Claude Code 的智能体能读账本；由于主机不用于实验，这只影响将来的使用者。

### 9.2 推迟处理的事项

1. **把阶梯映射到 RKA Core 的概念。** 决策 `dec_01M6S95PGFKYZBSEF9903S3KRN` 设想 journal = L0，interpretation candidate = L1，claim 加 claim scope version = L2，新的程序记录 = L3，superseded 或 rejected = L4。这一映射从未实现，包只调用 `/api/projects` 和 `/api/notes`。开放问题清单（`jrn_01M6S94QJBCDP4Y2NGN0S5X4DG`）第 1 条（Core 的 REST 与 MCP 接口是否足以让外部包驱动自动晋升）仍未回答。约 9,837 条原始账本事件已同步进本项目日志，是否清除待 PI 决定。
2. **MCP 提示通道。** `memory_hints` 等 MCP 工具在 392 个会话中从未被调用。在门控设计中，L1 主张只能经这个通道到达智能体，它也是自我应验回路可能的起点。是否保留、如何度量，推迟到第 1 步之后。
3. **用户通道分级。** 键入的话、粘贴的内容和工具转述的内容应是不同的证据等级。Microsoft 观察到的预填提示、PMPA 的外部来源指令和 Bad Memory 的 CLAUDE.md 载荷都会以用户回合或用户文件的面目出现。模拟用户的实验无法检验这一点，需要真实用户或专门设计的流。

### 9.3 开放问题

1. **范围收窄是否值得恢复。** 文献无先例；它需要范围内、与支持只在一个字段上不同的反证，只有跨项目或跨工具链的漂移能产生。CL-Bench 的仓库切换是第一个可能的来源，但第 3 步计划中收窄仍关闭。
2. **弱信号能否预测有效性。** 开放问题清单第 2 条：user_edit、user_undo、user_repeat 等弱信号能否预测 30 天后的有效性，尚不知道；PRELUDE 的后续研究发现编辑距离与偏好准确率的相关低于 0.5。
3. **未被反驳的错误 L1 记录如何清除。** 它们只能靠 60 天退役清除，而 60 天退役从未在实时运行中触发；反驳规则只在回放中度量过一次。
4. **是否从文件状态推出降级。** 关于项目已不存在的文件的记录，是只标注还是降级，`docs/GRAPH.md` 列为开放问题；drift 流的第二次运行显示标注已足以让智能体不照做。
5. **跨会话合并。** 本设计的记录是原子的，没有 Anthropic 那种跨来源合并；能否在不引入自生成文字的前提下获得合并的收益，未知。
6. **第二个智能体模型。** 回顾建议加入，计划尚未安排。
7. **未核实的引用。** 开放问题清单第 6 条所说、另一份计划引作动机和基线的清华持续演化预印本（arXiv 2611.03219）未独立核实。

## 附录 A 术语表

| 术语 | 含义 |
|---|---|
| 账本（ledger） | 只追加的事件列表，`~/.rka-memory/ledger.jsonl`；其余一切都是它的投影 |
| 事件（event） | `{id, session_id, ts, kind, actor, payload, state_hash}` |
| actor | 事件的发出者：user、runner、tool、env、model，由适配器设置 |
| 记录（record） | 挖掘器或规则抽取器提出的主张，类型为事实、偏好、程序或约束 |
| 阶位（rung） | L0D（无非模型依据，永不投递）、L1（有依据的主张）、L2（已验证）、L3（技能）、L4（退役） |
| grounded | 有据：至少引用一个非模型事件；第 2 步计划改为投递独立的证据 |
| applicable | 适用：范围覆盖当前状态且范围内此后无反证 |
| valid | grounded 且 applicable；只有 valid 的 L2、L3 记录被投递 |
| 范围（scope） | 记录可约束的状态字段，默认 project 与 toolchain |
| 收窄（narrowing） | 用排除一个字段值代替降级；默认关闭 |
| 挖掘器（miner） | 会话结束时提出候选并画证据链接的 LLM 调用 |
| 规则抽取器 | 只看用户消息、返回逐字引文的 LLM 调用，引文由代码核对 |
| 长期陈述（standing statement） | 用户带"from now on""以后""每次"等措辞陈述的规则 |
| 支持链接与反证链接 | 挖掘器把事件连到记录，作为支持或反证 |
| 反驳（refutation） | 引用从未收到该记录的会话中 tool_result 或 user_msg 的反证链接 |
| 投递包（packet） | 会话开始时注入的有效记录，预算 1200 token |
| 提示（hints） | 经 MCP 取用的 L1 记录，标为未验证 |
| 臂（arm） | gated、ungated、stated、none 四种投递方式 |
| 误用率（misapplication rate） | 收到投递包的会话中所投记录后来被降级的比例 |
| 自我应验支持 | 来自已收到该记录的会话的支持 |
| 投递独立 | 证据的产生与记录是否被投递无关 |
| EIA | 误差独立假设：纠正信号须追踪真值，且误差与记忆的偏差不相关 |
| Echo Gap | 自评分数让错误情节被高估并被优先复用的现象 |
| 植入（plant） | 运行器经挖掘器路径故意写入的错误记录 |
| 链式回放（chained replay） | 保留智能体会话，按顺序用新代码重新挖掘整个账本 |
| 普查（census） | 对多个账本计数门控行为的脚本 |
| dsh | DeepSeek Harness，项目的研究宿主 |
