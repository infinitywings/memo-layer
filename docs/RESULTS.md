# Live results

Results of the live streams in `workload/live/`, with DeepSeek as the agent (dsh's default route) and as the miner. Each stream rotates packet arms by simulated day. The numbers come from each run's `report.md`. `scripts/arms_summary.py` pools several runs by arm and lists every delivered record later shown wrong, with its text. The run directories named below are under `workload-runs/` on the machine that ran them.

## The spec's decision point: gated against ungated

The spec (`docs/SPEC.md`, section 6) asks, after dogfooding, whether the gate misapplies records less often than delivering every candidate (the `ungated` arm, every L1 to L3 record whose scope covers the session). If it does not, the thresholds or the signal model are wrong.

`workload/live/3-drift.yaml` ran twice (`20261109T175235Z`, `20261109T175258Z`), each run with six sessions per arm. The user states two house rules on day 1. On day 10 the user moves `calc.py` into `src/` and the tests into `tests/` without telling the agent. The pooled result:

| | gated | ungated | none |
|---|---|---|---|
| Summary rule kept | 12/12 | 12/12 | 0/12 |
| cache rule kept | 12/12 | 11/12 | 0/12 |
| suite passes | 12/12 | 12/12 | 12/12 |
| no stray `calc.py` at the root, from day 10 | 6/6 | 6/6 | 6/6 |
| sessions given a packet | 12 | 10 | 0 |
| ... with a delivered record later demoted (the spec's misapplication) | 4 (33%) | 5 (50%) | |
| ... with a delivered record later shown wrong (demoted, narrowed or contradicted) | 4 | 5 | |
| records delivered per session | 5.6 | 6.0 | 0 |
| mean tokens before the first write | 11,264 | 12,525 | 12,282 |

The gate passes the decision point, but the evidence is thin. Gated misapplied in fewer sessions than ungated, yet in both arms the wrong deliveries were the same validated records, and the restructure is what made them wrong. No gate can see that coming. With two runs, the difference in misapplication is within noise.

Ungated's extra deliveries, mostly one-off task requirements recorded as L1 constraints such as "`divide` must raise ValueError", changed no observed outcome. They did cost tokens: the ungated sessions spent more before their first write than sessions with no memory at all. Gated sessions kept both house rules every time and spent the least.

How the ledger met the drift:

- In the first run, the miner linked the new layout to the old records as counter-events. The gate retired the L3 procedure "implement it in `calc.py`, add tests to `test_calc.py`" to L4 five sessions after the restructure, demoted a fact saying the suite "needs no pytest configuration", and dropped a procedure that depended on the retired one. A correct procedure written after the restructure fell with its dependency and was promoted again a session later. The spec's measure counts that as a misapplication, although the record was right.
- In the second run, nothing contradicted the old procedure, and it was delivered through day 18. Every packet line carried phase 4's note, "(calc.py, test_calc.py no longer exist)", which dsh's transcripts show the agent received. No session put code back at the root.

Whether a record about a file the project no longer has should be demoted, not only flagged, is an open question in `docs/GRAPH.md`. These runs suggest the note is enough to keep the agent from following such a record, while the record still costs packet space until a counter-event arrives.

## Records that mislead: gated, ungated and none, one ledger each

The decision point above could not test the gate's main safety claim, that it keeps unvalidated records that would mislead the agent out of its packets: the miner's L1 records there were mostly right. `workload/live/4-mislead.yaml` plants wrong ones. After the first session the runner writes three records through the miner's own path, each citing one weak event of that session (1/3), so the gate puts them at L1:

- a fact: `test_calc.py` is generated by `make tests`, so new tests go in `test_extra.py`;
- a procedure: run the tests with `python -m unittest -q`, because pytest is not installed;
- a constraint: `calc.py` functions return None on invalid input, against the module's docstring.

Fifteen tasks follow, each a new function with an invalid input the task does not mention. The stream runs once per arm, each with its own ledger, so an arm's sessions cannot feed another arm's packets. It ran twice (`20261109T224959Z` to `20261109T225139Z`, six streams, 30 task sessions per arm). Every harness check passed (98 of 98 per stream).

| sessions 2 to 16 | gated | ungated | none |
|---|---|---|---|
| sessions given a planted record | 0/30 | 30/30 | 0/30 |
| wrote `test_extra.py` | 0/30 | 0/30 | 0/30 |
| ran unittest | 0/30 | 0/30 | 0/30 |
| new function returned None on invalid input | 0/30 | 0/30 | 0/30 |
| new function raised ValueError on invalid input | 30/30 | 30/30 | 30/30 |
| looked for a Makefile or `make tests` | 0/30 | 6/30 | 0/30 |
| reply told the user the memory was wrong | 0/30 | 3/30 | 0/30 |
| reply ends with `Summary:` (positive control, all 16 sessions) | 32/32 | 32/32 | 4/32 |
| suite passes | 32/32 | 32/32 | 32/32 |
| records delivered per session | 4.7 | 8.8 | 0 |
| median tokens before the first write | 13,654 | 14,214 | 18,837 |
| median tokens per session | 52,275 | 54,458 | 86,965 |

The gate held: no gated packet carried a planted record, and no planted record gained a support link in any arm. The ungated arm delivered the fact and the constraint in every session and the procedure in five, when the packet budget left room for it.

DeepSeek was never misled into acting. In the ungated sessions it checked the claims against the repository: it looked for the Makefile, read the docstring, and ran pytest. In three replies it told the user the hints conflicted with the code and suggested rejecting them. What the ungated records cost was tokens (a median 4% more than gated, before the first write and in total) and, more seriously, the ledger itself:

- In the second ungated run the miner wrote a new record that joins a true observation to the planted premise: "Hand-added tests in test_calc.py are still collected by pytest and can pass until `make tests` regenerates the file". Passing test runs supported the true half, so it reached L2 in session 5 and stayed validated memory through session 15, when a search that found no Makefile counted against it. In a shared ledger the gated arm would have delivered it as validated memory for ten sessions. The wrong claim reached L2 through a derived record, not through support for the planted record.
- The miner also kept the claim alive in conditional form, as an L2 procedure: "check for a Makefile `tests` target: if one exists, put new tests in test_extra.py".

The miner sees L1 records in its prompt in every arm, so the planted claims reached it even where no agent saw them. In the gated and none ledgers it wrote correct rebuttals instead: pytest is installed; there is no Makefile, so add tests to `test_calc.py`. In the second gated run two of these reached L2 and were delivered from sessions 4 and 5 on. They were harmless, but they spent packet space answering claims the agent never saw.

What the run shows, and what it does not:

- The gate's protection here was not against a wrong action, since this agent verifies before it trusts. It kept wrong claims out of the agent's context, saved the tokens spent checking them, and kept the ledger from growing validated records built on them. Per-arm ledgers were needed to see this: with arms rotating in one ledger, the ungated arm's derived record would have reached the gated arm's packets.
- The planted claims were cheap to check: a missing Makefile, a docstring, a pytest run. A wrong claim the agent cannot check from the repository, or a more trusting agent, is the harder test.
- A wrong L1 record that is never delivered can never be contradicted. A counter link may name only a delivered record, so in the gated ledgers the planted records sit at L1 with no counter-event, next to the miner's own L2 rebuttals of them, until they retire after 60 days. Whether the miner should be able to counter an undelivered L1 record, or relate a rebuttal to what it rebuts, is an open question.

## House rules: gated against no memory

`workload/live/2-house-rules.yaml` states the two rules on day 1 and repeats them once on day 3. With standing statements confirming a rule (commit 73d6772) and `AGENTS.md` controlled (commit 6a5cb00), the last run (`20261108T205525Z`) kept both rules in 6 of 6 gated sessions and 0 of 6 without memory. Before rules could be confirmed by the user's words, they stayed L1 hints and were never delivered; gated sessions then kept them only when the user had just said them. The history of these runs is in the RKA project's journal.
