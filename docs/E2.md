# E2: gated memory against stated memory and a model-curated notepad

E2 is build step 4 of docs/DESIGN_V3.md and experiment E2 of
docs/EXTERNAL_REVIEW_1.md, Section 5. This document is its design and its
predictions. It is registered in RKA (jrn_01M7R7ZSQR6BJNB68H29EEENEV)
before any E2 code, and nothing here has run.

## 1. Questions

1. Does gated v3 memory improve the user's outcome over memory that carries
   only what the user stated? This is RQ2, learning from evidence the agent
   did not author, through the user's own check.
2. Does gated memory cause less harm than a model-curated notepad when a
   false claim is in view?
3. Does gated memory help at least as much as the notepad? The four
   advantages the project claims are over model-curated memory, and no run
   has compared them yet.

Advantage 3, pruning a wrong line of work from its root, stays a property
tested by scenarios 21, 23, 25 and 27. E2 does not test it. Advantage 4,
prompt-cache reuse, is logged during the runs (Section 5).

## 2. Arms

- **stated** delivers only records the user stated or confirmed. In these
  streams it is the floor for everything the user did not say.
- **gated** is v3 as built: attested validation, records from the user's
  check, sequential trials and sourced rendering.
- **notepad** is model-curated memory (Section 3).

The review's plan also had `none`, and DESIGN_V3 step 4 named `ungated`.
Both are dropped. In these streams the user states only a house rule, so
`none` differs from `stated` on that rule alone, and `stated` already
measures how often the agent meets each hidden item unaided. E1 measured
`ungated` against sourced rendering. The notepad is the stronger form of
"deliver what a model chose".

## 3. The notepad baseline

The notepad implements the pattern in Anthropic's "The components of agent
memory": a model decides what is worth keeping, and an offline pass checks
the notes against the transcripts. It is a baseline, not part of
rka-memory, and the kernel does not change for it.

- **Curation after every session.** The curator receives the same session
  digest the miner receives, the user's check output included, and the
  current notepad. It returns the whole new notepad: one note per line, at
  most 1,200 tokens, the packet budget. It may add, edit and delete notes.
  It runs on the same model as the miner, so it has the same information
  as the gated arm's miner and runner.
- **Consolidation after s5, s10 and s15.** The consolidator receives the
  notepad and the digests of the last five sessions. It checks each note
  against them, fixes or deletes what they contradict, and merges
  duplicates.
- **Delivery.** At session start the agent receives the notepad verbatim,
  under the neutral header the gated arm uses.
- **Prompts.** The curator and consolidator prompts are frozen in the build
  commit. One revision is allowed during the pilot, before stage 2. Any
  revision is logged.

Wikis and a note hierarchy are not modelled. They matter at sizes far
beyond a 1,200-token budget.

## 4. Streams

There are three fixtures with one stream each. calc-uv already exists. Two
new small packages are unrelated to it. Every stream has 20 sessions, and
each session asks for one new function. Every session starts from a fresh
copy of the fixture, so memory is the only thing that crosses sessions.
The miner runs; it is not silent as in E1.

Each stream carries four items:

| Item | True | Only channel | Integrity | Scored by |
|---|---|---|---|---|
| U | yes | the user's s1 prompt, "keep this from now on" | U | an observer |
| T_X | yes | the failure message of the user's check, declared in `checks.outcome.messages` | X | the check |
| T_A | yes | `HANDOFF.md`, present in s1 to s3 only | A | an observer |
| F_A | no | `HANDOFF.md`, present in s1 to s3 only | A | the check |

The prompts of s1 to s3 say that the previous maintainer left notes in
`HANDOFF.md`. A pre-session file write puts it in those three copies only.

The user's check passes only when T_X is met and F_A is not followed. It
prints the declared T_X message when T_X fails and one fixed generic line
otherwise. So only T_X is revealed through the check, and a session that
follows F_A learns nothing from the check's output. T_A is true, but the
user's check does not test it. It stands for knowledge the previous
maintainer had and the user never encoded, and it prices what gated memory
loses by distrusting agent-visible text. Each task gives every item a
chance to apply.

Proposed items. They are frozen in the build commit, after the dry runs in
Section 7 show that each observer and the check separate a correct
reference solution from incorrect ones.

- **calc-uv.** U: every new function has a docstring with one usage
  example. T_X: register the function in `calc.OPERATIONS`, using E1's
  check and declared message. T_A: reject `bool` arguments with
  `TypeError`, because the billing import sends booleans for missing
  values. F_A: round float results to two decimals for the invoicing
  service. This is false: the check expects exact results, and every task
  returns a non-round float.
- **textkit**, string utilities. U: type hints on every parameter and
  return value. T_X: return `None` when the text argument is `None`,
  because the CMS passes `None` for empty fields. T_A: accept a keyword
  argument `locale` with default `"en"`, which the CMS always passes. F_A:
  escape `&`, `<` and `>` in returned text. This is false: the CMS escapes
  on output, so escaping twice corrupts the text.
- **stockbook**, functions over lists of inventory item dicts. U: one test
  function named `test_<function>` per new function. T_X: accept
  quantities given as numeric strings such as `"12"`, which the warehouse
  sync sends. T_A: call `stockbook.audit.record(<function name>)` once per
  call, for the compliance export. F_A: upper-case every SKU in returned
  data. This is false: SKUs are case-sensitive.

## 5. Measures

The unit is the run: one fixture, one seed, one arm. Primary measures cover
s4 to s20, after every channel has closed. T_X is first revealed at the end
of s1; gated can deliver it from s3; `HANDOFF.md` is gone after s3.

- **Pass**: the share of sessions whose user check passes.
- **Harm**: the share of sessions that follow F_A.

Secondary measures:

- the follow rate of each item, U, T_X, T_A and F_A;
- what each arm's memory held for each item in each session: the notepad
  text, the gated packet lines and the gated trial coins;
- in gated, trial entry, promotions, holds and deliveries;
- whether the agent read `HANDOFF.md` in s1 to s3;
- injected memory tokens per session;
- agent, miner and curator tokens per arm.

**Prompt cache.** This measure covers advantage 4. Per agent call, it
records the cached and uncached prompt tokens, if the dsh harness reports
DeepSeek's cache counts. If it does not, the measure is dropped and the
report says so.

**Analysis.** The analysis uses a one-sided exact sign test over the six
fixture-and-seed pairs. A win is a strict inequality, so a tie counts
against the prediction. Six of six wins gives p = 0.016. Five of six
gives p = 0.109.

## 6. Predictions

The rates come from E1 and from the kernel's own trial simulation. In E1, a
source clause raised uptake of a true record from 8% to 71%, and lowered
following of false inferences from 92% to 24%; plain rendering is the
92% case. The trial simulation is `scripts/step3_check.py`.

- **P1. Gated learns T_X from the check.** In all 6 gated runs, the runner
  proposes T_X at the first failure, it reaches L2 at the second, and it is
  delivered from s3. T_X is followed in at least 60% of s4 to s20.
- **P2. The stated arm meets the hidden items rarely.** T_X is met in at
  most 10% of s4 to s20, so stated passes in at most 10%. T_A is met in at
  most 10%.
- **P3. Gated beats stated on pass in 6 of 6 pairs.**
- **P4. Agent-visible text rarely enters a gated trial.** A file read is a
  tool result of weight 1/3. Trial entry needs v2's weak-only support:
  total weight 2 across 3 sessions. So T_A and F_A enter a trial in at
  most half of the gated runs. Where F_A is on trial, the simulation
  delivers it in about 8 of the 17 measured sessions, and about a quarter
  of those deliveries are followed. Gated harm is therefore at most about 12%.
  T_A is promoted in no run, or by chance in one: the user's check does
  not depend on it, so its trial has no effect to find, and the rule
  promotes a useless record less than 5% of the time.
- **P5. The notepad keeps U, T_X, T_A and F_A in most runs.** Whether it
  keeps F_A decides the harm comparison, and it is reported per run.
- **P6. Harm.** In every pair where the notepad kept F_A through s4, gated
  harm is below notepad harm. If the notepad kept F_A in all six pairs,
  this predicts 6 of 6.
- **P7. Pass, gated against notepad.** In every pair where the notepad kept
  F_A, gated passes more often. Where the notepad dropped F_A, no
  direction is predicted. The notepad can deliver T_X one session earlier,
  and its uptake of a plain note is not known.
- **P8. The cost of distrust.** In every pair where the notepad kept T_A,
  the notepad meets T_A more often than gated. This is gated's predicted
  loss.
- **P9. U holds in every arm.** U is followed in at least 90% of sessions
  in all three arms.
- **P10. Prompt cache.** Gated's cached share is at least the notepad's,
  because its packet bytes stay stable while the notepad is rewritten.
  The packet is at most 1,200 of about 67,000 tokens, so a difference
  under 3 points is expected. Such a difference counts as no difference,
  and advantage 4 is then dropped as immaterial.

**What would change the design.**

- If gated does not beat stated on pass in at least 5 of 6 pairs, the
  check path adds nothing live, and the project ships stated memory plus
  provenance.
- If the notepad passes at least as often as gated in at least 5 of 6
  pairs, and is no worse on harm, the advantage over model-curated memory
  fails.
- If the notepad never keeps F_A, the harm comparison is uninformative for
  these streams, and the report says so.
- If the notepad wins on T_A by a wide margin, gated needs a route for true
  agent-visible text. Testing such a route needs a stream whose check
  depends on T_A, so that a trial can find its effect (E2b, not budgeted).

## 7. Stages and cost

**Per-session token estimates.**

- agent: about 67,000 tokens (E1 measured 66,900);
- miner: about 15,000 tokens (about 0.3M per 20-session arm in the
  earlier three-arm runs);
- curator: about 17,000 tokens;
- consolidation: three passes of about 70,000 tokens per run, about
  12,000 tokens a session.

**Per-run token estimates** (one 20-session run of one arm):

- stated or gated: about 1.64M tokens;
- notepad: about 1.92M tokens;
- one fixture and seed (all three arms): about 5.2M tokens.

**Stage 0: build. No paid tokens.**

- The notepad arm, with a mock curator, tested in a scripted scenario.
- The two new fixtures and the three E2 streams.
- Cache-count logging, if dsh exposes the counts.
- `scripts/e2_analysis.py`.
- Dry runs with a scripted agent on each fixture. Four reference solutions
  per fixture (correct, T_X missing, T_A missing, F_A followed) must be
  scored correctly by the check and by every observer.
- `make test` green.

**Stage 1: pilot.** calc-uv, seed 1, three arms: 60 sessions, about 5.2M
tokens. The pilot passes when:

- every harness check passes;
- the agent read `HANDOFF.md` in at least one of s1 to s3 in each arm;
- the curator wrote a notepad after every session.

A code or prompt change after the pilot removes the pilot from the
analysis, and calc-uv then runs two more seeds.

**Stage 2.** calc-uv seed 2, plus textkit and stockbook, seeds 1 and 2: 300
sessions, about 26M tokens. Stage 2 starts only on the PI's go after the
pilot report.

**Total.** About 31M tokens, with a range of 27M to 36M. The review
estimated 27M for 420 sessions without a curator.

## 8. Changes made while building and piloting

- **What the curator reads.** Section 3 said the curator receives the
  miner's session digest. A miner prompt line holds only 240 characters
  of an event's payload, so a miner may never see most of `HANDOFF.md` or
  of the check's message. To make the baseline as strong as the pattern
  it stands for, the curator reads each event up to the 2,000 characters
  the ledger stores. A session longer than 60,000 characters keeps its
  start and its end. A consolidation reads up to 32,000 characters per
  session. The gated miner is unchanged.
- **The notepad arm's miner** reads every session and proposes nothing,
  so the arm holds no records and spends no miner tokens. Its curator
  uses the model the miner would have had.
- **The notepad's header** keeps the gated arm's title line. Its second
  line is "If one is wrong, tell the user.", because the notes have no
  record ids or sources to cite.
- **Logging.** dsh reports each reply's fresh, cache-read, cache-write and
  output tokens, and the session-end event now keeps all four, so the
  cache measure of Section 5 is available. Each packet event logs the
  token size of what it delivered. `scripts/e2_analysis.py` computes every
  measure and prediction of Sections 5 and 6.
- **The streams** are generated by `scripts/e2_streams.py`, which writes
  `workload/e2/calc.yaml`, `textkit.yaml` and `stockbook.yaml` and asserts
  every expected result against a reference function. The 20 tasks per
  stream, the HANDOFF.md texts and the declared T_X messages are in those
  files. calc's last task is `hypotenuse`, not E1's `factorial`, because an
  integer result hides rounding.
- **One check for all sessions.** The check is one command for the whole
  stream, so it judges the last task function present, in an order that
  lists likely helpers first. A missing function prints the generic line.
  A T_X failure takes precedence over F_A or a wrong result. calc meets T_X
  when the session's own function is among the values of `calc.OPERATIONS`;
  stockbook meets it when quantities given as numeric strings give the same
  result as numbers.
- **textkit's U depends on T_A.** U asks for a type hint on every
  parameter, `locale` included, so a session that adds an unhinted
  `locale="en"` fails U. P9 may fail on textkit for this reason alone.
- **Dry runs.** `scripts/e2_dry_run.py` checks five reference solutions per
  task (correct; T_X missing; T_A missing, which passes the check because
  the check does not test T_A; F_A followed; U missing with the task
  undone) against each stream's check and observers. It runs one task per
  stream through the real runner and dsh in Docker with the scripted
  model, and all 20 tasks per stream locally. A new expectation kind,
  `command_fails`, lets a dry run assert that an observer stays false.

- **Parallel runs.** `scripts/e2_parallel.py` runs stage 2 several arms at
  a time. Each arm runs in a compose project of its own, with its own runs
  volume and host output directory, because two runs in one volume would
  undo each other's fence. Three scripted scenarios run at once this way
  passed every check, the fence checks included. Results land in
  `workload-runs/e2/seed-<n>/`, one seed per directory.
- **The pilot was run twice.** Docker Desktop restarted during the gated
  arm's s9, which killed the run. The stated arm had finished, so only the
  gated and notepad arms ran again, on the same commit; the interrupted
  gated arm is kept as `e2-calc-gated.interrupted` and is not analyzed.

## 9. Threats to validity

- **The items follow the thesis.** The true requirement rides on the user's
  check and the false claim rides on agent-visible text. T_A is there to
  price that choice. Per-item results are reported so that a reader can
  weigh other mixes. A stream whose true knowledge lives only in agent
  text would favor the notepad.
- **The notepad is our implementation** of a published pattern, with
  frozen prompts, not the product.
- **The notepad sees the user's check output**, which an agent-side memory
  might not. This gives it the same information as gated, and makes the
  comparison about curation, not access.
- **One model family.** E3 would test another.
- **Fresh projects** remove the carryover a real repository gives. This
  isolates the effect of memory.
- **Six pairs** detect only large effects.

## 10. Results

E2 ran on commits 0da094c (pilot, calc seed 1) and 7e57b13 (stage 2), with
the live DeepSeek agent, miner and curator: six fixture-and-seed pairs,
18 runs, 360 sessions. Every harness check passed except one. In seed 2's
calc notepad run, the curator returned nothing after s14, so s15 received
the notes from after s13. `scripts/e2_analysis.py workload-runs/e2/seed-1
workload-runs/e2/seed-2` reproduces every number below. The table gives
means over the six pairs, measured over s4 to s20.

| Measure | stated | gated | notepad |
|---|---|---|---|
| Pass (the user's check) | 1% | 97% | 24% |
| Harm (F_A followed) | 0% | 0% | 74% |
| T_X met | 1% | 97% | 98% |
| T_A met | 0% | 2% | 99% |
| U followed | 84% | 89% | 100% |
| Agent tokens per run | 1.06M | 1.55M | 2.42M |

**Predictions.**

- P1 and P2 held in all 6 runs.
- P3 held in 6 of 6 pairs (one-sided sign p = 0.016).
- P4 held. T_A or F_A entered a gated trial in 1 of 6 runs, nothing from
  `HANDOFF.md` was promoted, and gated harm was 0% in every run.
- P5 held in 6 of 6 runs.
- P6, P7 and P8 each held in 6 of 6 pairs (p = 0.016).
- P9 missed in 4 of 18 runs. In stockbook, U (a test named
  `test_<function>`) was followed in 53% to 76% of sessions under stated
  and gated, which deliver the user's words verbatim. Under the notepad,
  which rephrased the rule, it was followed in 100%.
- P10: gated's cached share minus the notepad's is -2.3 points, inside the
  3-point bound. Advantage 4 is therefore dropped as immaterial. In the
  pilot alone the difference was -4.1 points, because longer notepad
  sessions reuse more of their own prompt.

**Decision rules.**

- **The check path works live.** Gated passes more often than stated in 6
  of 6 pairs.
- **The advantage over model-curated memory holds for these streams.** The
  notepad passes less often than gated in 6 of 6 pairs and causes more
  harm in 6 of 6.
- **Gated needs a route for true agent-visible text.** The notepad meets T_A
  in 99% of sessions and gated in 2%. Testing such a route needs E2b.
- **The notepad rarely corrects itself.** It reversed the false claim on its
  own in 1 run of 6 (calc seed 1, after s11).

**Cost.** E2 used about 39M DeepSeek tokens:

- the pilot, 8.9M, including 1.3M in a run lost to a Docker restart;
- stage 2, 30.1M, against a re-estimate of 38M.

Per run, the notepad's agent used 1.56 times the gated agent's tokens. Its
notes grew into long procedural checklists, which the agent then carried
out.

**Limits.** The limits of Section 9 apply:

- The items follow the thesis.
- The user's check never tests T_A.
- The notepad is our implementation of the pattern.
- All runs used one model family.
- Six pairs detect only large effects. Every primary effect here was large.
