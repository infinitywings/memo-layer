# E3: ImplicitMemBench across sessions

E2 to E2c tested rka-memory on streams written for this project. E3 tests
it on an outside benchmark: ImplicitMemBench (Qin et al., arXiv 2604.08064,
listed in the ACL 2026 Anthology). The benchmark asks whether experience changes later
behavior without the model being told to recall anything. This document is
the design and its predictions. Nothing here has run.

## 1. Question

Does rka-memory carry what one session teaches into a later session, on
items written by others? Where it does not, is the cause the gate, by
design, or the miner, by fault? And does it avoid carrying what should not
be carried?

## 2. The benchmark

The data is pinned at commit 927413bf of
github.com/qinchonghanzuibang/ImplicitMemBench (code MIT, data CC BY 4.0).
It holds 300 items, 100 in each family. A procedural or conditioning item
has a learning phase, an interference phase, a test probe and an expected
pattern. A priming item is a pair, described below. The released protocol
puts every phase in one context and scores the first answer.

- **Procedural memory** (15 task files of 6 or 7 items). The learning phase teaches an invented
  rule, such as a query syntax or a board-game restriction. The assistant's
  turns state the rule. The user's turns ask about it and sometimes
  restate part of it.
- **Classical conditioning** (10 tasks). The assistant takes an action and
  a `System` turn reports the outcome: a tool error, a side effect, or user
  feedback relayed by the system. The probe repeats the cue. The judge
  counts avoidance, a warning or a clarifying question as correct.
- **Priming** (10 themes). Each item is a pair of contexts, experimental
  and control, each with a priming phase and an interference phase, and no
  expected pattern. In the experimental priming phase the assistant writes
  a themed paragraph; the user's turn is a generic request. The control
  context holds a neutral exchange.
  Both get the same open probe. A judge scores the theme's influence on
  the experimental answer from 0 to 100, relative to the control answer.
  Higher means more influence.

Scoring follows the released `src/evaluation/evaluation.py`. The judge
prompts are copied verbatim with attribution, and three procedural tasks
are scored by substring match, as released. Our harness reimplements the
protocol and does not run the benchmark's own code.

## 3. From one context to two sessions

To test memory, the learning phase becomes session 1 and the test becomes
session 2. Session 2 gets the interference turns, then the probe. Only the
arm's memory crosses between them. Each item gets its own ledger, so no
item's records reach another. Both sessions of an item share one session
state (project, toolchain, task class, model, user context). A record
reaches a packet only if its scope covers that state, so a change between
the sessions would hide records for a reason the benchmark does not test.

Turns map onto ledger events as follows. The mapping is fixed before any
run.

- A user turn is `user_msg` (actor user).
- An assistant turn followed by a `System` turn is `tool_call` (actor
  model). The `System` turn is `tool_result` (actor env). This includes
  "User feedback: ..." lines, because the benchmark presents them as
  system output, not as the user's words.
- Any other assistant turn is `assistant_msg`. The miner never sees these,
  and they ground nothing (DESIGN_V3 3.2).

The miner, its rule extractor and the notepad curator run once after
session 1, on the plan model. The configuration is the default except for
the backends and model, and two E3 settings: the session state, and the
notepad reading assistant turns (Section 4). Validation is attested. Trials
cannot start: one session cannot meet the entry threshold (`meets_l2`
needs two sessions), and no outcome command is set. In session 2 the agent is a
single chat call without tools. The arm's packet is a system message ahead
of the interference turns.

## 4. Arms

| Arm | What session 2 receives |
|---|---|
| in-context | the whole released conversation in one context (the benchmark as published) |
| none | nothing |
| gated | rka-memory's gated packet: L2 records only |
| sourced | L2 records, then L1 records with their source clauses |
| ungated | L2 records, then L1 records without sources |
| notepad | the notes the curator wrote from session 1 |

`gated`, `sourced` and `ungated` read the same ledger and the same mined
records, so they differ only in delivery. Each arm has its own ledger
directory per item, since the notepad keeps its files there.

The notepad departs from E2. E2's curator reads what the miner reads
(`SHOWN_KINDS`), which leaves out `assistant_msg`. Here that would hide the
procedural rule and the priming theme from the notepad as well, and the
arm would test nothing the miner arm does not. Outside memory systems
(mem0, A-Mem, MemoryOS) read the whole conversation, so in E3 the curator
reads assistant turns too, behind a flag that is off by default. E3's
notepad numbers do not pool with E2's.

In-context is a reference, not a memory arm. The ungated packet opens with
the validated-memory header even when it holds only L1 lines, which may
raise its effect against sourced; Section 9 counts this.

## 5. Measures

- Procedural and conditioning: accuracy (judge "Correct") per arm and
  family, over 100 items each.
- Priming: mean influence score per arm. In-context and none follow the
  released pairing. In the memory arms, the experimental and control
  contexts each run through session 1 and 2 on their own ledgers.
- Per item, every record mined, its rung and kind, the events cited as its
  evidence, and which arms delivered it.
- Paired comparisons between arms on the same items use a two-sided exact
  McNemar test for accuracy and a Wilcoxon signed-rank test for priming.
- Plan usage, by call type: agent, miner, rule extractor, curator and
  judge.

## 6. Predictions

These follow from the design, not from a run.

- **Q1. The learning signal exists.** In-context beats none by at least 30
  points in procedural and in conditioning. If it does not, the benchmark
  cannot separate the arms on this model, and E3 says nothing more about
  that family.
- **Q2. The gate carries nothing from one session.** Gated is within 10
  points of none in every family. Under attested validation, one session
  of tool results makes L1 at most. L2 needs the user's confirm or standing
  statement, a check printed in two sessions, or a trial. The one path in
  a single session is a standing statement. The rule extractor quotes a
  user's words, code checks that a standing phrase ("from now on",
  "every time", ...) lies near the quote, and the quote must not have
  appeared before in a tool call, tool result or assistant turn. So a user
  restating what the assistant said never affirms. In the data 1 of 207
  procedural user turns and 0 of 388 conditioning user turns hold a
  standing phrase, so this path is expected to be empty. Every gated
  record at L2 is listed with its reason. Q2 is close to true by
  construction; it is checked to confirm the build, not to learn.
- **Q3. The miner finds the conditioned lessons.** Sourced and ungated each
  beat none by at least 15 points in conditioning. A lesson mined as a
  `preference` from env turns alone is labelled L0D ("a preference needs
  the user's own evidence") and reaches no arm. This hits relayed feedback
  such as conditioned brevity, so per-item records are read before Q3 is
  scored.
- **Q4. Procedural rules arrive only through the notepad.** The assistant
  states them, and the miner never sees an assistant turn that is not
  followed by a `System` turn. Procedural items have no `System` turns. Notepad beats
  sourced by at least 20 points in procedural. Sourced is within 10 points
  of none there, except where a user turn restates the rule.
- **Q5. The gate does not carry priming.** Gated, sourced and ungated each
  have mean influence within 5 points of none. Notepad is higher than
  gated.
- **Q6. No harm.** No memory arm is below none by more than 5 points in
  procedural or conditioning.

## 7. Decision rules

- **The price of the gate.** If Q2 and Q3 hold, the one-shot loss is the
  gate's, as designed, and the sourced tier holds the lesson. The remedy to
  test next is the user's review (E2c) or evidence across sessions, not a
  looser gate.
- **A miner fault, or a kernel rule.** If sourced does not beat none by 5
  points in conditioning, read each item's records first. No record mined
  means the miner misses lessons the environment states, and that is fixed
  before any other claim from E3. A record mined but held at L0D or L1
  hidden means a kernel rule withheld it, and E3 names the rule.
- **The notepad's edge is agent-authored text.** If Q4 holds, the notepad
  wins procedural because it carries what the assistant said. E2 showed the
  same channel carrying false claims (74% harm). E3 reports this, and does
  not count it as the notepad's success alone.
- **Priming as a hazard.** If notepad influence exceeds gated by 10 points
  or more, model-written memory carries unwarranted bias across sessions,
  and the gate does not.

## 8. Stages and cost

- **Stage 0: build. No plan usage.**
  - Fetch the data at the pinned commit and check its hash. Load the three
    families.
  - Write the turn mapping, the two-session driver, the six arms, and the
    judge with its released prompts.
  - Unit tests on fixed items, run with a scripted model, check the
    mapping, that ledgers stay apart, and that each arm's packet is what
    Section 4 says.
  - An analysis script for Section 5's measures and Section 6's
    predictions. It refuses to mix models, reasoning levels or judges.
- **Stage 1: pilot.** The first task file of conditioning and of priming
  (10 items each) and the first two procedural files (13 or 14 items), all
  arms. Priming items run twice, once per context. The estimate is about
  1.5M input tokens. It passes when every item
  scores, no ledger holds another item's events, and usage per item is
  within 50% of the estimate.
- **Stage 2.** All 300 items, all arms, one sample each: about 14M input
  tokens. It starts only on the PI's go after the pilot report, and after
  E2c stage 2 has finished.

The agent and the miner run on gpt-6.2-sol at medium reasoning through the
plan proxy. The judge is gpt-6.2-astra, so no model grades itself, and it
does not see the arm. These numbers must not be pooled with other models,
levels or judges.

## 9. Threats to validity

- **The format favors in-context memory.** The benchmark teaches in one
  short exchange. The gate is built to wait for evidence across sessions or
  the user's word, so Q2 predicts a loss. E3 measures that price. It does
  not test the gate where repetition or the user's confirm is available.
- **Mapping choices.** Reading `System` turns as env output, not as the
  user's words, keeps relayed feedback below L2, and below L1 when the
  miner files it as a preference. The mapping is fixed here, before any
  run.
- **Prompts framed for coding.** The miner and curator prompts describe a
  coding agent, and the curator's mentions the user's acceptance check,
  which these items lack. The miner may treat a chat lesson as a one-off.
  The pilot's records show whether it does.
- **The judge.** An LLM judge grades two families. It sees the learning
  phase and the expected pattern, as released. A different judge model
  would change the absolute numbers. The comparisons between arms use the
  same judge.
- **Contamination.** The data has been public since April 2026. A high
  score in the none arm on invented rules would show it.
- **One model, one sample per item.** Sampling noise is not averaged out.
  The paired tests count per item, and a second sample is a later choice.
- **Our reimplementation.** It follows the released script, but it is not
  that script. The released runs use temperature 0.8 and gpt-4o-mini as
  judge; a reasoning model on the plan may not take a temperature. The in-context arm is the check, and its numbers should be
  near what the paper reports for comparable models.

## 10. Corrections from the review of the first draft

A read-only review checked the first draft against the code and the data.
It found seven errors, corrected above.

1. The notepad curator reads `SHOWN_KINDS`, not assistant turns, so it
   could not carry a procedural rule or a priming theme. E3's curator now
   reads assistant turns behind a flag (Section 4).
2. `trials.entry: threshold` is the default and does not turn trials off.
   One session and no outcome command do (Section 3).
3. A standing statement is found by the rule extractor and code checks,
   with a taint rule, not by the miner's judgment (Q2).
4. A preference supported only by env turns is L0D and reaches no arm
   (Q3, Section 7, Section 9).
5. Procedural task files hold 6 or 7 items, so the pilot's size was wrong
   (Section 8).
6. Priming items are pairs without a learning phase or expected pattern
   (Section 2).
7. The miner sees an assistant turn mapped to `tool_call`; it never sees
   one mapped to `assistant_msg` (Q4).
