# Immutable, append-only and provenance-carrying data models, and their use in LLM agent memory and context

Research date: 2026-11-13. Source labels used below: **[classical]** = peer-reviewed or standards work that predates LLM agents; **[industry]** = practitioner article, book or vendor documentation; **[peer-reviewed]**, **[preprint]**, **[vendor]** for LLM-agent work. "(search summary; page not opened)" marks a claim taken from a search-result summary and not checked against the page itself.

## 1. Established patterns: what they are, where they come from

### Takeaway
Eight mature families all express change by adding records and derive "current state" by a fold or query over them: event sourcing, Datomic-style fact stores, content-addressed Merkle DAGs, CRDT operation logs, W3C PROV, nanopublications, RDF 1.2 triple terms, and incremental view maintenance. None of them makes deletion free: each needs a separate, explicitly lossy mechanism (crypto-shredding, excision, redaction, tombstone compaction), and each pays for reads with a materialized view, snapshot or index.

### Cited Findings

**Event sourcing and derived views [industry, 2005 onward]**
- Fowler's canonical article (12 December 2005) defines event sourcing as "Capture all changes to an application state as a sequence of events", and lists three consequences: complete rebuild (discard state and re-run the log), temporal query (state at any point in time), and event replay (correct a wrong past event by reversing it and later events, or by replaying with the correction). — [Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)
- Fowler treats current state as a cache: state "is purely derivable from the event log", so snapshots can be stored anywhere and taken in parallel; either the state or the log may be the system of record. — [Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)
- Fowler names external systems as the main complication: updates must go through a gateway that can be disabled during replay, and queries during replay need the historical answer, not the current one. — [Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)
- Kleppmann's 2015 talk transcript frames a database as "an always-growing collection of immutable facts" with materialized views derived from the log, and claims simpler code, better scalability and robustness, lower latency and more flexibility. — [Kleppmann, Turning the database inside-out](https://martin.kleppmann.com/2015/03/04/turning-the-database-inside-out.html) (search summary; page not opened)
- Greg Young's book *Versioning in an Event Sourced System* has chapters titled "Why can't I update an event?", "Basic Type Based Versioning" (with "Double Write"), "Weak Schema", "Negotiation", "Whoops, I Did It Again" (compensating actions, section "Accountants Use Pens"), "Copy and Replace", "Copy-Transform", and "Upcasting State"; only the table of contents was readable. — [Young, Versioning in an Event Sourced System](https://leanpub.com/esversioning/read)
- Upcasting is described by a practitioner as a middleware between deserialization and application logic that maps an old event schema to the new one. — [Dudycz, How to (not) do the events versioning?](https://event-driven.io/en/how_to_do_event_versioning/) (search summary; page not opened)
- A 2017 Young talk reported by InfoQ notes that when old and new software run side by side, consumers may read event versions they cannot deserialize. — [InfoQ, Versioning in Event Sourcing](https://www.infoq.com/news/2017/07/versioning-event-sourcing) (search summary; page not opened)
- Crypto-shredding (Verraes, 13 May 2019): "Encrypt sensitive information in an event and delete the key"; one key per resource such as a customer; deleting the key makes copies and backups unusable. The pattern is "only as good as your encryption and your key management practices". — [Verraes, Crypto-Shredding](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)
- The same page records a legal objection: encrypted personal data is still personal data under GDPR (attributed to Harrison J. Brown and his lawyer), with "Forgettable Payloads" (store the sensitive part outside the event and delete it there) recommended for personal data. The page presents this as one view, not a settled answer. — [Verraes, Crypto-Shredding](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)
- Kafka-style tombstones do not erase at once: compaction is asynchronous and segment-based, a consumer replaying from the earliest offset reads the personal data before reaching the tombstone, tombstones need subject-based keys, and they do not clean downstream warehouses, indexes, caches or backups. — [Conduktor, GDPR and Kafka: Right to Erasure](https://conduktor.io/blog/gdpr-kafka-right-to-erasure) (vendor blog; search summary; page not opened)

**Datomic-style immutable facts [industry; excision announced May 2013]**
- A datom is "an immutable atomic fact that represents the addition or retraction of a relation between an entity, an attribute, a value, and a transaction", a five-tuple (E, A, V, Tx, Op). "Existing datoms never change." — [Datomic, Data Model](https://docs.datomic.com/whatis/data-model.html)
- "Retractions state that an assertion no longer holds at some later point in time"; "'removing' occurs not by taking something away, but by adding a retraction"; "The original assertion remains unchanged." — [Datomic, Data Model](https://docs.datomic.com/whatis/data-model.html)
- "A db is a point-in-time, immutable value and will never change"; an as-of view "considers only datoms whose Op is true as of a certain Tx"; transactions are fully serialized and each carries a wall-clock `:db/txInstant`. — [Datomic, Data Model](https://docs.datomic.com/whatis/data-model.html)
- The docs state "Datomic is indelible and chronological" and also "Datomic is not append-only, and does not have the performance characteristics associated with append-only systems." — [Datomic, Data Model](https://docs.datomic.com/whatis/data-model.html)
- Excision "is the complete removal of a set of datoms matching a predicate", intended for privacy and retention; "Excision should never be used to correct erroneous data"; it is "permanent and unrecoverable" short of restoring a backup. — [Datomic, Excision](https://docs.datomic.com/operation/excision.html)
- "Every excision creates a permanent record"; excision attributes cannot themselves be excised; schema and bootstrap datoms cannot be excised; the effect runs in a background indexing job, "puts a substantial burden on background indexing", and the docs advise against excising more than a few thousand datoms at a time on a live system. — [Datomic, Excision](https://docs.datomic.com/operation/excision.html)
- Release 1.0.7469 fixed a bug that had prevented excisions from removing datoms from the as-of or history indexes. — [Datomic, Release Notices](https://docs.datomic.com/release-notices.html) (search summary; page not opened)

**Content-addressed Merkle DAGs [industry: Git; IPLD]**
- "Git is a content-addressable filesystem ... at the core of Git is a simple key-value data store." The key is the SHA-1 of a `<type> <size>\0` header plus content; objects are zlib-compressed. Blobs hold content, trees hold entries pointing to blob or subtree hashes, commits name a top-level tree and parent commits. Two versions of the same file both persist as separate objects. — [Pro Git 2nd ed., Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- IPLD: "since data is addressed by its content, it is also immutable by default"; changing data means creating a new object with a new address, and a DAG can link back to earlier versions. — [IPLD, Benefits of Content Addressing](https://ipld.io/docs/motivation/benefits-of-content-addressing/) (search summary; page not opened)
- In IPLD a link is a CID; linking "is always immutable, and uses hashes"; content-addressed links cannot form cycles. — [IPLD, Glossary](https://ipld.io/glossary/) (search summary; page not opened)

**CRDTs and operation logs [classical/peer-reviewed]**
- A CRDT overview notes that some older designs stored tombstones for removed data, inflating storage, while modern designs avoid that but still keep metadata that grows linearly with the number of replicas. — [Preguiça, Conflict-free Replicated Data Types: An Overview (arXiv 1806.10254, 2018)](https://arxiv.org/pdf/1806.10254) (search summary; page not opened)
- Automerge retains a full history of operations "in the style of a version control system", which drives its memory and load cost; Yjs and Collabs deliberately trim or compress tombstone metadata. — [Weidner et al., Collabs (arXiv 2212.02618)](https://arxiv.org/pdf/2212.02618) (search summary; page not opened)
- Eg-walker (Gentle and Kleppmann, EuroSys 2025) stores an event graph and reports "an order of magnitude less memory in the steady state" than existing CRDTs, document loading "orders of magnitude faster", and merging long-running branches orders of magnitude faster than OT. — [Eg-walker (arXiv 2409.14252)](https://arxiv.org/abs/2409.14252)
- The Eg-walker paper states that storing the event graph costs between 20% and 3x the size of the final plain-text file. — [Eg-walker PDF](https://arxiv.org/pdf/2409.14252) (search summary; page not opened)

**W3C PROV [classical/standard; W3C Recommendation, 30 April 2013]**
- Entity: "a physical, digital, conceptual, or other kind of thing with some fixed aspects". When an attribute changes the result is a different entity (the page's examples: a traffic light's green and red states; a news site on two different days). — [W3C PROV-DM](https://www.w3.org/TR/prov-dm/)
- Derivation (`wasDerivedFrom`): "a transformation of an entity into another, an update of an entity resulting in a new one". Revision (`wasRevisionOf`): "a derivation for which the resulting entity is a revised version of some original". Invalidation (`wasInvalidatedBy`): "the start of the destruction, cessation, or expiry of an existing entity by an activity". — [W3C PROV-DM](https://www.w3.org/TR/prov-dm/)
- PROV also defines Quotation (`wasQuotedFrom`, repeating some or all of an entity), Primary Source (`hadPrimarySource`), Attribution (`wasAttributedTo`), and Bundle: "a named set of provenance descriptions" that is itself an entity, which gives provenance of provenance. — [W3C PROV-DM](https://www.w3.org/TR/prov-dm/)

**Nanopublications [classical/peer-reviewed lineage, 2014 onward]**
- Nanopublications are small packages of Linked Data with provenance and metadata attached; trusty URIs embed a cryptographic hash of the content in the identifier, so any content change yields a new URI and the verifiable range is the whole reference tree reached by following trusty URIs. — [Kuhn and Dumontier, Trusty URIs (arXiv 1401.5775)](https://ar5iv.arxiv.org/html/1401.5775) (search summary; page not opened)
- "A nanopublication is persistent, you can never edit nor delete it." Retraction publishes a new nanopublication whose assertion uses `npx:retracts` with the retractor as subject and the retracted nanopublication's URI as object. — [nanopub docs, Retracting a nanopublication](https://nanopub.readthedocs.io/en/latest/publishing/retraction.html)
- A retraction is valid only if signed with the same public key as the nanopublication it retracts; nanopublications with a valid retraction are excluded from default search results; `find_retractions_of()` returns the retraction URIs. — [nanopub docs, Retracting a nanopublication](https://nanopub.readthedocs.io/en/latest/publishing/retraction.html)
- Superseding works like retraction but supplies a corrected successor (`npx:supersedes`); for someone else's nanopublication you cannot retract, so you publish your own nanopublication that disputes or corrects it. — [Nanopublication FAQ nanopub](https://registry.knowledgepixels.com/np/RARplnH5vXPc_Ew5Ub0jSI_pjPvl3gDSMkw_5fKzb3ivc) (search summary; page not opened)

**RDF 1.2 triple terms ("RDF-star") [standard in progress; Candidate Recommendation Draft, 13 November 2026]**
- "An RDF triple used as the object of another triple is called a triple term." A reifying triple has predicate `rdf:reifies` and a triple term as object; its subject, the reifier, can be the subject or object of other triples. — [W3C RDF 1.2 Concepts](https://www.w3.org/TR/rdf12-concepts/)
- A triple term is not asserted unless the same triple also appears as an asserted triple; several reifiers can point to one proposition, "such as statements with different sources". The data model itself is atemporal. — [W3C RDF 1.2 Concepts](https://www.w3.org/TR/rdf12-concepts/)

**Incremental view maintenance [classical/peer-reviewed]**
- Gupta, Mumick and Subrahmanian (SIGMOD 1993) give a counting algorithm that tracks the number of alternative derivations of each derived tuple, and DRed (delete and rederive) for recursive views, which first over-deletes a superset and then re-derives what still has support. Counting cannot handle recursive rules. — [Hu, Motik, Horrocks, Optimised Maintenance of Datalog Materialisations (arXiv 1711.03987)](https://arxiv.org/pdf/1711.03987) (search summary; page not opened); [GMS93 record](https://researchr.org/publication/GuptaMS93)
- Differential dataflow (McSherry, Murray, Isaacs, Isard; CIDR 2013) extends incremental computation to arbitrarily nested iteration by distinguishing why a collection changed (loop feedback versus new input) and reusing prior work; implemented in Naiad. — [Microsoft Research, Differential dataflow](https://www.microsoft.com/en-us/research/publication/differential-dataflow/) (search summary; page not opened)
- DBSP (Budiu, Chajed, McSherry, Ryzhyk, Tannen; PVLDB 16(7), 2023; VLDB 2023 best paper per Feldera) gives a general algorithm for incrementalizing arbitrary programs; it uses Z-sets, rows with integer weights that may be negative, so a deletion is a row with weight -1. — [DBSP (arXiv 2203.16684)](https://arxiv.org/pdf/2203.16684); [Feldera, Best Research Paper VLDB 2023](https://feldera.com/blog/Best-Research-Paper-VLDB-2023) (both search summary; pages not opened)

### Inferences
- The designer's target (immutable nodes, appended amendment nodes, views by deterministic traversal, every derived statement traceable) is closest to a combination of three of these: Datomic's assert/retract facts for the amendment vocabulary, nanopublication retract/supersede for "the correction is itself a signed node", and PROV for edge names (`wasDerivedFrom`, `wasRevisionOf`, `wasInvalidatedBy`). PROV's rule that a changed thing is a new entity is the same commitment as "nothing is overwritten".
- Reifiers in RDF 1.2 and PROV bundles both answer the same need: an amendment or a provenance record must be addressable so that it can itself be amended or attributed.
- Datomic's own statement that it is "not append-only" is a useful warning: an immutable logical model does not imply an append-only physical layout, and good read performance came from maintained indexes, not from the log.

### Gaps
- CQRS as a named pattern (Young, Dahan) was not sourced directly; the notes cover projections only through Fowler and Kleppmann.
- Kleppmann's *Designing Data-Intensive Applications* (2017) discussion of the limits of immutability and of deletion ("excision", "shunning") was not retrieved; neither were Shapiro et al.'s 2011 CRDT paper or the 2019 "Local-first software" essay. The report writer should cite these from the originals if needed.
- Truth maintenance systems (Doyle 1979; de Kleer 1986), the AI-side classical answer to retracting a premise and its consequences, returned no usable source in this session.
- Body text of Young's versioning book was not readable (table of contents only), so no direct quotes on weak schema or copy-replace.
- Publication years for the Pro Git 2nd edition and Datomic's first release were not on the pages read.

## 2. Per pattern: correction without overwrite, current state, read versus write cost, deletion, scale

### Takeaway
Every pattern represents a correction as a new record that points at the old one, and computes "current" by a fold, an index lookup of unretracted facts, or a head pointer. Writes are cheap and reads are expensive unless a snapshot, index or materialized head is maintained. True deletion is always out-of-band, lossy, and recorded as having happened.

### Inferences
- Content addressing and redaction pull against each other. If node identity is a hash of content (Git, IPLD, trusty URIs), removing or rewriting a node's content invalidates its identifier and every identifier that includes it. A design that needs both should hash a reference to a separately stored, separately deletable payload (the forgettable-payload shape) or keep the hash and replace the body with a recorded redaction marker, as Datomic's permanent excision record and Anthropic's version redact do (section 3).
- For an amendment-node memory, the classical options for "current" are three: fold at read time (cheap writes, read cost grows with amendment chain length), maintain a head pointer per key at write time (Datomic indexes, Git refs), or maintain derived views incrementally with support counting (IVM). Support counting is the piece that answers "which summaries must be recomputed when a source is retracted": a derived statement whose derivation count drops to zero is no longer supported. Recursion (summaries of summaries) is the case where plain counting fails and DRed-style over-delete and re-derive, or DBSP-style weights, are needed.
- Signature rules matter for retraction authority. Nanopublications only honor a retraction signed by the original key; a third party can only publish a competing claim. An agent memory with several writers (user, agent, background consolidator) needs an equivalent rule for who may retract what.
- Snapshots, projections and backups are all places where "deleted" content survives. Any view cache in the design must be either rebuildable from the post-redaction log or covered by the same erasure step.

### Gaps
- No peer-reviewed quantitative comparison of read cost versus write cost across these patterns was found; the table is qualitative apart from the OpenHands and Eg-walker figures.
- No authoritative regulator statement (EDPB or a national authority) on whether crypto-shredding satisfies GDPR erasure was retrieved; the sources conflict.
- Scale figures for Datomic, nanopublication networks and RDF-star stores were not collected.

## 3. LLM-agent systems, 2024 to November 2026, that use append-only logs, versioned memory or git-like structures

### Takeaway
By late 2026 the "keep the originals, derive the rest" shape is common but partial. Vendor systems keep immutable history behind a mutable head (Anthropic memory versions, Letta git-backed memory); research systems make the log or provenance graph primary (Zep/Graphiti, DISCERN, P-Mem, MAP-Graph, OpenHands). Most still build their derived views with an LLM, so the store is immutable but the views are not deterministic; ACE's non-LLM delta merge, OpenHands' replay and P-Mem's readout are the deterministic exceptions.

### Cited Findings

**Anthropic Managed Agents: memory stores, memory versions, Dreams [vendor; beta and research preview]**
- A memory store is a workspace-scoped collection of text documents mounted into the session sandbox under `/mnt/memory/`; the agent reads and writes it with ordinary file tools. Individual memories are capped at 100 kB (about 25k tokens) and a store holds at most 10,000 memories. — [Anthropic, Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)
- "Every mutation to a memory creates an immutable memory version (`memver_...`)"; versions belong to the store, survive deletion of the memory, and are attributed to the session that wrote them. Versions are retained for 30 days, with recent versions of a live memory always kept. There is no restore endpoint; rollback means writing an old version's content back. — [Anthropic, Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)
- Redact "scrubs content out of a historical version while preserving the audit trail (who did what, when)"; the current head of a live memory cannot be redacted. Updates can carry a `content_sha256` precondition for optimistic concurrency. — [Anthropic, Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)
- The docs warn that with `read_write` access "a successful prompt injection could write malicious content into the store. Later sessions then read that content as trusted memory"; `read_only` mounts are enforced at the filesystem level. — [Anthropic, Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)
- Dreams: "A dream reads an existing memory store alongside past session transcripts, then produces a new, reorganized memory store"; "The input store is never modified, so you can review the output and discard it if you don't like the result"; "The dream itself never deletes or modifies its inputs." Inputs are one memory store and 1 to 100 sessions; the output is a separate store, cloned from the input at start. — [Anthropic, Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)
- The dream pipeline is "a synthesis pass over the inputs, not an editor applied to the text of the store", so line-targeted instructions generally produce no change; the pipeline's own session is archived, not deleted, so its transcript stays available. No accuracy or quality numbers are published. — [Anthropic, Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)
- A session "keeps its conversation history until you delete the session", and the full event history can be listed. — [Anthropic, Session event stream](https://platform.claude.com/docs/en/managed-agents/events-and-streaming)

**Letta / MemGPT: memory blocks to git-backed "context repositories" [vendor; blog dated 12 February 2026]**
- Context Repositories are "a rebuild of how memory works in Letta Code based on programmatic context management and git-based versioning"; "every change to memory is automatically versioned with informative commit messages". — [Letta, Context Repositories](https://www.letta.com/blog/context-repositories)
- Each subagent gets an isolated git worktree so that "multiple subagents can process and write to memory concurrently", merging back "through git-based conflict resolution"; the sleep-time reflection process also works in a worktree and merges automatically. — [Letta, Context Repositories](https://www.letta.com/blog/context-repositories)
- The file tree is always in the system prompt, files carry frontmatter descriptions, and a `system/` directory marks files loaded in full. A defragmentation skill backs up the memory filesystem and has a subagent reorganize it into "a clean hierarchy of 15-25 focused files". The post reports no measurements. — [Letta, Context Repositories](https://www.letta.com/blog/context-repositories)
- Enabling MemFS detaches the legacy `memory(...)` tool and migrates memory blocks into the git-backed filesystem. — [Letta docs, MemFS](https://docs.letta.com/letta-code/memfs) (search summary; page not opened)

**Git Context Controller (GCC) [preprint; arXiv 2508.00031, v1 30 July 2025, v2 1 March 2026]**
- Context lives in a `.GCC/` directory: `main.md` (global roadmap) and, per branch, `commit.md` (milestone summaries), `log.md` (step-level trace) and `metadata.yaml`. Commands are COMMIT, BRANCH, MERGE and CONTEXT (read-only retrieval at several granularities). — [GCC (arXiv 2508.00031v2)](https://arxiv.org/html/2508.00031v2)
- `commit.md` and `log.md` are appended to; `main.md` and `metadata.yaml` are "updated" or "revised", and each COMMIT regenerates a coarse summary. — [GCC (arXiv 2508.00031v2)](https://arxiv.org/html/2508.00031v2)
- SWE-Bench Verified (N=500), Claude 4 Sonnet: ReAct 0.682, Summary 0.666, Folding 0.740, GCC 0.802. Ablation on the same setting: baseline 67.2, plus roadmap and COMMIT 69.1, plus detailed logs and CONTEXT 75.3, plus metadata 77.8, plus BRANCH and MERGE 80.2. BrowseComp-Plus (N=150), Claude 4 Sonnet: GCC 0.786 versus Folding 0.720. — [GCC (arXiv 2508.00031v2)](https://arxiv.org/html/2508.00031v2)
- GCC uses more tool calls (GPT-5 on SWE-Bench Verified: 101.5 versus 95.3 for Folding). The paper has no limitations section and its text contains figures that do not match its tables ("over 24%" for GPT-4.1 and DeepSeek). — [GCC (arXiv 2508.00031v2)](https://arxiv.org/html/2508.00031v2)

**Zep / Graphiti [preprint; arXiv 2501.13956, 20 January 2025]**
- Each edge carries four timestamps on two timelines: `t_valid` and `t_invalid` (when the fact held in the world) and `t_created` and `t_expired` (when the system learned and invalidated it). On a contradiction an LLM compares the new edge with related edges and sets the old edge's `t_invalid` to the new edge's `t_valid`; the old edge is kept. — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)
- Raw episodes are a non-lossy store; episodes and semantic edges keep bidirectional indices so a fact can be traced to its source. The authors state they did not evaluate these links. — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)
- Community summaries are updated incrementally by a single label-propagation step, which drifts from a full recomputation, so periodic full refreshes are needed. — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)
- Results: DMR 94.8% (gpt-4-turbo) versus MemGPT 93.4%, with recursive summarization at 35.3% and full conversation at 94.4%. LongMemEval-S with gpt-4o: 71.2% versus 60.2% full-context, 2.58 s versus 28.9 s, about 1.6k versus 115k context tokens. Single-session-assistant questions dropped 17.7% (gpt-4o). Zep's latency included a residential network hop that the baseline's did not. — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)

**OpenHands Software Agent SDK [peer-reviewed; MLSys 2026; arXiv 2511.03690]**
- Every interaction is an immutable event appended to an `EventLog`; `ConversationState` is the only mutable component; events are stored as individual JSON files and a conversation resumes by loading `base_state.json` and replaying events. — [OpenHands SDK (arXiv 2511.03690v2)](https://arxiv.org/html/2511.03690v2)
- Context compression is itself an event: the SDK "preserve[s] the entirety of the event log, regardless of condensation"; before each LLM call the agent applies condensation events by dropping the forgotten events and inserting the summary. — [OpenHands SDK (arXiv 2511.03690v2)](https://arxiv.org/html/2511.03690v2)
- The Condensation event records the `forgotten_event_ids` alongside the summary. — [OpenHands docs, Condenser](https://docs.openhands.dev/sdk/arch/condenser) (search summary; page not opened)
- Results: system-attributable errors fell from 78.0 to 30.0 per 1,000 conversations (61%) from V0 to V1 in a 15-day rollout; SWE-Bench Verified 72.8% (V1, Sonnet 4.5) versus 64.6% (V0); the LLM summarizing condenser cuts API cost by up to 2x with no reported loss (attributed to a 2025 source). — [OpenHands SDK (arXiv 2511.03690v2)](https://arxiv.org/html/2511.03690v2)

**ACE, Agentic Context Engineering [peer-reviewed; ICLR 2026; arXiv 2510.04618]**
- Context is a set of itemized bullets, each with a unique id and helpful/harmful counters. A Reflector proposes small candidate deltas, a Curator integrates them, and deltas are "merged deterministically into the existing context by lightweight, non-LLM logic". New bullets are appended; existing ones are updated in place (counters); embedding-based de-duplication runs after each delta or lazily. — [ACE (arXiv 2510.04618v3)](https://arxiv.org/html/2510.04618v3)
- Results: AppWorld average 59.4 versus 42.4 for the ReAct base (DeepSeek-V3.1, offline); finance average 81.9 versus 69.1; adaptation latency 82.3% lower than GEPA offline and 91.5% lower than Dynamic Cheatsheet online; token cost 83.6% lower online. — [ACE (arXiv 2510.04618v3)](https://arxiv.org/html/2510.04618v3)

**DISCERN [preprint; arXiv 2611.15729, 11 November 2026; listed for the TTCL Workshop 2026; Amazon]**
- "An immutable, append-only, per-actor log is the single source of truth"; an entity-family graph, a bitemporal fact store and an episodic/profile layer are rebuildable views, a "reversible projection rather than the store of record". Confusable entities are linked by SIMILAR_NAME edges and never merged; superseded values get `expired_at` and are kept. — [DISCERN (arXiv 2611.15729)](https://arxiv.org/html/2611.15729)
- Entity, fact and edge views are LLM-extracted; only episode summaries and topic labels use deterministic distillers. Conflict resolution happens at read time through a read-only tool loop (at most 8 turns) with citation-or-abstain gates. — [DISCERN (arXiv 2611.15729)](https://arxiv.org/html/2611.15729)
- Results on the authors' synthetic ENT-310: answer correctness 0.861 versus 0.806 (extract-retrieve) and 0.788 (agentic RAG); abstention F1 0.924 versus 0.802 (HippoRAG2); Mem0 false-decline 0.867. LoCoMo: 0.663 versus 0.638 (HippoRAG2), with agentic RAG slightly ahead on abstention (0.827 versus 0.820). Read cost: 4.1 turns, 5.7 tool calls, 7.6 s mean per query. Write cost is not reported. — [DISCERN (arXiv 2611.15729)](https://arxiv.org/html/2611.15729)

**P-Mem, "Memory of Memory" [preprint; arXiv 2609.25054, 7 September 2026; NUS]**
- A typed temporal provenance graph with four node kinds (evidence, version, operation, tombstone) and four edge types (supported-by, supersedes, alternative-of, revokes). Operations are accept, contest, reject, revoke, resolve, noop. "The graph is append-only": items are retyped or relinked, never deleted. — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)
- Current value: each key's head is the most recent open version with status active or contested, under a one-current-value-per-key invariant; a deterministic readout renders the current value first with optional support, alternatives or history. Revoke or reject walks the supersedes chain to reinstate the prior value. — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)
- The paper positions itself between archival memory (settle at query time, retain) and CRUD memory (settle on arrival, erase). — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)
- Results: LongMemEval knowledge-update subset (n=78, oracle setting) accuracy 76.9 with stale rate 5.4, versus MemoryOS 66.7 and 22.6. LongMemEval-S overall 52.6 versus HippoRAG-v2 50.8 (not significant), Mem0 39.4, long-context 27.0. About 3k tokens per query versus about 11k (MemoryOS) and 106k (long-context). FactConsolidation single-hop at 6k/64k/262k: 95/95/88% versus Mem0 36/45/30%; multi-hop only 41/21/11%. — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)
- Write-time extraction pays for itself only after roughly 70 queries per history; with a small (4B) writer, materialized accuracy was 52.6% with a 33.3% stale rate. — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)

**Other provenance-typed memory graphs [all preprints, 2025 to 2026]**
- MAP-Graph (arXiv 2608.10509, 11 August 2026): a task-scoped execution-lineage graph with 8 node types (User, Agent, Tool, Resource, Message, Memory, Claim, Action) and 10 edge types including `derived_from`, `summarized_from`, `verified_by`, `invalidated_by`. New records append; revocation marks and retains affected records. On 2,700 synthetic tasks: task success 94.96% versus 74.67% for flat provenance, with 0% observed unauthorized access; removing the provenance stack drops success to 67.89%. Single run, synthetic, within-task only. — [MAP-Graph (arXiv 2608.10509)](https://arxiv.org/html/2608.10509v1)
- SodaMem (arXiv 2608.08055, 8 August 2026): typed FactEvents with mandatory provenance spans, mention time, occurrence time and validity, linked by SUPERSEDES, CONTRADICTS and UPDATES edges; a planner-reader loop gathers citable evidence before answering. Reports 92.8% on LongMemEval-S (best of 3, self-graded by the same model, about 18.3k tokens per question). — [SodaMem (arXiv 2608.08055)](https://arxiv.org/abs/2608.08055)
- MemIR (arXiv 2605.25869, 25 May 2026) names "provenance-role collapse", source-monitoring errors that arise when memory is stored as flat text, and writes memory as typed atoms separating raw evidence, retrieval cues and truth-bearing claims, with factual authority restricted to supported claim atoms. The abstract gives no numbers. — [MemIR (arXiv 2605.25869)](https://arxiv.org/abs/2605.25869)
- "Stored Is Not Supported" (arXiv 2609.02127, 2 September 2026): a typed provenance graph separating origin, dependency lineage, epistemic role, validity and disclosure scope, with a generate-verify-revise mediator; premise "Persistence changes availability, not epistemic standing". On 24 hand-authored conformance cases typed mediation released 0 of 19 unsafe candidates, a flat rule 19 of 19, source tags 18 of 19. The authors state this is not an end-to-end evaluation. — [Stored Is Not Supported (arXiv 2609.02127)](https://arxiv.org/abs/2609.02127)
- PROV-AGENT (arXiv 2508.02866) extends the W3C PROV data model with agent- and LLM-centric entities, activities and relations for tracing agentic workflows; it targets execution tracing, not memory supersession. — [PROV-AGENT (arXiv 2508.02866)](https://arxiv.org/pdf/2508.02866) (search summary; page not opened)
- A 2026 preprint contrasts a mutable Letta memory block with an append-only decision log (Engram), arguing the log supports audit and replay at higher operational cost. — [Entity-Collision (arXiv 2605.29630)](https://arxiv.org/pdf/2605.29630) (search summary; page not opened)

**Counter-position**
- Infini Memory (arXiv 2606.10677, 9 June 2026) appends to a buffer but then rewrites into topic documents with split and merge, arguing that when new observations contradict old ones "append-style storage can leave both versions available for retrieval". MemoryAgentBench overall 64.7 versus HippoRAG-v2 45.5 and Mem0 25.0; removing split and merge costs 6.7 points on LongMemEval-S; multi-hop selective forgetting is weak (35.0 versus 81.0 single-hop). — [Infini Memory (arXiv 2606.10677)](https://arxiv.org/html/2606.10677v1)

### Inferences
- Three distinct immutability levels appear, and they should not be conflated: (a) mutable head with immutable history (Anthropic memory versions, Letta git memory, GCC's `main.md`), which gives audit and rollback but still lets a rewrite lose content from the live view; (b) immutable log with LLM-derived views (Zep, DISCERN, Dreams), which keeps evidence but makes views non-reproducible; (c) immutable log with deterministic views (OpenHands replay, ACE merge, P-Mem readout). The design described in the objective is level (c), which is the least populated.
- Dreams is the closest vendor analogue to "derive, never overwrite": output is a new store, input untouched, the deriving transcript retained. It is still a whole-store LLM synthesis with no per-statement link from output memory to input sessions documented.
- Bi-temporal invalidation (Zep, DISCERN, SodaMem) and typed supersession (P-Mem) agree on the representation of an update: keep the old value and add validity metadata or a supersedes edge. They differ on when the conflict is settled: write time (Zep, P-Mem) or read time (DISCERN).
- Infini Memory's objection is about retrieval, not storage: an append-only store needs the current-value projection to filter superseded content before it reaches the model. P-Mem's stale-rate drop from pruning (19.6 to 5.4) is the measured version of the same point.
- Anthropic's redact rule (cannot redact the head; history entry stays with content scrubbed) is a working example of redaction that preserves an audit skeleton, the same shape as Datomic's permanent excision record.

### Gaps
- No Anthropic documentation was found stating that every model request is reconstructable from the session event log; the docs confirm only persistent, listable event history. The event-type reference was not read in full.
- No measured results exist for Letta Context Repositories, Anthropic memory versions or Dreams.
- GCC v1's self-replication case study was not present in the v2 text read, so its numbers are not reported here.
- LangGraph checkpointing and time travel, "12-factor agents", and other event-sourced agent frameworks were not researched.
- Graphiti's current (2026) invalidation behavior was taken from the January 2025 paper, not from current documentation.
- MemIR, SodaMem and "Stored Is Not Supported" were read at abstract level only; whether their stores are strictly append-only is not confirmed.
- Almost all research systems here are preprints with author-built or synthetic benchmarks; only ACE (ICLR 2026) and the OpenHands SDK (MLSys 2026) are peer-reviewed.

## 4. Evidence on rewrite-in-place failure modes, and head-to-head comparisons of append-only versus rewrite memory

### Takeaway
The measured evidence against LLM rewrite-in-place is now direct. One rewrite step collapsed an 18,282-token context to 122 tokens and pushed accuracy below the no-memory baseline (ACE, ICLR 2026), and a controlled 2026 ablation found raw trajectories at 76.6% versus 43.2% for default in-place consolidation, with append-only variants in between. The dominant measured failure in commercial memory systems is omission, not fabrication: update omission rates above 50% for most systems.

### Cited Findings
- ACE defines context collapse as what happens "when an LLM is tasked with fully rewriting the accumulated context at each adaptation step", and brevity bias as "the tendency of optimization to collapse toward short, generic prompts". — [ACE (arXiv 2510.04618v3), ICLR 2026](https://arxiv.org/html/2510.04618v3)
- The collapse example: on AppWorld with Dynamic Cheatsheet, the context at step 60 was 18,282 tokens with accuracy 66.7; one step later it was 122 tokens with accuracy 57.1, below the 63.7 baseline with no adaptation. The authors say the issue is not specific to that method. — [ACE (arXiv 2510.04618v3)](https://arxiv.org/html/2510.04618v3)
- Online on AppWorld, ACE's incremental deltas beat Dynamic Cheatsheet's rewriting by 7.6 points on average (59.5 versus 51.9). — [ACE (arXiv 2510.04618v3)](https://arxiv.org/html/2510.04618v3)
- "Useful Memories Become Faulty When Continuously Updated by LLMs" (preprint, arXiv 2605.12978, May 2026, revised August 2026) reports a head-to-head ablation with GPT-5.4 on ARC-AGI Stream at step 400: default consolidation with in-place rewrite 43.2%; append-only with the prior store visible 50.0% (+6.8); add and delete without in-place edit 64.0% (+20.8); append-only with the prior store hidden 70.0% (+26.8); raw trajectories with no consolidation 76.6%. The paper notes that "pruning (delete without rewrite) actually helps". — [Useful Memories (arXiv 2605.12978v2)](https://arxiv.org/html/2605.12978v2)
- Same paper, repeated-run check (GPT-5.4, 33 tasks, 10 runs): no memory 58.5 +/- 5.4 pass@1; consolidated memory 55.1 +/- 4.9 after epoch 1 and 38.5 +/- 5.3 after epoch 10. — [Useful Memories (arXiv 2605.12978v2)](https://arxiv.org/html/2605.12978v2)
- Same paper, other environments: on ScienceWorld the score "peaks near step 20 and declines through step 100 for every memory size and sometimes below no-memory baseline"; on WebShop with Agent Workflow Memory success fell from 0.64 to 0.20 as examples grew to 128, equal to the no-memory baseline. With an agent that controls its own memory, final accuracy fell 10 to 22 points from peak across four backbones (for example GPT-5.5: peak 80.0, step 400 68.0). — [Useful Memories (arXiv 2605.12978v2)](https://arxiv.org/html/2605.12978v2)
- The abstract says GPT-5.4 "fails on 54% of a set of ARC-AGI problems it had previously solved without memory" even when consolidating from ground-truth solutions; the body text gives about 46% for what appears to be the same result. The methods studied are CLIN, Agent Workflow Memory, Dynamic Cheatsheet and ACE. — [Useful Memories (arXiv 2605.12978v2)](https://arxiv.org/html/2605.12978v2)
- Its recommendation: "Raw episodes should be treated as first-class evidence, not disposable material to be compressed away", with abstraction selective, delayed, opt-in and "grounded in recoverable trajectories". — [Useful Memories (arXiv 2605.12978v2)](https://arxiv.org/html/2605.12978v2)
- HaluMem (preprint, arXiv 2511.03506, v3 January 2026), an operation-level benchmark of extraction, updating and QA with about 15k memory points and 3.5k questions per split: memory-update omission rates on HaluMem-Medium were Mem0 74.02%, Mem0-Graph 75.24%, Memobase 94.25%, Supermemory 82.47%, Zep 52.31%, MemOS 37.48%; update hallucination rates were all at or below 1.15%. — [HaluMem (arXiv 2511.03506v3)](https://arxiv.org/html/2511.03506v3)
- On HaluMem-Long, Mem0's extraction recall fell to 3.23% and its update accuracy to 1.45% (omission 98.51%); MemOS held 81.90% recall and 65.25% update accuracy. QA hallucination rates on Medium ranged from 15.17% (MemOS) to 29.97% (Memobase). — [HaluMem (arXiv 2511.03506v3)](https://arxiv.org/html/2511.03506v3)
- HaluMem's diagnosis: "most systems suffer omission rates above 50%", because "when the pre-update memories are not extracted, related updates cannot be properly processed"; errors made in extraction and updating propagate to QA. — [HaluMem (arXiv 2511.03506v3)](https://arxiv.org/html/2511.03506v3)
- Lossy summarization baselines on Deep Memory Retrieval: recursive summarization 35.3% and conversation summaries 78.6% versus 94.4% for the full conversation (gpt-4-turbo). — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)
- Retraction recovery (ALFWorld-Revision, P-Mem paper): commit with retained history recovers 100%; without retention 0%; raw archival 97.9% (92.0% with 32 distractors); Graphiti 0%. After conflict resolution: contest/resolve 97.9%, raw 57.1%, Graphiti 39.3%. On revision chains of length 1/2/4/8, raw top-10 retrieval fell to 100/72.9/42.9/25.0% while the committed graph stayed at 100%. Graphiti was run mainly with the same 4B extractor, which the authors flag as limiting. — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)
- Stale-answer rates on FactConsolidation: P-Mem 4.7/5.8/4.2% at 6k/64k/262k versus HippoRAG-v2 35.9/24.6/22.5% and Mem0 rising from 43.8% to 59.2%. — [Memory of Memory (arXiv 2609.25054)](https://arxiv.org/html/2609.25054v1)
- Incremental summary maintenance drifts even without overwriting sources: Zep's one-step community update diverges from a full label-propagation run and needs periodic full refresh. — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)
- Anthropic's own framing of the problem Dreams addresses: agent writes "are local and incremental: over many sessions a memory store accumulates duplicates, contradictions, and stale entries." — [Anthropic, Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)

### Inferences
- The ablation ordering in the "Useful Memories" paper (in-place 43.2 < append-only, prior visible 50.0 < add/delete 64.0 < append-only, prior hidden 70.0 < raw 76.6) separates two harms. Forbidding in-place edits recovers some accuracy; preventing the consolidator from conditioning on its own earlier abstractions recovers much more. For a design with derived summaries, this argues for regenerating a summary from source nodes, not from the previous summary.
- Pure append-only is not sufficient either. Raw retrieval over revision chains fell to 25% at chain length 8, and append-only-with-visible-prior was only +6.8. What works in these results is append-only storage plus an explicit supersession structure that determines the current value.
- HaluMem's finding that update errors are omissions (above 50%) with almost no update hallucination (at most 1.15%) suggests the binding constraint in extraction-based memories is write-time coverage. An immutable raw layer makes that recoverable, since a missed fact can be re-extracted later; a rewrite-in-place store has discarded the source.
- All head-to-head evidence comes from two preprints (arXiv 2605.12978 and 2609.25054) plus one peer-reviewed paper (ACE) whose comparison is against one rewriting method. The direction is consistent; the effect sizes are single-backbone, small-n results.

### Gaps
- No independent replication of the 2605.12978 ablation was found, and its 54% versus 46% inconsistency is unresolved.
- No peer-reviewed study isolates "summarization drift" (meaning change across repeated re-summarization) with a drift metric; the evidence here is task accuracy and token counts.
- No study compares an immutable-source, rebuildable-view architecture against rewrite-in-place at equal token and latency budgets on a standard long-horizon benchmark.
- HaluMem figures for Zep lack extraction metrics (no API to read extracted memories), so its omission rate is only partly comparable.

## 5. Provenance for generated text: keeping each sentence of a derived summary traceable to source nodes

### Takeaway
Free-form generation with citations is far from fully supported: about half of sentences in deployed systems and in the best ALCE ELI5 runs lack complete support. Selecting source spans first and generating from them gives 0% uncited sentences and citations 11 to 45 times shorter, and extract-and-point APIs guarantee pointer validity, but neither guarantees that the sentence is entailed by the span; verifiability trades off against fluency and perceived utility.

### Cited Findings
- ALCE (Gao, Yen, Yu, Chen; EMNLP 2023, peer-reviewed) defines citation recall per statement (1 if it has at least one citation and an NLI model judges the cited passages jointly entail it) and citation precision per citation (1 if the statement has recall 1 and the citation is not irrelevant), using the TRUE T5-11B NLI model, following the attributable-to-identified-sources (AIS) framework. — [ALCE (arXiv 2305.14627v2)](https://arxiv.org/html/2305.14627v2)
- ALCE results with 5 passages: ChatGPT on ASQA citation recall 73.6 and precision 72.5; on ELI5 51.1 and 50.0; on QAMPARI 20.5 and 20.9. GPT-4 on ELI5: 44.0 and 50.1. The abstract's summary: on ELI5 "even the best models lack complete citation support 50% of the time". — [ALCE (arXiv 2305.14627v2)](https://arxiv.org/html/2305.14627v2)
- Reranking four samples by automatic citation recall raises ChatGPT recall from 73.6 to 84.8 on ASQA and 51.1 to 69.3 on ELI5. Feeding summaries or snippets instead of full passages improves correctness but lowers citation quality. Closed-book generation with post-hoc citation has citation recall 47% lower than the vanilla approach on ASQA. — [ALCE (arXiv 2305.14627v2)](https://arxiv.org/html/2305.14627v2)
- The automatic metrics agree with human labels 85.1% of the time for citation recall (Cohen's kappa 0.698) and 77.6% for citation precision (kappa 0.525). — [ALCE (arXiv 2305.14627v2)](https://arxiv.org/html/2305.14627v2)
- Human audit of four generative search engines (Liu, Zhang, Liang; Findings of EMNLP 2023, peer-reviewed): "a mere 51.5% of generated sentences are fully supported by citations and only 74.5% of citations support their associated sentence"; citation quality was inversely related to fluency and perceived utility. — [Liu et al., Evaluating Verifiability in Generative Search Engines](https://aclanthology.org/2023.findings-emnlp.467) (search summary; page not opened)
- "Attribute First, then Generate" (Slobodkin et al.; ACL 2024, peer-reviewed) splits generation into content selection, sentence planning and sentence-by-sentence generation, so the selected source spans are the citations. Multi-document summarization: ALCE baseline AutoAIS 88.7, 843.6 cited tokens per sentence, 3.4% sentences uncited; Attribute-First CoT AutoAIS 72.8, 75.3 cited tokens, 1.5% uncited (0.0% for the plain ICL variant, AutoAIS 79.5). Long-form QA: ALCE AutoAIS 49.8, 2,153.3 cited tokens, 26.9% uncited; Attribute-First CoT AutoAIS 89.3, 48.2 cited tokens, 0.0% uncited. — [Attribute First, then Generate (arXiv 2403.17104)](https://ar5iv.labs.arxiv.org/html/2403.17104)
- Human evaluation in the same paper: verification time per sentence fell from 47 s to 22 s (summarization) and 59 s to 35 s (QA); human AIS was 79.9 versus 89.3 for ALCE on summarization and 94.4 versus 87.6 on QA; fluency 4.9 versus 4.7 to 4.9. — [Attribute First, then Generate (arXiv 2403.17104)](https://ar5iv.labs.arxiv.org/html/2403.17104)
- "The Extractive-Abstractive Spectrum" (Worledge, Hashimoto, Guestrin; arXiv 2411.17375, listed in TACL 2026) defines five operating points (extractive, quoted, paraphrased, entailed, abstractive). Between extractive and GPT-4 plus retrieval abstractive output, perceived utility rises by over 200% while citation coverage falls by over 50%; people take three times longer to verify abstractive cited sentences than quoted ones; Gemini outputs showed over 80% lower citation coverage than entailed generations at similar fluency. — [Extractive-Abstractive Spectrum (arXiv 2411.17375)](https://arxiv.org/abs/2411.17375) (search summary; page not opened); [TACL listing](https://aclanthology.org/2026.tacl-1.114/)
- Anthropic's Citations feature [vendor, stable]: documents are chunked into sentences (or caller-defined blocks); the API "extracts `cited_text` directly", so "citations are guaranteed to contain valid pointers to the provided documents"; `cited_text` does not count toward output tokens. Quality is claimed only qualitatively ("significantly more likely to cite the most relevant quotes" than prompt-based approaches). Citations cannot be combined with structured outputs, and the API does not guarantee that every field or claim carries a citation. — [Anthropic, Citations](https://platform.claude.com/docs/en/build-with-claude/citations)
- Agent-memory systems applying citation gating: DISCERN uses a citation-or-abstain gate at read time; SodaMem requires provenance spans on every extracted fact and gathers citable evidence before answering; MemIR restricts factual claims to supported claim atoms. — [DISCERN](https://arxiv.org/html/2611.15729); [SodaMem](https://arxiv.org/abs/2608.08055); [MemIR](https://arxiv.org/abs/2605.25869)
- Zep stores bidirectional episode-to-fact indices for citation but did not evaluate them. — [Zep (arXiv 2501.13956)](https://arxiv.org/html/2501.13956)

### Inferences
- For summaries derived from memory nodes, the evidence favors plan-then-write: choose the source nodes (or spans) for each output sentence deterministically or as an explicit recorded step, then generate each sentence conditioned only on those. This gives a structural guarantee that every sentence has a source pointer (0% uncited) and makes citations small enough to check (tens of tokens). It does not guarantee entailment: AutoAIS was 72.8 to 89.3, so a separate entailment check, or quoting, is still needed for strict traceability.
- Pure extractive composition (the summary is a deterministic selection and ordering of source node text) is the only point on the spectrum where traceability holds by construction. The cost, per the spectrum paper, is perceived utility. Compact, self-contained nodes reduce that cost, since quoted nodes then read well without rewriting.
- ALCE's finding that feeding summaries in place of passages lowers citation quality is a caution for layered derivation: citing a summary node as the source of another summary weakens support. Derived text should cite leaf evidence, with intermediate summaries recorded as `wasDerivedFrom` steps and not as sources of authority.
- Valid-pointer guarantees (Citations API) and NLI-based metrics (ALCE) measure different things: pointer validity versus support. A provenance-carrying memory needs both, plus a rule for what happens to a derived sentence when one of its cited nodes is later retracted (section 2, support counting).
- The automatic metric ceiling is modest (77.6 to 85.1% agreement with humans), so attribution scores in an evaluation should be reported with that error in mind.

### Gaps
- No study was found that measures attribution precision and recall for summaries generated from an agent's own memory store (as opposed to retrieved web or Wikipedia passages).
- No measured faithfulness figures were found for Anthropic's Citations feature; the vendor claim is qualitative.
