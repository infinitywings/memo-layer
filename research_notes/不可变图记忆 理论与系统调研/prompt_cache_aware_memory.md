# Prompt caching (KV-cache reuse) for LLM agents, and how memory and context design affect cache hit rates and cost

Research date: 2026-11-13. Every provider fact below was read on that date at the linked URL unless another date is given. Provider pages were read through a fetch tool that summarizes pages, so field names and numbers are reported as the tool returned them; wording is paraphrased, identifiers are in code font. Source labels: [vendor doc], [vendor blog], [peer-reviewed], [preprint], [issue/forum].

Hypothesis under test: memory made of immutable nodes, rendered in a stable, append-mostly order, yields a higher prompt-cache hit rate and lower input cost than memory rewritten in place; the effect size depends on where memory sits in the prompt, how large it is, and how often it changes.

## 1. Provider semantics (2025-2026): what exactly is cached, for how long, at what price

### Takeaway
Every hosted provider and every open-source server caches on an exact token-prefix match, so one changed token invalidates everything after it; what differs is the lifetime (5 minutes to days), whether writes carry a premium (Anthropic 1.25x/2x, OpenAI GPT-5.6+ 1.25x/2.5x, others none), and how deep the read discount is (0.1x down to 0.025x of base input). No provider offers non-prefix ("segment") reuse in its public API; that exists only in research systems.

### Cited Findings

**Anthropic (Claude API) [vendor doc]**
- The only cache type is `ephemeral`; an explicit breakpoint is `"cache_control": {"type": "ephemeral"}` on a content block, with a default 5-minute lifetime, and `"ttl": "1h"` selects the 1-hour cache — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Automatic caching exists: a single top-level `cache_control` field in the request body. It uses one of the 4 available breakpoint slots and is rejected with a 400 on Amazon Bedrock `bedrock-runtime`. In the documented multi-turn pattern the final block of the final message carries the marker each turn, and the system finds and uses the longest previously cached sequence of blocks — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Up to 4 cache breakpoints per request; the prefix is built in the order `tools`, then `system`, then `messages` — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Lookback: for each breakpoint the system checks at most 20 positions (the breakpoint itself is the first). A growing conversation that pushes the breakpoint 20 or more blocks past the last cache write falls outside the window, which is the documented reason to use more than one breakpoint — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Minimum cacheable prefix by model: 512 tokens (Fable 5.2, Mythos 5.2, Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5, Mythos 5, Haiku 5.5); 1,024 (Opus 4.8, Sonnet 5, Sonnet 4.6, Sonnet 4.5, Opus 4.1, Opus 4, Sonnet 4); 2,048 (Mythos Preview, Opus 4.7); 4,096 (Opus 4.6, Opus 4.5, Haiku 4.5). Shorter prefixes are processed without caching and without an error — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Pricing multipliers on base input price: 5-minute write 1.25x; 1-hour write 2x; read 0.1x by default, 0.05x on Opus 5.5 and Sonnet 5.5, 0.025x on Fable 5.2, Mythos 5.2, Fable 5.1, Mythos 5.1. Example given for Opus 5.5 at $4/MTok base: $5 (5m write), $8 (1h write), $0.20 (read) — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Usage fields: `cache_creation_input_tokens`, `cache_read_input_tokens`, `input_tokens` (tokens after the last breakpoint), and the TTL breakdown `cache_creation.ephemeral_5m_input_tokens` / `cache_creation.ephemeral_1h_input_tokens`. Total input = `cache_read_input_tokens` + `cache_creation_input_tokens` + `input_tokens` — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- A cache read refreshes the entry's lifetime at no extra cost; there is no manual clear; entries expire after a minimum of 5 minutes (or 1 hour) of inactivity — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Invalidation table: changing tool definitions invalidates tools, system and messages caches; toggling web search, citations or `speed: "fast"` keeps the tools cache but invalidates system and messages; changing `tool_choice` or adding/removing images invalidates only the messages cache; thinking parameters and effort are model-specific — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Cache keys are a cryptographic hash of the prompt up to the breakpoint, so only identical prompts hit. A breakpoint placed on a block that changes each request (timestamp, arbitrary user input) writes a new entry every time and never reads — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Isolation: never shared across organizations; isolated per workspace on the Claude API, Claude Platform on AWS and Microsoft Foundry; per organization on Bedrock and Google Cloud. KV representations are held in memory only — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Cache hits are not deducted against the rate limit (given as a reason to use the 1-hour cache) — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Server-side context editing interacts with the cache: clearing tool results invalidates the cached prefix from the cleared point, so the docs provide `clear_at_least` (a minimum number of tokens to clear, else the strategy is skipped) to make the invalidation worth its cache-write cost; clearing thinking blocks also invalidates from the clearing point, while `"keep": "all"` preserves hits — [Anthropic context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)

**OpenAI [vendor doc]**
- Caching is on by default for supported models, stores KV tensors rather than tokens, and requires the entire rendered prefix to match — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Minimum cacheable prefix is 1,024 tokens on GPT-5.6 and later; on earlier models the minimum varies with request settings and cached tokens are reported rounded down to a multiple of 128 — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Usage field in the Responses API: `usage.input_tokens_details.cached_tokens` — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching). Chat Completions reports `cached_tokens` under `prompt_tokens_details` (third-party documentation, not confirmed on the OpenAI page read) — [LiteLLM docs](https://docs.litellm.ai/docs/completion/prompt_caching.md); Azure describes hits after the first 1,024 tokens in 128-token steps — [Azure OpenAI prompt caching](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/prompt-caching)
- Routing: cached state lives on individual machines; above about 15 requests per minute for a prefix-and-key combination traffic can overflow to other machines. `prompt_cache_key` influences routing but neither pins a machine nor guarantees a hit; on GPT-5.6 and later routing is automatic and the key is optional — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Retention on earlier models: `prompt_cache_retention` takes `"in_memory"` (typically 5 to 10 minutes of inactivity, at most 1 hour) or `"24h"` (up to 24 hours). Extended retention is listed for gpt-5.5, gpt-5.5-pro, gpt-5.4, gpt-5.2, the gpt-5.1 family, gpt-5, gpt-5-codex and gpt-4.1. Organizations without Zero Data Retention default to `24h` — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Retention on GPT-5.6 and later: `prompt_cache_options.ttl` with `"30m"` (default) or `"12h"`; writes cost 1.25x (30-minute) or 2.5x (12-hour) of uncached input; reads cost 0.1x (0.05x for GPT-6.1 Sol and Terra). The guide states a cached-input discount of up to 95% — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Cached input tokens still count toward tokens-per-minute limits; entries cannot be cleared manually — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Layout guidance: stable developer instructions and shared reference material first; timestamps and user-specific data at the end or in later messages; keep tool definitions, their order and schemas unchanged; append new messages instead of rewriting earlier turns — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)

**DeepSeek [vendor doc]**
- Context caching (a disk cache) is enabled by default for all users with no code change — [DeepSeek context caching guide](https://api-docs.deepseek.com/guides/kv_cache)
- Prefix units: each request creates cache prefix units at the end of the user input and at the end of the model output; a prefix shared by several requests is persisted as its own unit; long inputs or outputs get units at fixed token intervals; a later request hits only if it fully matches a unit — [DeepSeek context caching guide](https://api-docs.deepseek.com/guides/kv_cache)
- Usage fields: `prompt_cache_hit_tokens` and `prompt_cache_miss_tokens` — [DeepSeek context caching guide](https://api-docs.deepseek.com/guides/kv_cache)
- Best-effort, no guaranteed hit rate; unused entries are cleared automatically, usually within a few hours to a few days; construction takes seconds — [DeepSeek context caching guide](https://api-docs.deepseek.com/guides/kv_cache)
- Launch note dated 2024-08-02: 64 tokens is the storage unit and content under 64 tokens is not cached; only prefixes identical from token 0 count, mid-input partial matches do not; launch prices were $0.014/MTok for hits against $0.14/MTok for misses; a 128K-token highly repeated prompt went from 13 s to 500 ms first-token latency — [DeepSeek news 2024-08-02](https://api-docs.deepseek.com/news/news0802)
- Pricing page as read 2026-11-13 (USD per 1M tokens, off-peak/peak): `deepseek-flash` hit $0.003/$0.006, miss $0.15/$0.30, output $0.60/$1.20; `deepseek-v4-pro` hit $0.022/$0.044, miss $0.66/$1.32, output $1.98/$3.96. That is a 50x hit/miss ratio on flash and 30x on v4-pro, with no separate write price — [DeepSeek models and pricing](https://api-docs.deepseek.com/quick_start/pricing)

**Google Gemini [vendor doc]**
- Implicit caching is on by default for Gemini 2.5 and newer, with savings passed on automatically when a request hits. Minimum input: 4,096 tokens (Gemini 4 Carbon/Argon/Hydrogen, 3.8 Flash, 3.6 Flash, 3.1 Pro Preview), 2,048 tokens (2.5 Flash, 2.5 Pro) — [Gemini API caching docs](https://ai.google.dev/gemini-api/docs/caching)
- Guidance: put large, common content at the start of the prompt and send similar-prefix requests close together in time — [Gemini API caching docs](https://ai.google.dev/gemini-api/docs/caching)
- Gemini 4 agent-loop rule: the full previous request is cached only when the new request adds at least 2,050 tokens (model output, thoughts and function results count); smaller additions re-process the last 2,050 tokens at the standard rate — [Gemini API caching docs](https://ai.google.dev/gemini-api/docs/caching)
- The Gemini API page reports hits in `usage.total_cached_tokens` (Interactions API SDKs); it states that explicit caching is not supported by the Interactions API or by Gemini 4 models and needs `generateContent` on Gemini 3 and 2.5 models — [Gemini API caching docs](https://ai.google.dev/gemini-api/docs/caching)
- Vertex AI: implicit caching is on by default for all projects; cached tokens get a 90% discount (explicit: 90% on Gemini 2.5 or later, 75% on Gemini 2.0); an implicit prefix expires no later than 24 hours after creation and usually sooner; the response metadata field is `cachedContentTokenCount`; explicit caches default to a 60-minute TTL, are billed for storage time, and are created at the standard input price (except where Gemini 4 cache-write pricing applies) — [Vertex AI context cache overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)

**Open-source servers**
- vLLM automatic prefix caching: each KV block is hashed from its parent block's hash, the block's own tokens and extra hashes (LoRA IDs, multimodal input hashes, cache salts); only full blocks are cached; eviction is LRU over a free-block queue with reference counts; default hash is `sha256` since v0.11; a per-request `cache_salt` is injected into the first block's hash to restrict reuse to same-salt requests (timing-attack mitigation) [project doc] — [vLLM prefix caching design](https://docs.vllm.ai/en/latest/design/v1/prefix_caching/)
- llama.cpp server: `cache_prompt` (default `true`) reuses the KV cache of the previous request so only the differing suffix is evaluated, with a warning that results can be nondeterministic; `--cache-reuse N` / `n_cache_reuse` (default 0, disabled) attempts chunk reuse through KV shifting; `--slot-save-path` plus `POST /slots/{id_slot}?action=save|restore|erase` persists a slot's cache to disk; `--slot-prompt-similarity` (default 0.10) picks the slot; `--cache-ram` (default 8192 MiB) bounds the host prompt cache; `timings.cache_n` and `tokens_cached` report reused tokens [project doc] — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- SGLang: RadixAttention is described in the abstract as a runtime optimization for KV-cache reuse, with up to 6.4x higher throughput than prior inference systems across agent control, RAG and multi-turn chat workloads [preprint, arXiv 2312.07104, v2 June 2024; venue not confirmed on the page read] — [SGLang paper](https://arxiv.org/abs/2312.07104)
- Manus advises that self-hosted vLLM deployments enable prefix caching and route a session's requests to the same worker, for example by session ID [vendor blog] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

### Inferences
- All five hosted providers share one rule that matters for memory design: reuse is keyed on the exact prefix from token 0. A memory block that is byte-identical but preceded by any changed token gets no hit. None of the public APIs can reuse an unchanged memory segment that moved or that follows a changed segment.
- Lifetime bounds cross-session reuse. With Anthropic's defaults a prefix survives 5 minutes or 1 hour of inactivity; OpenAI 5-10 minutes up to 24 hours (older models) or 30 minutes/12 hours (GPT-5.6+); Gemini implicit at most 24 hours; DeepSeek hours to days. A memory prefix that is stable across sessions only pays off across sessions when the next session arrives inside that window, or when many sessions run concurrently on the same prefix.
- Where writes carry a premium (Anthropic, OpenAI GPT-5.6+), an invalidation costs more than an uncached request: each invalidated token is billed at 1.25x instead of 0.1x or lower. On DeepSeek and older OpenAI models an invalidation costs the plain miss price.
- As read discounts deepen (0.05x, 0.025x), the relative penalty of breaking the prefix grows: on a 0.025x-read model one re-write of a prefix at 1.25x costs the same as 50 cached reads of it.
- Anthropic's 20-position lookback means a memory rendered as many small content blocks can fall out of reach of a later breakpoint; rendering the stable memory core as one block (or ending it with its own breakpoint) avoids this.
- Gemini 4's 2,050-token increment rule and DeepSeek's prefix units mean small appended deltas are not always cached immediately; the accounting granularity differs by provider and should be measured, not assumed.

## 2. Measured effects in agent workloads, and research systems for cache reuse

### Takeaway
Production traces show agent loops reach 90-98% token-weighted cache hit rates inside a turn, and that the misses come from three structural events: idle gaps longer than the cache lifetime, model switches, and context rewriting (compaction). Compaction in the GitHub Copilot trace costs a median 66.1% drop in hit rate, on a par with a model switch. Engineering reports from Manus, Anthropic's Claude Code team and OpenAI converge on the same rules: stable prefix, append-only context, deliver updates as new messages.

### Cited Findings

**Engineering reports**
- Manus (Yichao "Peak" Ji, 2025-07-18) calls KV-cache hit rate "the single most important metric" for a production agent; reports an average input-to-output token ratio near 100:1; cites Claude Sonnet cached input at $0.30/MTok against $3/MTok uncached [vendor blog] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Manus rules: keep the prompt prefix stable (a second-precision timestamp at the top of the system prompt is the named mistake); make context append-only and never modify earlier actions or observations; make serialization deterministic because JSON key order can vary; set breakpoints explicitly where the provider needs them, at least at the end of the system prompt [vendor blog] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Manus "mask, don't remove": tool definitions sit near the front of the context, so adding or removing a tool mid-task invalidates the cache for all later actions and observations; Manus keeps the tool list fixed and constrains choice by masking token logits during decoding, helped by shared tool-name prefixes such as `browser_` [vendor blog] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Claude Code team (Thariq Shihipar, 2026-04-30): the harness is built around prefix caching; layout is static system prompt and tools, then CLAUDE.md and memory (cached per project), then session context, then conversation messages; the team alerts on cache hit rate and declares incidents when it drops; past cache breaks came from a detailed timestamp in the static prompt, non-deterministic tool ordering, and changed tool parameters [vendor blog] — [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Claude Code updates state through messages: a `<system-reminder>` in the next user message or tool result instead of editing the system prompt. Plan mode keeps all tools and is entered and left through tools; unused MCP tools are sent as stubs with `defer_loading: true` instead of being removed. Switching to a cheaper model 100K tokens into a session is described as costing more than staying, because the new model has no cache [vendor blog] — [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Cache-safe compaction in Claude Code: the summarization call reuses the parent's exact system prompt, context and tool definitions, prepends the parent's messages, and appends the compaction instruction as a final user message, so the call reads the parent's cache; a separate call with a different system prompt would diverge at the first token [vendor blog] — [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Claude Code documentation lists what invalidates the cache (model switch, effort change on most models, fast-mode toggle, adding or removing loaded tool definitions, compaction, removal of old images, version upgrade) and what keeps it (file edits, CLAUDE.md edits, permission-mode and output-style changes, skills, `/rewind`, subagent spawn). `/rewind` truncates back to a prefix that is already cached; compaction builds a new one [vendor doc] — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Claude Code TTL policy: the main conversation gets the 1-hour TTL only on a subscription within plan usage; API-key, usage-credit and cloud-provider sessions default to 5 minutes; subagents default to 5 minutes; overridable with `promptCacheTtl` / `subagentPromptCacheTtl` [vendor doc] — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- OpenAI's Codex agent-loop post could not be retrieved (HTTP 403). Secondary commentary says Codex keeps each new prompt an exact extension of the previous one and appends configuration changes as new messages; treat as unverified [secondary blog] — [Codex CLI prompt caching commentary](https://codex.danielvaughan.com/2026/04/21/codex-cli-prompt-caching-maximise-cache-hits-cost-reduction/)

**Controlled evaluation**
- "Don't Break the Cache" (Lumer et al., PwC; arXiv 2601.06007, v2 2026-01-31) [preprint]: DeepResearch Bench tasks, a 10,000-token system prompt, 40 sessions per condition per model, over 500 sessions, t-tests at alpha 0.05. Cost reduction against no caching: GPT-5.2 79.3-81.4%, Claude Sonnet 4.5 77.8-78.5%, Gemini 2.5 Pro 27.8-41.4%, GPT-4o 45.9-47.8% — [Lumer et al. 2026](https://arxiv.org/abs/2601.06007)
- Same paper, time to first token: system-prompt-only caching improved TTFT by 10.5% (GPT-5.2), 22.9% (Claude Sonnet 4.5), 6.1% (Gemini 2.5 Pro), 30.9% (GPT-4o); full-context caching made GPT-4o TTFT 8.8% worse and excluding tool results made Gemini 2.9% worse — [Lumer et al. 2026](https://arxiv.org/abs/2601.06007)
- Same paper, ablations: with a 50,000-token prompt savings reached 89% (GPT-5.2), 88% (Claude Sonnet 4.5), 54% (GPT-4o); a 500-token prompt (below the minimum) produced TTFT regressions of 10-18% on three models; Claude's TTFT gain fell from 19% with 3 tools to 5% with 50 tools — [Lumer et al. 2026](https://arxiv.org/abs/2601.06007)
- Same paper, recommendations: keep timestamps, session IDs and user-specific values out of the system prompt or at its very end; keep the tool set fixed; pruning or summarizing old tool calls breaks the cached prefix; caching dynamic tool results can add write cost with no later read — [Lumer et al. 2026](https://arxiv.org/abs/2601.06007)

**Production traces**
- GitHub Copilot trace study (Liu, Qiu, Goiri, Fonseca, Bianchini, Choukse; UIUC and Microsoft Azure Research; June 2026 sampled traces: 3.2M users, 13M sessions, 761M LLM calls, 95T tokens) [technical report/preprint; venue not confirmed]: median prompt 68K tokens of which a median 63K are cached, against 247 output tokens; hit rate about 98% at the median but bimodal, with about 10% of calls below 20% — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf)
- Same study, within a turn: about 45% on the first call, about 86% on the second, 92-94% from the third call on — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf)
- Same study, turn boundaries: same-model boundaries lower the hit rate by 26 points on average. By idle gap: medians at or above 95% under 2 minutes, about 70% for 2-10 minutes with a tail to 0%, and 0-5% beyond 10 minutes — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf)
- Same study, model switches: about 6.4% of sessions; average hit rate after a switch is 8% (a 67-point drop) — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf)
- Same study, compaction: 7.8% of sessions (22.6% of sessions with prompts over 100K tokens), which account for 44.2% of total tokens; the median event removes 72.8% of prompt tokens; the first call afterwards shows a median 66.1% hit-rate drop; 34.3% of events erase 90% or more of the hit rate and 21% erase 99% or more. The authors recommend incremental, prefix-preserving compaction — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf)
- TraceLab (Zhu et al., University of Washington; arXiv 2606.30560, 2026-06-30) [preprint]: about 4,265 sessions from 43 developers (2,676 Claude Code, 1,589 Codex), about 357K LLM steps. Token-weighted prefix cache hit rate 95.7% overall (Claude 95.8%, Codex 95.7%); 84.4% on user-initiated steps against 97.5% on tool-result steps — [TraceLab](https://arxiv.org/abs/2606.30560)
- TraceLab, lifetime sweep (idealized): achievable hit rate 85.4% with a 1-minute eviction timeout, about 94% at 5 minutes, 98.6% at 1 hour; low-hit steps appear once the gap passes 5 minutes and nearly all steps miss after 1 hour — [TraceLab](https://arxiv.org/abs/2606.30560)
- TraceLab, shape and cost: median per-step prefix about 126K tokens (Claude) and 116K (Codex) with under 900 appended tokens and 184-252 output tokens; cache-read tokens are 59.5% of session spend, appended (fresh and cache-write) tokens 29.2%, output 11.2%; mean session cost $9.70, median $0.61 — [TraceLab](https://arxiv.org/abs/2606.30560)
- TraceLab, context reductions: context grows in 99.6% of Claude steps and 96.6% of Codex steps; 9.7% of sessions have at least one compaction (Claude 4.5%, Codex 18.4%); an upper-bound estimate is that keeping caches alive across human thinking gaps would cut cost by 12.8% ($5,189 of $40,431) — [TraceLab](https://arxiv.org/abs/2606.30560)
- Requesty (gateway vendor, April 2026 data) reports cached-token shares of 92% for Claude Code and 89% for OpenCode; method and sample size were not visible in the snippet [vendor data, unverified] — [Requesty](https://www.requesty.ai/data/coding-agent-cache-hit-rate-apr-2026)

**Research systems that relax the prefix constraint**
- Prompt Cache (Gim et al., MLSys 2024) [peer-reviewed]: precomputes attention states for reusable prompt modules defined by a schema; the abstract reports TTFT improvements of 8x on GPU and up to 60x on CPU without changing model parameters (the arXiv v2 body gives 1.5-10x GPU and 20-70x CPU) — [Prompt Cache](https://arxiv.org/abs/2311.04934)
- CacheBlend (Yao et al., EuroSys 2025) [peer-reviewed]: fuses precomputed KV caches of chunks that are not at the prefix by recomputing a small fraction of tokens; TTFT 2.2-3.3x lower and throughput 2.8-5x higher than prefix caching, with F1 0.1-0.2 higher than full KV reuse — [CacheBlend](https://arxiv.org/abs/2405.16444)
- CacheGen (Liu et al., SIGCOMM 2024) [peer-reviewed]: compresses KV caches into bitstreams for storage and transfer; KV size 3.5-4.3x smaller and context fetch-and-process delay 3.2-3.7x lower than prior KV-reuse systems — [CacheGen](https://arxiv.org/abs/2310.07240)
- AgentKVShift (Pandey et al., arXiv 2607.21604, 2026-05-15) [preprint]: targets retrieved agent-memory units that are re-encoded on every retrieval; a probe-estimated per-memory offset correction reaches near full-recompute quality while refreshing 10-30% of the cache (prior reuse methods need 45-55%), giving 2-3.5x prefill speedup on one A100 across four open models of 3B-32B parameters — [AgentKVShift](https://arxiv.org/abs/2607.21604)
- Related 2026 preprints seen only as titles or abstracts: a persistent 4-bit-quantized per-agent KV cache saved to disk — [arXiv 2603.04428](https://arxiv.org/abs/2603.04428); MemDecay, region-aware KV eviction with pinned regions — [arXiv 2607.10582](https://arxiv.org/abs/2607.10582)

### Inferences
- The three largest measured sources of misses (idle beyond lifetime, model switch, context rewrite) are all independent of how carefully the prefix is laid out. Layout discipline gets a harness to the 92-98% plateau; lifetime and rewriting decide what happens after that.
- Compaction is the closest measured analogue to "memory rewritten in place": it replaces earlier context with a summary. The Copilot numbers (median 66.1% hit-rate drop, 21% of events losing essentially everything) are the best available estimate of what an in-context rewrite does to the following request. They are not a measurement of memory rewriting itself.
- Non-prefix reuse (Prompt Cache, CacheBlend, AgentKVShift) would make order-independent memory cacheable, but it requires control of the inference server and open weights; it does not help a designer who calls hosted APIs. For a self-hosted deployment it weakens the hypothesis, because stable order stops being a precondition for reuse.
- Lumer et al.'s finding that full-context caching can hurt latency shows that "more cached" is not the objective; the boundary should sit after the last block that will actually be re-read.

### Gaps
- No Cursor engineering note on cache-aware layout was found.
- OpenAI's Codex agent-loop post was not retrievable, so its statements are known only through secondary summaries.
- The Copilot study's publication venue and the exact definition of its per-call hit rate (it appears to be cached prompt tokens over prompt tokens) were not confirmed; its "drop" figures mix percentage points and relative terms in the text.
- Neither trace study isolates memory injection, tool-definition changes or timestamps as separate causes of misses.

## 3. Memory-specific evidence

### Takeaway
There is direct but thin evidence, almost all from vendors and bug reports, that memory injected ahead of the conversation and changed every turn destroys the cache (about 1% hit rate on 64K-token prompts in one report; 1.3-1.9x session cost in one vendor experiment), and that the working fixes are the ones the hypothesis predicts: freeze memory per session, or move volatile memory behind the cached prefix. I found no peer-reviewed study that measures cache invalidation caused by memory updates, and none that compares append-only memory with rewritten memory.

### Cited Findings
- Zep experiment (Jack Ryan, 2026-06-24) [vendor blog]: Claude Opus 4.8, a static prompt of about 12K tokens, a per-turn retrieved context block, the same scripted conversation replayed with the block in the system prompt and then as a trailing message after the breakpoint. The trailing placement was 1.3x cheaper at 18 turns, 1.6x at 36 and 1.9x at 54. One prompt size, one script; cached-token shares and absolute costs were not reported — [Zep blog](https://www.getzep.com/blog/where-you-put-memory-in-the-prompt-can-cut-your-token-bill-up-to-2x/)
- Zep's procedure each turn: drop the previous context block, add the prior reply and the new user message to history, move the breakpoint, attach a fresh block at the tail (a mid-conversation system message on Opus 4.8, a synthetic tool-role message elsewhere) [vendor blog] — [Zep blog](https://www.getzep.com/blog/where-you-put-memory-in-the-prompt-can-cut-your-token-bill-up-to-2x/)
- hermes-agent issue 25971 (opened 2026-05-14) [issue]: a Mem0 plugin ran retrieval every turn and injected the result into the system prompt before the `cache_control` breakpoint; the reporter measured a prefix cache hit rate of about 1% on 64K-token prompts and estimated 5-10x the cost of cached turns. The maintainer's fix (release v2026.5.28) appends memory recall to the current user message so the system-prompt prefix stays stable — [hermes-agent issue 25971](https://github.com/NousResearch/hermes-agent/issues/25971)
- Letta forum (2025-12-23) [forum; the replier's affiliation is not stated]: a memory-block edit invalidates the cache for that turn and hits resume on the next turn without edits; suggested mitigations are sleep-time agents that update memory while the conversation is idle, batching writes, and archival memory, which is out of context and so does not touch the cache — [Letta forum](https://forum.letta.com/t/breaking-prompt-caching/149)
- Claude Code freezes memory per session: project and user CLAUDE.md files and auto memory are read once at session start into the project-context layer; a mid-session edit neither invalidates the cache nor takes effect until `/clear`, `/compact` or restart. Nested CLAUDE.md files and path-scoped rules load on demand as conversation content [vendor doc] — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Claude Code's cache scope is narrowed by memory: the system prompt embeds auto-memory paths, so sessions in different directories build different prefixes; the Agent SDK documentation offers a way to move the auto-memory location out of the system prompt for fleets [vendor doc] — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Claude Code's layer order puts memory after the system prompt and tools and before the conversation, cached per project [vendor blog] — [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Anthropic's API pairs a memory tool (`memory_20250818`) with context editing (`clear_tool_uses_20250919`): the model is warned before clearing so it can save to memory files first; memory operations are tool calls [vendor doc] — [Anthropic context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Manus treats the file system as external memory read and written on demand, and keeps compression restorable (drop a page's content, keep its URL) [vendor blog] — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Two further bug reports surfaced in search and were not opened: an OpenCode memory plugin whose system-prompt injection broke the Anthropic cache every turn — [opencode-agent-memory issue 8](https://github.com/joshuadavidthomas/opencode-agent-memory/issues/8); a MEMORY.md injected without a size limit where every write invalidated the cached system prompt — [picoclaw issue 439](https://github.com/afjcjsbx/picoclaw/issues/439)
- AgentKVShift is the one research system aimed at agent-memory units specifically, and it works by correcting reused KV states, not by ordering the prompt [preprint] — [AgentKVShift](https://arxiv.org/abs/2607.21604)

### Inferences
- The practitioner evidence separates three memory placements with very different cache behaviour: (a) before the conversation and changing per turn: near-zero hits on everything after it; (b) before the conversation and frozen for the session: full hits, at the price of stale memory within the session; (c) after the conversation prefix, as a trailing message or tool result: the prefix stays cached and only the memory block itself is paid at the uncached rate each turn.
- The hypothesis needs one refinement that this evidence makes clear. Appending a node to a memory block that sits before the conversation still invalidates the conversation behind it, exactly as a rewrite would. Within a session, append-only order beats rewriting only if new nodes are delivered at the tail of the conversation (as appended messages) or if memory is the last stable layer and updates are deferred to a session boundary. The stable-order advantage of immutable nodes shows up in two other places: across sessions (session N+1's memory prefix extends session N's, so the old nodes are a hit if the cache is still alive) and across concurrent sessions that share the memory prefix.
- Letta's sleep-time argument is the strongest counter-case: a rewrite performed while the session is idle past the cache lifetime costs nothing in cache terms, because the prefix would have been re-written anyway. Rewritten memory loses only when the rewrite lands inside a live cache window or changes bytes that concurrent sessions would otherwise share.
- A layered design follows from the sources: a frozen, append-only core rendered once per session in the prefix (Claude Code's model), plus a volatile delta delivered as trailing messages (Zep's and hermes-agent's model), with consolidation deferred to boundaries (Letta's model).

### Gaps
- No peer-reviewed or preprint study measures cache invalidation caused by memory updates, or compares append-only with rewritten memory, or oldest-first with relevance-first ordering, on cost and hit rate. The Zep experiment is the only controlled measurement found and it varies placement, not mutability or order.
- No source reports the answer-quality effect of serving frozen (session-start) memory or of placing memory at the tail instead of the system prompt.
- Whether Anthropic's memory-tool reads return as tool results that context editing may later clear was not stated on the page read.

## 4. Design rules and their trade-offs

### Takeaway
The rules are consistent across sources: keep everything ahead of the volatile part byte-identical, serialize deterministically, append instead of edit, put volatile content last, and batch any unavoidable rewrite so that it happens at a boundary where the cache is already cold or where the tokens removed justify the re-write. Each rule trades freshness or context size for cache continuity.

### Cited Findings
- Byte-identical prefix: a single differing token invalidates from that point on (Manus); only identical prompts map to the same cache key (Anthropic); the whole rendered prefix must match (OpenAI) — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- Deterministic serialization: unstable JSON key order silently breaks the cache (Manus); non-deterministic tool ordering broke Claude Code's cache in the past — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Order by change frequency: content that changes least goes first (system prompt and tools, then project context and memory, then conversation) — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Volatile content goes at the end or in later messages: timestamps, session IDs and user-specific values (OpenAI; Lumer et al.); state changes as appended reminders (Claude Code) — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching); [Lumer et al. 2026](https://arxiv.org/abs/2601.06007); [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Editing or removing something in the middle re-processes everything after it: removing old images re-processes the conversation from the earliest affected message, which is why Claude Code removes them in batches so there is one slow turn per batch — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- A rewrite must be worth its cost: `clear_at_least` skips a clearing pass that would free too few tokens to justify breaking the cache — [Anthropic context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Truncation is cache-safe where rewriting is not: rewinding to an earlier turn lands on a prefix that is already cached, while compaction creates a new prefix — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Disable instead of delete: keep tool definitions and mask them (Manus); keep stubs and defer loading (Claude Code) — [Manus blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Derived calls should share the parent's prefix: compaction, summarization and forks reuse the parent's system prompt, tools and messages and append their own instruction — [Claude Code blog](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- Breakpoint placement: one breakpoint on the last block that stays identical is usually enough; separate breakpoints are for sections that change at different frequencies (the docs' example is rarely-changing instructions plus daily-changing RAG context) or for conversations that outgrow the 20-position lookback — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Lifetime limits reuse: Claude Code describes its cache as effectively scoped to one machine and directory, with sequential sessions sharing a prefix only when the startup git snapshot matches, and with entries expiring after 5 minutes or 1 hour of inactivity — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Longer lifetimes cost more: the 1-hour write is 2x base against 1.25x for 5 minutes (Anthropic); 12-hour writes are 2.5x against 1.25x for 30 minutes (OpenAI GPT-5.6+); TraceLab estimates that moving eviction from 5 minutes to 1 hour adds about 4 points of hit rate for about 2.7x the KV storage — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching); [TraceLab](https://arxiv.org/abs/2606.30560)
- Keep-alive: a cheap request just before the lifetime ends refreshes the entry and avoids a full recompute (Copilot study, citing Claude's 300-second default; TraceLab recommends periodic refresh during long human gaps) — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf); [TraceLab](https://arxiv.org/abs/2606.30560)
- Security side effect: prefix caching opens timing side channels; vLLM's `cache_salt` and provider workspace or organization isolation are the mitigations, and both reduce sharing — [vLLM prefix caching design](https://docs.vllm.ai/en/latest/design/v1/prefix_caching/); [Lumer et al. 2026](https://arxiv.org/abs/2601.06007)

### Inferences
These are derived from the cited prices and rules; none is a measured result.
- Cost of one invalidation. Let p be the base input price, w the write multiplier, r the read multiplier, D the number of tokens after the first changed byte. One invalidation adds D x (w - r) x p to that request. With Anthropic's 5-minute cache and 0.1x reads this is 1.15 x p per downstream token: for D = 100K tokens at $5/MTok, $0.575 instead of $0.05.
- Break-even for a consolidating rewrite inside a live cache window. If the rewrite shrinks memory by S tokens and forces D tokens to be re-written, it pays back after D x (w - r) / (S x r) further cached turns. With w = 1.25 and r = 0.1 that is 11.5 x D / S turns: removing 5K tokens ahead of a 100K-token conversation needs about 230 more turns to break even. With r = 0.025 it is 49 x D / S. Mid-session consolidation is therefore almost never worth it on cost alone; at a boundary where the cache is already cold, D's write cost is sunk and the rewrite is free.
- Ordering policy. Oldest-first append is the only order under which adding a node leaves all earlier memory bytes in place. Relevance-first or recency-first ordering re-sorts on every retrieval, so the first changed position is near the top of the block and nearly the whole block (and everything behind it) is re-written. If relevance ordering is wanted, it belongs in the volatile tail, not in the cached core.
- Supersession without deletion. Removing or editing a superseded node in the middle invalidates every later node and everything behind the block. With immutable nodes, the cache-preserving alternative is to append a node that marks the earlier one superseded and to leave the old bytes in place until the next re-base. The cost is context spent on stale nodes and a risk that the model uses them; this is the same trade Manus and Claude Code accept for tools.
- Re-base policy. Stale nodes accumulate, so an append-only block needs a periodic re-render (dropping superseded nodes). By the break-even above, re-base when the cache is cold (session start after a gap longer than the lifetime) or when the tokens removed are a large fraction of the tokens that must be re-written.
- Three factors set the effect size, as the hypothesis states. Position: the cost of a change scales with the tokens behind it, so the same edit is cheap at the tail and expensive at the head. Size: memory below the provider minimum (512-4,096 tokens) cannot be cached on its own and matters only as part of a longer prefix; large memory raises both the saving from stability and the price of a rewrite. Change frequency relative to lifetime and request rate: a rewrite between sessions that are further apart than the cache lifetime costs nothing; a rewrite every turn costs the full downstream context every turn.
- A stable memory prefix also widens sharing: concurrent sessions and subagents with an identical tools-system-memory prefix read one another's cache, while per-user or per-directory strings ahead of the memory (paths, IDs) split it.

### Gaps
- No source quantifies the quality cost of leaving superseded nodes in context, of oldest-first versus relevance-first ordering (position effects), or of session-frozen memory.
- No source gives a measured break-even for consolidation; the formula above is my derivation from list prices and ignores output tokens, latency and rate-limit effects.

## 5. How to measure it, and what a fair comparison must control

### Takeaway
Use the token-weighted cached share of input from provider usage fields, input cost per session at list prices, and time to first token, and report them by step type and idle gap. A fair test of stable-order against rewritten memory must hold token count, update schedule, timing and prompt position equal, isolate caches between arms, and report task quality alongside cost, because consolidation changes the size and content of memory as well as its bytes.

### Cited Findings
- Hit-rate definition used by TraceLab: token-weighted share of input served from cache, counting Claude `cache_read_input_tokens` and Codex `cached_input_tokens` as prefix tokens, and fresh input plus cache-creation tokens as appended tokens; the paper stresses this is not the share of steps with a hit — [TraceLab](https://arxiv.org/abs/2606.30560)
- Anthropic's per-request accounting: total input = `cache_read_input_tokens` + `cache_creation_input_tokens` + `input_tokens`, with `cache_creation.ephemeral_5m_input_tokens` and `cache_creation.ephemeral_1h_input_tokens` separating write tiers — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Other providers' fields: OpenAI `usage.input_tokens_details.cached_tokens`; DeepSeek `prompt_cache_hit_tokens` and `prompt_cache_miss_tokens`; Vertex `cachedContentTokenCount`; llama.cpp `timings.cache_n` — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching); [DeepSeek context caching guide](https://api-docs.deepseek.com/guides/kv_cache); [Vertex AI context cache overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview); [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- Operational signal: a high read-to-creation ratio means caching works; creation staying high turn after turn means something in the prefix is changing. Claude Code exposes a per-session hit ratio, miss count and likely cause of the last miss — [Claude Code prompt caching docs](https://code.claude.com/docs/en/prompt-caching.md)
- Cost metrics used in the literature: per-session cost split into cache-read, appended and output tokens (TraceLab); percentage cost reduction against a no-cache baseline with 40 sessions per condition and t-tests (Lumer et al.); ratio of total session cost between two placements on a replayed script (Zep) — [TraceLab](https://arxiv.org/abs/2606.30560); [Lumer et al. 2026](https://arxiv.org/abs/2601.06007); [Zep blog](https://www.getzep.com/blog/where-you-put-memory-in-the-prompt-can-cut-your-token-bill-up-to-2x/)
- Latency metric: time to first token; Lumer et al. warn it varies with server load and should be tested on representative workloads; DeepSeek's launch example is 13 s to 500 ms on a 128K-token prompt — [Lumer et al. 2026](https://arxiv.org/abs/2601.06007); [DeepSeek news 2024-08-02](https://api-docs.deepseek.com/news/news0802)
- Replay design: Zep replayed one scripted conversation with identical memory blocks and identical model replies in both arms, so placement was the only variable — [Zep blog](https://www.getzep.com/blog/where-you-put-memory-in-the-prompt-can-cut-your-token-bill-up-to-2x/)
- Timing matters: hit rate collapses between 2 and 10 minutes of idle time in the Copilot trace, and user-initiated steps hit far less often than tool-result steps in TraceLab — [Agentic Coding in the Wild](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/08/ghcp_traces-6.pdf); [TraceLab](https://arxiv.org/abs/2606.30560)
- Prompt size matters: below the provider minimum caching gives nothing and can regress TTFT; savings grow with prefix size — [Lumer et al. 2026](https://arxiv.org/abs/2601.06007)
- Caches can leak between runs: identical prefixes are shared within a workspace or organization, and vLLM's `cache_salt` exists to restrict that — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); [vLLM prefix caching design](https://docs.vllm.ai/en/latest/design/v1/prefix_caching/)
- Hits are best-effort on some providers: DeepSeek states no guaranteed hit rate; OpenAI keys do not guarantee a hit; on Gemini only explicit caching is described as ensuring the discount (a search snippet of the Gemini API page says implicit caching has no cost-saving guarantee; I did not see that sentence on the page as fetched) — [DeepSeek context caching guide](https://api-docs.deepseek.com/guides/kv_cache); [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching); [Vertex AI context cache overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview); [Gemini API caching docs](https://ai.google.dev/gemini-api/docs/caching)

### Inferences
Proposed protocol for the comparison; this is my design, assembled from the cited methods.
- Primary metrics: (1) cached input share = cache-read tokens / total input tokens, token-weighted per session; (2) input cost per session = sum over requests of fresh x p + write x w x p + read x r x p, with write tiers kept separate; (3) TTFT per request, reported as a distribution. Secondary: re-written tokens per memory update (the direct measure of invalidation), and cost per completed task.
- Arms: (A) immutable nodes, oldest-first append, frozen core plus tail deltas; (B) the same information consolidated by a rewrite pass. Cross each arm with placement (system-level prefix, after the conversation prefix as a trailing message) so that mutability and position are not confounded.
- Hold equal: model, provider, lifetime setting, breakpoint policy, tool set, system prompt, the scripted user turns and tool results (replay), and the schedule on which memory changes (same number of updates at the same turns).
- Control memory size two ways, because consolidation shortens memory. Run one comparison at equal token count (pad or truncate) to isolate the byte-stability effect, and one at natural sizes to get the net cost. Report absolute cost, not only hit rate: a rewritten memory can show a lower cached share and still cost less if it is much smaller.
- Control timing explicitly. Inter-turn and inter-session gaps decide whether a cache exists to be broken. Replay with fixed gap distributions on both sides of the lifetime (for example under 1 minute, 2-10 minutes, over 1 hour), and run rewrites both inside and outside the live window; the hypothesis predicts a large difference inside and none outside.
- Isolate caches between arms and repetitions: a unique run-specific token at the very start of each run's prefix (or separate workspaces; `cache_salt` on vLLM), and sequential, not concurrent, first requests so that one arm does not warm the other.
- Account for provider noise: best-effort hits and load-dependent TTFT call for repeated sessions per cell (Lumer et al. used 40) and a significance test; a self-hosted vLLM or llama.cpp run gives a deterministic check of the invalidation mechanics.
- Guardrail: task success or answer quality per arm, since frozen or stale memory and superseded-but-present nodes may change behaviour.
- Sweep the three factors the hypothesis names: memory size (below the minimum, about 2K, 10K, 50K tokens), position (head against tail), and update frequency (every turn, every N turns, per session).

### Gaps
- No standard benchmark exists for cache-aware memory; the protocol above is untested.
- Rate-limit effects (Anthropic excludes cache hits from the limit, OpenAI counts cached tokens toward TPM) are documented but I found no measurement of their impact on agent throughput.
- No source reports variance of hit rate under identical replays on hosted APIs, so the number of repetitions needed is unknown.
