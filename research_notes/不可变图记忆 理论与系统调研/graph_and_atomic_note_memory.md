# Graph-structured and atomic-note memory systems for LLM agents: data models, evidence, and what is missing (research notes, 2026-11-13)

Reading conventions used throughout:
- Status tags: **[PR]** peer-reviewed venue confirmed in this session; **[PR?]** venue reported but not verified in this session; **[pre]** arXiv preprint; **[vendor]** vendor paper, blog or documentation. Sources dated July 2026 or later are recent preprints found by search today and read once; none is independently replicated.
- "Not verified" means I could not confirm the item on the page I read.
- The design being positioned ("the target design") is: an append-only typed knowledge graph of compact immutable nodes; a full note is composed at read time by traversing typed edges; a change is an appended amendment node; every node and edge type is checked by code; a wrong line of work is pruned by tracing typed dependency edges from a root decision.

## Key question 1: What is the precise data model of each system (and of Anthropic's notes/wiki/index model and Claude Code auto memory)?

### Takeaway
Almost every surveyed system stores LLM-written units (notes, fact sentences, triples, summaries) whose types and links are free-form LLM output, and most of them rewrite or delete stored units in place (A-MEM, Mem0, MemTree, AriGraph, Cognee, Anthropic's dreaming). The systems that come closest to the target design each hold only part of it: Zep/Graphiti (history-preserving bi-temporal edges, optional Pydantic types), Kumiho (immutable revisions plus six typed edges), PACMI and MemTX (typed dependency edges with cascade invalidation), and code graphs such as RepoGraph/LocAgent (node and edge types assigned by a parser, not a model).

### Cited Findings

#### Baseline: Anthropic, "The components of agent memory" [vendor, 2026-11-06]
- Four layers, bottom to top: transcripts (a "searchable event log"), memory notes written by Claude and kept in a folder, memory representations (mainly wikis, "a collection of pages written and maintained by Claude"), and injected context loaded into every session, which "has to stay relatively small". — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Notes are files in folders (file names such as `global.md` and `MEMORY.md`); the model decides what to save under "simple guidance". Wiki pages link to related notes and links act as "a map"; the article gives link counts only (for example 255 links over 68 pages; 225 to 278 links after a second pass) and describes no link types or schema. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- "Dreaming" is an offline model-run pass that checks notes against transcripts and rewrites wrong ones, writes/corrects/merges wiki pages, repoints broken links, adds pages, and promotes notes into injected context. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Measured (vendor-run): CL-Bench mean reward no-memory to memory, Opus 5.5 0.655 to 0.838, Sonnet 5.5 0.644 to 0.833, Opus 5 0.564 to 0.828, Opus 4.7 0.383 to 0.700, Sonnet 5 0.306 to 0.610, Sonnet 4.6 0.330 to 0.364. Stainless corpus (~350k files, ~420M tokens, 25 questions): wiki-only 13% to 48% of graded criteria as dreaming scaled from 2 to 128 sessions; wiki plus search 61% vs 53% search alone, saving about 20,000 tokens per question. Cross-document merger questions (24): 87% with wiki vs 73% search-only; no clear gain on a single-document task. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Failure cases reported by Anthropic itself: one wiki grew to 203 KB from a 115 KB corpus (1.77x; 68 pages, 255 links, some unlinked) and "effectively abstracted nothing"; agents overwrote a shared terms table so only 41 of 57 graded facts (72%) survived, fixed by one page per contract (57/57); a wrong location note sent an agent looping until dreaming rewrote it. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Managed Agents "dreams" take a memory store plus 1 to 100 sessions and write a new, separate output store; the input store is not modified (taken from this project's earlier notes file `production_systems_and_anchor.md`; not re-fetched in this session). — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)

#### Baseline: Claude Code auto memory [vendor docs]
- Claude "saves four kinds of notes for itself" and records the kind as a `type` field in the file's frontmatter: `user` (role, expertise, working preferences), `feedback` (corrections and confirmed approaches), `project` (ongoing work, deadlines, decisions not derivable from code or git history), `reference` (where to find information outside the project). It skips anything derivable from the codebase or already in CLAUDE.md. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Storage: `~/.claude/projects/<project>/memory/` with a `MEMORY.md` index ("one line per memory, loaded into every session") and one topic file per memory, read on demand; the first 200 lines or 25 KB of `MEMORY.md` load at session start. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- The only code-side check described is on index size: after a write, Claude Code measures `MEMORY.md` against the limits and returns an error telling Claude to rewrite the index when over. Files are "plain markdown you can edit or delete at any time"; they stay "until you or Claude edits or deletes them". No type validation, link typing or history is described. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

#### A-MEM (Xu et al.) [PR: NeurIPS 2025 per arXiv comments]
- Note: m_i = {c_i content, t_i timestamp, K_i LLM keywords, G_i LLM tags, X_i LLM contextual description, e_i embedding of the concatenation, L_i set of linked notes}. — [A-MEM, arXiv 2502.12110](https://arxiv.org/html/2502.12110v11)
- Links: embedding top-k candidates, then the LLM decides which links to create; links carry no type. — [A-MEM](https://arxiv.org/html/2502.12110v11)
- "Memory evolution": for each neighbour the LLM decides whether to update its context, keywords and tags; the evolved memory "replaces the original memory" (overwrite, no history). The paper is internally inconsistent: the appendix prompt asks only for updated context and tags, and lists "merge" and "prune" actions the text does not describe. — [A-MEM](https://arxiv.org/html/2502.12110v11)
- Read-time assembly beyond embedding top-k (for example, pulling linked notes with a hit) was not confirmed from the text I read; not verified.

#### Zep / Graphiti (Rasmussen et al.) [pre, vendor; arXiv Jan 2025]
- Three subgraphs: episode subgraph (episodic nodes hold raw input of type message, text or JSON; episodic edges link episodes to the entities they mention), semantic entity subgraph (entity nodes; fact edges between entities), community subgraph (community nodes with summaries; edges to member entities). — [Zep, arXiv 2501.13956](https://arxiv.org/html/2501.13956v1)
- Bi-temporal: fact edges carry t_valid and t_invalid (event time) and t'_created and t'_expired (ingestion time). — [Zep](https://arxiv.org/html/2501.13956v1)
- Invalidation: an LLM compares a new edge with related edges; on a temporally overlapping contradiction the old edge's t_invalid is set to the new edge's t_valid. Invalidated edges are kept; the paper describes no deletion. — [Zep](https://arxiv.org/html/2501.13956v1)
- Mutable parts: entity resolution has an LLM produce an updated name and summary for an existing entity; community summaries are updated on each new member and drift, so "periodic full refreshes" are needed. — [Zep](https://arxiv.org/html/2501.13956v1)
- Typing in the paper: entities free-form; relation labels are LLM-generated all-caps strings; the paper says LLM-generated graphs mostly lack formal ontologies and lists domain ontologies as future work. Graph writes use predefined Cypher queries, not LLM-generated ones. — [Zep](https://arxiv.org/html/2501.13956v1)
- Typing in current Graphiti docs: custom entity and edge types are Pydantic models; an `edge_type_map` lists which edge types are allowed between which entity-type pairs; attributes are validated by Pydantic; if a pair has no map entry the extracted predicate is kept as the edge name with no schema; classifying previously ingested data under new types requires re-ingestion into a new graph. — [Graphiti docs](https://help.getzep.com/graphiti/core-concepts/custom-entity-and-edge-types)
- Read time: cosine, BM25 and breadth-first search; rerank (RRF, MMR, episode-mentions, node-distance, cross-encoder); a constructor formats facts with valid date ranges, entity summaries and community summaries. — [Zep](https://arxiv.org/html/2501.13956v1)
- Provenance: episodic edges give bidirectional links between episodes and derived facts for citation; the paper says these are not examined in its experiments. — [Zep](https://arxiv.org/html/2501.13956v1)

#### Mem0 and Mem0^g (Chhikara et al.) [pre, vendor; arXiv Apr 2025; a peer-reviewed venue is not verified]
- Mem0 base: an LLM extracts candidate facts from (conversation summary, last 10 messages, new message pair); for each fact the top-10 similar memories are retrieved and the LLM picks ADD, UPDATE, DELETE or NOOP by tool call. UPDATE replaces the memory under the same ID; DELETE removes it; no versioning or history is described. — [Mem0, arXiv 2504.19413](https://arxiv.org/html/2504.19413v1)
- Mem0^g: directed labelled graph G = (V, E, L); entity nodes have an entity type, embedding and creation timestamp; relations are triplets (v_s, r, v_d) from an LLM entity extractor and relation generator; a conflict detector plus LLM "update resolver" marks outdated relationships invalid rather than removing them. — [Mem0](https://arxiv.org/html/2504.19413v1)
- Mem0^g read time: entity-centric subgraph expansion, plus matching the query embedding against triplet encodings. — [Mem0](https://arxiv.org/html/2504.19413v1)

#### HippoRAG [PR: NeurIPS 2024] and HippoRAG 2 [PR: ICML 2025]
- HippoRAG combines an LLM, a knowledge graph and Personalized PageRank; reports up to 20% gains on multi-hop QA and single-step retrieval comparable to iterative IRCoT at 10 to 30 times lower cost and 6 to 13 times faster. — [HippoRAG, arXiv 2405.14831](https://arxiv.org/abs/2405.14831)
- HippoRAG 2 index: an LLM runs schema-less OpenIE per passage; subjects and objects become phrase nodes, relations become relation edges; phrase pairs with embedding similarity above 0.8 get a synonym edge; each passage is a passage node linked to its phrases by "contains" context edges. — [HippoRAG 2, arXiv 2502.14802](https://arxiv.org/html/2502.14802v2)
- Read time: query matched to triples (top-5), an LLM "recognition memory" step filters triples, filtered phrase nodes and all passage nodes seed Personalized PageRank (damping 0.5), passages ranked by score. — [HippoRAG 2](https://arxiv.org/html/2502.14802v2)
- Updates: the paper describes only appending; no mechanism to edit, correct or delete triples. — [HippoRAG 2](https://arxiv.org/html/2502.14802v2)

#### Microsoft GraphRAG [pre; arXiv 2404.16130, no venue on the page] and LazyGraphRAG [vendor blog, 2024-11-25]
- GraphRAG index: 600-token chunks with 100-token overlap; the LLM emits entities (name, type, description), relationships (source, target, description, numeric strength) and optional claims; "gleaning" rounds re-ask for missed entities; entity matching is exact string match; duplicate relationships become edge weights; hierarchical Leiden communities; each community gets an LLM report (title, summary, 0 to 10 impact rating, 5 to 10 findings). — [GraphRAG](https://arxiv.org/html/2404.16130v2)
- Types are free-form LLM output steered by a type list in the prompt; no programmatic schema validation is described. How the index handles new or changed documents is not described in the text I read. — [GraphRAG](https://arxiv.org/html/2404.16130v2)
- Read time (global): map-reduce over community reports, each partial answer scored 0 to 100, packed into an 8k context. — [GraphRAG](https://arxiv.org/html/2404.16130v2)
- LazyGraphRAG: no upfront LLM extraction or summarization; NLP noun-phrase concepts and co-occurrences form a concept graph with hierarchical communities; it "defers all LLM use until query time", with a relevance-test budget as the main parameter. — [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)

#### G-Memory (Zhang et al.) [PR: NeurIPS 2025; "spotlight" per search summary, not verified]
- Three tiers: insight graph (node = insight text plus the set of supporting queries; hyper-edges (insight_m, insight_n, query_j)), query graph (node = query, status Failed/Resolved, its interaction graph; edges = semantic relations between queries), interaction graph (node = an agent's utterance; directed temporal edges). — [G-Memory, arXiv 2506.07398](https://arxiv.org/html/2506.07398v2); venue: [NeurIPS proceedings](https://papers.neurips.cc/paper_files/paper/2025/hash/136a45cd9b841bf785625709a19c6508-Abstract-Conference.html)
- Structure is mostly set by code; the LLM summarizes insights, scores query relevance, and sparsifies interaction graphs. — [G-Memory](https://arxiv.org/html/2506.07398v2)
- Read time: embed query, top-k similar queries, 1-hop expansion, upward to insights whose support sets intersect, downward to LLM-sparsified interaction subgraphs, then per-role filtering. — [G-Memory](https://arxiv.org/html/2506.07398v2)
- Update: new interaction graph, query node and insight node are appended; existing insights change only in their support sets (insight text unchanged in the equations). — [G-Memory](https://arxiv.org/html/2506.07398v2)

#### MemTree (Rezazadeh et al.) [PR: ICLR 2025]
- Node: content text, embedding, parent pointer, children, depth; root is structural only. — [MemTree, arXiv 2410.14052](https://arxiv.org/html/2410.14052); venue: [ICLR 2025 proceedings](https://proceedings.iclr.cc/paper_files/paper/2025/hash/0382cb76309820f71c6eacd47b36ce71-Abstract-Conference.html)
- Insertion: traverse from the root by embedding similarity against a depth-dependent threshold; add as a new leaf or descend; every ancestor on the path has its content rewritten by an LLM and its embedding recomputed (internal nodes are mutable). About 3.27 LLM calls per insertion (plus or minus 2.38). No deletion or forgetting mechanism. — [MemTree](https://arxiv.org/html/2410.14052)
- Read time: "collapsed tree" retrieval, cosine similarity over all nodes, top-k. Traversal-based retrieval performed worse than collapsed retrieval. — [MemTree](https://arxiv.org/html/2410.14052)

#### AriGraph (Anokhin et al.) [PR: IJCAI 2025]
- G = (V_s, E_s, V_e, E_e): semantic vertices (objects), semantic edges (triplets), episodic vertices (the full observation at each step), episodic edges linking all triplets extracted from one observation to that observation. — [AriGraph, arXiv 2407.04363](https://arxiv.org/html/2407.04363); venue: [IJCAI 2025 proceedings](https://www.ijcai.org/proceedings/2025/0002)
- Update: the LLM extracts triplets, compares them with existing edges on the same vertices, and outdated edges are removed (destructive on the semantic layer; the episodic vertex keeps the raw observation). — [AriGraph](https://arxiv.org/html/2407.04363)
- Read time: semantic search over triplets (Contriever, bounded depth and width), then episodic search scoring observations by how many retrieved triplets link to them. — [AriGraph](https://arxiv.org/html/2407.04363)

#### MemOS / MemCube (MemTensor et al.) [pre, vendor; arXiv 2507.03724 v4]
- MemCube wraps three payload types (plaintext; activation such as KV-cache; parameter such as LoRA) with metadata: descriptive (timestamps, origin signature, semantic type such as fact or user preference), governance (access control, TTL or decay, priority, sensitivity tags, logs), behavioural (access frequency, contextual fingerprint, version chain). — [MemOS](https://arxiv.org/html/2507.03724)
- Provenance ID assigned at creation persists through the lifecycle; a version chain is said to support conflict resolution and rollback; lifecycle states Generated, Activated, Merged, Archived, Expired, plus a "Frozen" state (the paper lists the states inconsistently between sections). Update API supports append, merge or overwrite. No conflict-resolution algorithm is given. — [MemOS](https://arxiv.org/html/2507.03724)
- Plaintext memory is described as a hierarchical graph organized by task, concept and fact paths; node and edge details were not in the text I read. — [MemOS](https://arxiv.org/html/2507.03724)

#### Cognee [vendor docs]
- A DataPoint is a Pydantic model ("atomic units of knowledge") with base fields id (shared across vector, graph and relational stores), created_at, updated_at, version, type (the subclass name), belongs_to_set, ontology_uri, topological_rank, metadata.index_fields. — [Cognee docs](https://docs.cognee.ai/core-concepts/building-blocks/datapoints)
- Fields that reference other DataPoints become graph edges whose type comes from the field name; developers define the classes. — [Cognee docs](https://docs.cognee.ai/core-concepts/building-blocks/datapoints)
- Updates: mutate fields, call `update_version()`, re-run `add_data_points()`; the upsert replaces the node in all three stores. Deletion is permanent; there is no soft delete. — [Cognee docs](https://docs.cognee.ai/core-concepts/building-blocks/datapoints)

#### Letta (MemGPT lineage) [vendor docs; MemGPT itself is an earlier 2023 preprint]
- Current memory is "MemFS": a git-backed directory of Markdown files with YAML frontmatter (name, description); root-level files load into the system prompt every turn; subdirectories with their own `MEMORY.md` stay out of context until needed. — [Letta MemFS docs](https://docs.letta.com/concepts/memfs)
- The agent edits files with ordinary file tools; every memory edit is committed (version history, conflict resolution); background subagents ("dreaming", "memory doctor") use git worktrees. No typing, schema validation or link checking is described. — [Letta MemFS docs](https://docs.letta.com/concepts/memfs)

#### LightMem (Fang et al.) [PR: ICLR 2026]
- Three stages: sensory (LLMLingua-2 pre-compression, topic segmentation), short-term (LLM summary per topic group when a token threshold is hit), long-term (offline "sleep-time" update). An entry holds a topic, the summary embedding, timestamps and the raw user and model turns. — [LightMem, arXiv 2510.18866](https://arxiv.org/html/2510.18866); venue: [ICLR 2026 proceedings](https://proceedings.iclr.cc/paper_files/paper/2026/hash/a05b72653ec5b473732129829ae04195-Abstract-Conference.html)
- Online "soft update": new entries are only inserted with timestamps, nothing is overwritten at test time. Offline: each entry gets an update queue of its top-k similar entries with later timestamps, processed in parallel (add, delete, update, merge). — [LightMem](https://arxiv.org/html/2510.18866)

#### MIRIX (Wang and Chen) [pre, vendor; arXiv Jul 2025]
- Six stores with fixed fields: Core (persona and human blocks, rewritten above 90% capacity), Episodic (event_type, summary, details, actor, timestamp), Semantic (name, summary, details, source), Procedural (entry_type, description, steps), Resource (title, summary, resource_type, content), Knowledge Vault (entry_type, source, sensitivity, secret_value). Six memory-manager agents plus a meta manager route and write; storage is sqlite. No typed links between entries and no deletion behaviour are described. — [MIRIX, arXiv 2507.07957](https://arxiv.org/html/2507.07957)
- Read time: the agent generates a topic, retrieves top-10 entries per store (embedding, BM25 or string match), and injects them with source tags. — [MIRIX](https://arxiv.org/html/2507.07957)

#### Memory-R1 (Yan et al.) [pre; arXiv Aug 2025, v5 Jan 2026]
- Flat bank of ID-tagged natural-language facts (no graph). A Memory Manager fine-tuned with PPO or GRPO chooses ADD, UPDATE, DELETE or NOOP, rewarded by a frozen answer agent's exact-match correctness; trained on 152 QA pairs. — [Memory-R1, arXiv 2508.19828](https://arxiv.org/html/2508.19828)
- Motivating failure: a user adopts a dog named Buddy and later a second dog named Scout; a vanilla LLM manager DELETEs the Buddy memory and ADDs Scout, treating a different name as a replacement. — [Memory-R1](https://arxiv.org/html/2508.19828)

#### RAPTOR (Sarthi et al.) [PR?: ICLR 2024, not verified on the page I read; earlier foundation]
- 100-token leaf chunks; SBERT embeddings; GMM soft clustering with UMAP (a node can belong to several clusters); gpt-3.5-turbo summaries become parent nodes; recursion until clustering is infeasible. Summary-to-child length ratio averages 0.28. Collapsed-tree retrieval (about top-20 nodes, 2,000 tokens) beat layer-by-layer traversal. Whether the tree supports incremental update is not stated. — [RAPTOR, arXiv 2401.18059](https://arxiv.org/html/2401.18059)

#### Knowledge graphs for coding agents (types assigned by a parser)
- RepoGraph [PR?: reported as ICLR 2025, not verified]: nodes are lines of code classed as definition or reference (attributes line_number, file_name, directory); two edge types, contain and invoke; built with tree-sitter AST parsing, not an LLM; retrieval is the k-hop ego graph (k = 1 or 2) of a search term. Persistence across sessions is not described. — [RepoGraph, arXiv 2410.14684](https://arxiv.org/html/2410.14684v2)
- LocAgent [PR: ACL 2025 per ACL Anthology listing in search results]: node types directory, file, class, function; edge types contain, import, invoke, inherit; built by AST parsing; tools SearchEntity, TraverseGraph (filter by entity type and relation type, direction, hops), RetrieveEntity. — [LocAgent, arXiv 2503.09089](https://arxiv.org/html/2503.09089)
- CodexGraph [PR: NAACL 2025 per ACL Anthology listing in search results; schema taken from a search summary, not fetched]: node types MODULE, CLASS, METHOD, FUNCTION, FIELD, GLOBAL_VARIABLE; edge types CONTAINS, INHERITS, HAS_METHOD, HAS_FIELD, USES; the agent writes graph-query-language queries against a graph database built by static analysis. — [CodexGraph, arXiv 2408.03910](https://arxiv.org/html/2408.03910v2)

#### 2025-2026 systems that type memory nodes or edges
- Hindsight [pre, vendor plus academic authors; arXiv Dec 2025]: four "networks" (world facts, agent experiences, opinions with confidence in [0,1], observations = entity summaries regenerated when facts change); a memory unit has id, bank id, narrative text, embedding, occurrence interval, mention time, fact type, confidence (opinions), metadata; four link types: temporal, semantic and entity links are created by code, causal links (causes, caused_by, enables, prevents) are extracted by the LLM. Opinions are mutable (confidence stepped up or down). The paper says controlled forgetting and time-aware belief revision are not addressed. — [Hindsight, arXiv 2512.12818](https://arxiv.org/html/2512.12818)
- MAGMA [pre; arXiv Jan 2026]: event nodes (content, timestamp, embedding, attributes) connected by four edge types: temporal (code rule on the fast path), semantic (embedding threshold), causal and entity (LLM inference in a background "slow path" over the 2-hop neighbourhood). Read time: classify intent (Why/When/Entity), pick anchors by rank fusion, beam traversal with intent-specific edge-type weights, order output by time or by topological sort on causal edges. — [MAGMA, arXiv 2601.03236](https://arxiv.org/html/2601.03236)
- Kumiho [pre, single author affiliated with the vendor; arXiv Mar 2026]: Item (named, typed unit) with an append-only sequence of immutable Revisions; mutable Tags point to a revision ("Immutable Revisions, Mutable Pointers"); six typed edges: Depends_On (validity dependency), Derived_From (evidential provenance), Supersedes, Referenced, Contains, Created_From. A change is a new revision plus a Supersedes edge plus a tag move; rollback moves the tag back. `AnalyzeImpact` computes the transitive dependency cascade of conclusions that "may need re-evaluation" (identification, not automatic invalidation). Who assigns the non-Supersedes edge types was not clear from the text I read. — [Kumiho, arXiv 2603.17244](https://arxiv.org/html/2603.17244)
- PACMI [pre; arXiv Oct 2026]: memory as a provenance graph of prior-memory and new-evidence nodes; dependency edges `supports` and `used-by`, plus `updates` or `contradicts` added by an LLM relation classifier constrained by deterministic rules; validity states active, needs-verification, historical-only, superseded. In the reported benchmark the `supports`/`used-by` edges are supplied by annotation; inducing them from raw memory text is left as future work. — [PACMI, arXiv 2610.05732](https://arxiv.org/html/2610.05732)
- MemTX [pre, "under review"; arXiv Jul 2026]: record = (entity, attribute, value) with source and authority weight, permission block, derived-from edges forming a DAG, record type (belief, summary, profile, index entry, shared copy, tool action), validity interval, confidence; eight lifecycle states (raw, tentative, validated, committed, action-safe; quarantined, superseded, revoked); transactions with risk tiers; commit runs four checks (evidence, validity interval, rule-based conflict, dependency stability). Protocol logic, gating and repair are code; LLM agents produce content. — [MemTX, arXiv 2607.23929](https://arxiv.org/html/2607.23929v2)

### Inferences
- No surveyed system composes a "note" at read time from compact immutable nodes plus amendment nodes. The nearest are Kumiho (an item is a chain of immutable revisions, but each revision replaces the whole previous one; the paper lists partial semantic merge as future work) and Zep (a fact's history is the chain of invalidated edges, but entity summaries and community summaries are rewritten in place).
- Typing by code exists today mainly where the source is formal (code graphs parsed by tree-sitter/AST) or where a developer supplies a schema (Graphiti custom types, Cognee DataPoints, MIRIX's fixed stores). In those schema systems the classification of a piece of text into a type is, as far as the papers and docs show, still done by the extraction model (the Graphiti page does not name the classifier); code checks attribute shape, not whether the type was the right one.
- Anthropic's notes/wiki model and Claude Code auto memory sit at the untyped end: four note types as a frontmatter string written by the model, untyped links, and in-place rewriting during dreaming. Relative to them, the target design changes three things at once: link typing, code-side checking, and immutability.
- Edge-type vocabularies in the typed systems converge on two families: associative/structural (semantic, temporal, entity, contains, referenced) and dependency/derivation (depends_on, derived_from, supports, used-by, supersedes, contradicts). Only the second family supports pruning; the mainstream systems (A-MEM, Zep, Mem0, GraphRAG, HippoRAG, G-Memory, MemTree, AriGraph, MIRIX, LightMem) have only the first.

### Gaps
- MemOS's graph structure for plaintext memory (node and edge kinds) and its conflict algorithm were not found in the text I read; the open-source repository was not inspected.
- A-MEM's read-time use of links, RAPTOR's and RepoGraph's venues, and whether RepoGraph/LocAgent graphs persist across sessions as memory were not verified.
- Not examined at all: MemoryOS, Nemori, LangMem, Memobase, Supermemory, MemU, SGMem, H-MEM, CAM, D-SMART, TReMu, MemoTime (named in surveys or as baselines only). Code Graph Model (CGM), ARISE and Prometheus were seen only in search summaries.
- Kumiho's edge-assignment procedure and the body of its postulate proofs (the page was truncated at about one third) were not read.
- GraphRAG's handling of incremental updates in the current open-source release was not checked.

## Key question 2: For each system, what are the unit of memory and its size, who assigns and checks types, how are updates done, how is context assembled, is provenance kept, and what are the measured results and token or cost savings?

### Takeaway
Compact units cut read-time context by one to two orders of magnitude (about 1 to 4k tokens against 16k to 115k), and that saving is consistent across papers; the accuracy claims are not. The same system's LoCoMo score moves by 20 or more points depending on who ran it, and on LoCoMo a plain full-context baseline beats Mem0 and MIRIX in their own papers. Build cost is the hidden price: on the same corpus, LLM-built graphs cost about 5 to 70 times the index tokens of a summary tree (RAPTOR), and a plain embedding index needs no LLM tokens at all.

### Inferences
- Token savings from compact units are the one result that replicates across independent papers (A-MEM, Zep, MAGMA, LightMem, AriGraph, MemOS all report low-thousands context against tens of thousands or more). Accuracy rankings do not replicate: Zep ranges from 59 to 79 and MIRIX from 64 to 85 on LoCoMo depending on the paper, and full-context ranges from 48 to 88. A new design should not be positioned on LoCoMo rank.
- Where a full-context baseline is reported on LoCoMo by a memory vendor, it wins (Mem0: 72.90 vs 68.44; MIRIX: 87.52 vs 85.38). Structured memory shows a clear accuracy advantage only where the history exceeds the context window (LongMemEval at 115k tokens) or where the question needs several documents (Anthropic's merger task, HippoRAG 2 on 2Wiki and MuSiQue).
- Every system that keeps raw source alongside extracted units (Zep episodes, HippoRAG 2 passage nodes, AriGraph episodic vertices, LightMem raw turns, G-Memory interaction graphs) uses the source at read time or for citation; systems that keep only extracted units (Mem0, Memory-R1) have no way to re-check an extraction.
- Graph build cost is a real axis of comparison: GraphRAG's index costs about 12 times HippoRAG 2's and about 68 times RAPTOR's input tokens on the same corpus. A design whose nodes are written once and never rewritten avoids the recurring rewrite cost seen in MemTree (ancestors rewritten per insert) and Zep (community refreshes), but the notes found no measurement of that saving.

### Gaps
- No paper reports the size distribution of stored units in tokens; "typical size" in the table is inferred from descriptions.
- No source measured the token cost of composing a note at read time by edge traversal against loading a monolithic note.
- I found no coding-agent benchmark result for a persistent cross-session knowledge-graph memory; the code-graph papers evaluate a per-repository index, not memory of past work.
- Mem0's counter-rebuttal to Zep (the 58.44% claim) and the Backboard 90% LoCoMo claim were not checked against primary sources.

## Key question 3: What is the evidence for or against atomic notes (granularity, link-traversal composition, error rates of LLM-built graphs)?

### Takeaway
Small self-contained units help retrieval (Dense X: +10 to +12 Recall@5 for unsupervised retrievers; LongMemEval: rounds beat sessions) but stripping them from their source hurts answers (LongMemEval: fact-only values lose information; triple-only KGs score 30 F1 points below plain RAG and miss about a third of answer entities). The supported recipe is atomic units as index and link targets with the source kept, which is what HippoRAG 2 did to fix HippoRAG. LLM-built graphs carry measurable error: 26% of failures traced to the triple filter, about 1 to 5% defective propositions even from GPT-4, near-zero relation reuse without normalization, and update omission above 50% in most commercial memory systems.

### Cited Findings

#### Granularity
- Dense X Retrieval [PR: EMNLP 2024]: propositions are atomic, minimal, self-contained statements; on a 2021 Wikipedia dump, 41.4M passages (58.5 words average), 114.2M sentences (21.0), 256.9M propositions (11.2). Passage to proposition Recall@5: SimCSE 34.3 to 46.3, Contriever 43.0 to 52.7, DPR 57.3 to 59.9, GTR 65.2 to 68.0. Downstream EM@500 tokens with LLaMA-2-7B: +4.1, +3.2, +2.7, +2.8. Gains are largest for rare entities. The error case study notes proposition retrieval struggles on multi-hop questions needing long-range reasoning. — [Dense X Retrieval, arXiv 2312.06648](https://arxiv.org/html/2312.06648)
- Proposition quality (expert-annotated, 50 passages): not faithful 0.7% (GPT-4) and 1.3% (fine-tuned Propositionizer); not minimal 2.9% and 2.0%; not stand-alone 4.9% and 3.1%. — [Dense X Retrieval](https://arxiv.org/html/2312.06648)
- LongMemEval: storing individual rounds works better than whole sessions; compressing sessions into extracted facts as the stored value loses information and hurts overall QA but helps multi-session reasoning; using extracted facts to expand the index key while keeping the original value improves recall@k by 9.4% and accuracy by 5.4% on average; time-aware query expansion improves temporal recall by 6.8 to 11.3%; a structured (JSON plus Chain-of-Note) reading format adds up to about 10 points. — [LongMemEval](https://arxiv.org/html/2410.10813)
- SeCom [PR?: reported as ICLR 2025, not verified]: turn-level, session-level and summarization-based memory units each limit retrieval accuracy; topically coherent segments outperform them, and compression (LLMLingua-2) acts as denoising; the abstract gives no numbers. — [SeCom, arXiv 2502.05589](https://arxiv.org/abs/2502.05589)
- Anthropic: one page per contract with terms quoted verbatim preserved 57/57 graded facts where a shared table kept 41/57; an over-built wiki at 1.77x the corpus size "effectively abstracted nothing". — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

#### Links and traversal
- A-MEM ablation (GPT-4o-mini, F1): without links and evolution, multi-hop 9.65, temporal 24.55, single-hop 13.28; with link generation only, 21.35, 31.24, 39.17; full system 27.02, 45.85, 44.65. Links account for most of the gain. — [A-MEM](https://arxiv.org/html/2502.12110v11)
- HippoRAG 2 states that structure-augmented methods (GraphRAG, RAPTOR, LightRAG, HippoRAG) underperform a strong embedding retriever; e.g. NQ F1 GraphRAG 46.9 and HippoRAG 55.3 vs NV-Embed-v2 61.9. Adding passage nodes and query-to-triple matching lifts HippoRAG 2 above the embedding baseline (average 59.8 vs 57.0; recall@5 78.2 vs 73.4), with the largest gain on 2Wiki (71.0 vs 61.5). — [HippoRAG 2](https://arxiv.org/html/2502.14802v2)
- RAG vs GraphRAG [PR: KDD 2026]: with Llama-3.1-8B, plain RAG F1 64.78 (NQ) and 60.04 (HotpotQA); triplets-only KG 34.28 and 25.02; triplets plus text 50.27 and 42.60; community-local 63.01 and 61.66; HippoRAG 2 61.03 and 63.01. RAG leads on single-hop and detail queries, graph methods on multi-hop; on MultiHop-RAG 13.6% of queries were answered only by GraphRAG and 11.6% only by RAG. — [Han et al.](https://arxiv.org/html/2502.11371)
- MemTree: traversal-based retrieval was worse than flat "collapsed" retrieval over all nodes; RAPTOR found the same. — [MemTree](https://arxiv.org/html/2410.14052); [RAPTOR](https://arxiv.org/html/2401.18059)
- Mem0^g: the graph variant adds about 2 points overall (68.44 vs 66.88) but lowers single-hop (65.71 vs 67.13) and multi-hop (47.19 vs 51.15) J scores, doubles stored tokens and roughly doubles latency. — [Mem0](https://arxiv.org/html/2504.19413v1)
- MAGMA: weighting traversal by edge type and query intent is reported to beat untyped-link systems (0.700 vs A-MEM 0.580 on LoCoMo judge score); single paper, no replication. — [MAGMA](https://arxiv.org/html/2601.03236)
- Anthropic: a linked wiki helps cross-document questions (87% vs 73%) and gives no clear gain where one document answers the question. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

#### Error rates of LLM-built graphs and memories
- Coverage: only about 65.8% of answer entities appear in the LLM-built KG for HotpotQA and 65.5% for NQ. — [Han et al.](https://arxiv.org/html/2502.11371)
- HippoRAG 2 failure analysis (100 cases): in 26% no supporting phrase survives the LLM triple filter and 18% end with zero triples; only 2% lack a supporting phrase within one hop; the authors say the filter's precision "has room for further improvement". The paper does not measure OpenIE extraction error directly. — [HippoRAG 2](https://arxiv.org/html/2502.14802v2)
- KGGen [pre; NeurIPS 2025 inferred from its checklist, not verified]: without entity resolution and relation normalization, graphs have "nearly as many unique relation types as edges"; GraphRAG on 1M characters produced 981 relations with 966 edge types over 514 entities. MINE-1 fact-recovery: KGGen 66.07%, GraphRAG 47.80%, OpenIE 29.84%. Valid triples in a 100-sample check: KGGen 98%, OpenIE 55%, GraphRAG 0% (by the paper's own validity criterion). KGGen's own limitation: over- or under-merging of entities. — [KGGen, arXiv 2502.09956](https://arxiv.org/html/2502.09956)
- HaluMem [pre; authors include MemTensor, the MemOS vendor, and MemOS ranks first]: memory extraction recall (Medium / Long sets) Mem0 42.91% / 3.23%, Supermemory 41.53% / 53.02%, MemOS 74.07% / 81.90%; extraction accuracy below 62% for all systems; update correctness MemOS 62.11%, Zep 47.28%, Mem0 25.50%, Supermemory 16.37%, Memobase 5.20% (Medium); update omission above 50% for most systems (Mem0 74.02%). Errors compound from extraction to update to QA. — [HaluMem, arXiv 2511.03506](https://arxiv.org/html/2511.03506)
- RAPTOR: about 4% of sampled summary nodes (6 of 150) contained minor hallucinations. — [RAPTOR](https://arxiv.org/html/2401.18059)
- GraphRAG did not measure fabrication rates and lists SelfCheckGPT-style checks as future work. — [GraphRAG](https://arxiv.org/html/2404.16130v2)
- MAGMA's stated limitation: LLM extraction errors and hallucinations yield wrong or missing causal and entity links that propagate to retrieval. — [MAGMA](https://arxiv.org/html/2601.03236)
- Zep's drop on single-session-assistant questions (94.6 to 80.4 with gpt-4o) shows extraction losing assistant-side detail. — [Zep](https://arxiv.org/html/2501.13956v1)
- LLM-judge evaluations of graph methods are fragile: with GPT-4o as judge, community-local GraphRAG won 0.97 when presented first and 0.12 when presented second. — [Han et al.](https://arxiv.org/html/2502.11371)

### Inferences
- The evidence favours atomic units as retrieval keys and link endpoints, and disfavours atomic units as the only stored form. For the target design this argues for compact immutable nodes that each keep a pointer to their source episode, rather than nodes that replace the source.
- Typed, code-checked edges address a specific measured defect: free-form LLM relation labels do not repeat (966 edge types for 981 relations), so they cannot drive traversal rules. A closed edge vocabulary enforced by code is the direct remedy, and MAGMA's and LocAgent's type-filtered traversal show what a closed vocabulary enables.
- Typing does not remove extraction error. Dense X shows about 3 to 5% of propositions are not stand-alone even with GPT-4, and HaluMem shows large omission rates. A design that never rewrites nodes keeps an early extraction error forever unless amendment nodes are actually written, so the amendment path needs its own measurement.
- Traversal is not automatically better than flat search: MemTree and RAPTOR both found flat retrieval over all nodes beat structure-following retrieval, and Mem0^g lost on multi-hop. Read-time composition by traversal should be tested against flat retrieval over the same nodes.

### Gaps
- I found no study that directly compares link-traversal composition of one note from several small nodes against a single monolithic note holding the same content, on either accuracy or tokens.
- I found no measurement of entity-resolution error rates in Zep/Graphiti or of hallucinated-edge rates in any agent-memory graph; the available numbers are for document KGs (KGGen, Han et al.) or for end-to-end memory operations (HaluMem).
- HaluMem's ranking should be treated with care because of author affiliation; no independent replication found.

## Key question 4: What exists for pruning, forgetting and correction in graph memories, and can any system remove a whole dependent subgraph when a root is found wrong?

### Takeaway
Mainstream graph memories correct locally: they invalidate, overwrite or delete the one fact that a new fact contradicts, and none records which other memories were derived from it. On the ICLR 2026 selective-forgetting test, memory systems score 2 to 7% on multi-hop cases. Dependent-subgraph handling appears only in 2026 preprints: PACMI and MemTX cascade over typed dependency edges, Kumiho computes the impact set without acting on it, ReTree prunes branches inside one search task, and RECON benchmarks the task; none is peer-reviewed, and PACMI's own ablation of the cascade is not statistically significant.

### Cited Findings

#### Local correction and forgetting in existing systems
- Zep: contradiction sets t_invalid on the old edge; nothing is deleted; community summaries drift and need periodic full refresh. — [Zep](https://arxiv.org/html/2501.13956v1)
- Mem0: DELETE removes a contradicted memory and UPDATE overwrites, with no history; Mem0^g marks relations invalid instead. — [Mem0](https://arxiv.org/html/2504.19413v1)
- A-MEM: evolution overwrites neighbour notes' attributes; no history. — [A-MEM](https://arxiv.org/html/2502.12110v11)
- AriGraph: outdated triplets are removed from the semantic graph. — [AriGraph](https://arxiv.org/html/2407.04363)
- MemTree, HippoRAG 2, GraphRAG: no deletion, correction or update mechanism described. — [MemTree](https://arxiv.org/html/2410.14052); [HippoRAG 2](https://arxiv.org/html/2502.14802v2); [GraphRAG](https://arxiv.org/html/2404.16130v2)
- MemOS: TTL and decay policies, access-frequency garbage collection or archiving, version chain with rollback and a "Time Machine" snapshot, as described; no algorithm given. — [MemOS](https://arxiv.org/html/2507.03724)
- Cognee: hard delete only; upsert overwrites. — [Cognee docs](https://docs.cognee.ai/core-concepts/building-blocks/datapoints)
- Letta MemFS: files edited in place with git history. — [Letta docs](https://docs.letta.com/concepts/memfs)
- LightMem: correction deferred to an offline pass in which only later-timestamped entries may update earlier ones. — [LightMem](https://arxiv.org/html/2510.18866)
- Hindsight: opinion confidence moves by a step on reinforce, weaken or contradict; the paper says controlled forgetting and time-aware belief revision are not addressed. — [Hindsight](https://arxiv.org/html/2512.12818)
- Memory-R1: a vanilla LLM manager wrongly deletes a still-true memory (the Buddy/Scout case); reinforcement learning on 152 QA pairs is proposed to make the ADD/UPDATE/DELETE choice more reliable. — [Memory-R1](https://arxiv.org/html/2508.19828)
- Anthropic: dreaming rewrites wrong notes against transcripts; generic multi-agent writing overwrote shared content (41/57 facts survived); the article says checking all memories continuously may be impractical. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Survey view: graph-memory evolution is described as consolidation (merging, conflict resolution by confidence or recency), graph reasoning (link prediction), and reorganization (significance-based pruning by PageRank variants or decay). — [Graph-based Agent Memory survey, arXiv 2602.05665](https://arxiv.org/html/2602.05665v1)

#### Benchmarks on selective forgetting and updating
- MemoryAgentBench [PR: ICLR 2026]: four competencies including selective forgetting; the FactConsolidation set places a contradicting fact after the original (built from MQUAKE counterfactual edits) and tells agents newer facts win. Single-hop / multi-hop accuracy: GPT-4o long-context 60.0 / 5.0; GPT-5-mini 78.0 / 28.0 (the best multi-hop score); BM25 RAG 48.0 / 3.0; HippoRAG-v2 54.0 / 5.0; GraphRAG 14.0 / 2.0; Mem0 18.0 / 2.0; Cognee 28.0 / 3.0; Zep 7.0 / 3.0; MemGPT 28.0 / 3.0; MIRIX 14.0 / 2.0. The paper says "all methods fail on the multi-hop situation". — [MemoryAgentBench, arXiv 2507.05257](https://arxiv.org/html/2507.05257); venue: [ICLR 2026 poster](https://iclr.cc/virtual/2026/poster/10010781)
- HaluMem: update omission above 50% for most systems; update correctness 5 to 62%. — [HaluMem](https://arxiv.org/html/2511.03506)
- LongMemEval knowledge-update category: Zep 74.4 vs full-context 76.9 (gpt-4o-mini) and 83.3 vs 78.2 (gpt-4o). — [Zep](https://arxiv.org/html/2501.13956v1)
- The graph-memory survey notes that many benchmarks lack explicit supervision for memory updates, so overwriting or forgetting outdated information is "less systematically evaluated" than recall. — [Graph-based Agent Memory survey](https://arxiv.org/html/2602.05665v1)

#### Dependent-subgraph invalidation (all 2026 preprints)
- PACMI [pre, Oct 2026]: breadth-first traversal over outgoing dependency edges from the directly contradicted record; `supports` successors become needs-verification, `used-by` successors become historical-only, the direct target becomes superseded; "original text is preserved". On its own benchmark (100 cases, 300 queries, fixed two-hop chains, six memories per case): final accuracy PACMI 0.99, A-MEM-style 0.90, CUPMem-style 0.80, Recency-RAG 0.78, vector RAG 0.74, LLM-only update 0.63; stale-in-context 0.34 vs 0.47 to 0.53. Removing cascading invalidation changes errors from 3 to 11 (p = 0.0574, not significant). Limits stated by the authors: dependency edges are given by annotation; the benchmark cannot exercise over-invalidation; single run; judge from the same model family; handling of a node with independent support is not addressed beyond "stronger state wins". — [PACMI](https://arxiv.org/html/2610.05732)
- MemTX [pre, Jul 2026]: retraction (transaction abort or revocation of a committed record) walks transitive descendants in the derived-from DAG and repairs by record type: beliefs revoked; summaries, profiles, index entries and shared copies quarantined for rebuild; tool actions compensated if reversible, otherwise logged as leaked irreversible effects; every repair writes to a rollback log. Invariant "after any retraction, every non-terminal descendant is inactive" checked by property-based tests over 10,000 traces and bounded enumeration of 5,530,160 states with zero violations (the checking found one missed cascade on the abort path). On its own 90-case suite, task success 0.756 to 0.956 across five backbones and zero realized downstream harm; removing cascading rollback costs about 11 points; overhead up to about 14% more tokens. Stated limits: repair covers only recorded provenance; an agent that copies content without declaring its parent defeats every method. — [MemTX](https://arxiv.org/html/2607.23929v2)
- Kumiho [pre, Mar 2026]: `AnalyzeImpact` returns the transitive dependency cascade of conclusions that "may need re-evaluation"; contraction soft-deprecates items (excluded from retrieval by default); whether deprecation cascades is not stated. Claims AGM postulates K*2 to K*6 plus Hansson's Relevance and Core-Retainment; rejects Recovery by design; K*7 and K*8 open; contraction does not handle joint entailment. — [Kumiho](https://arxiv.org/html/2603.17244)
- ReTree [pre, Aug 2026]: within a single search task, a contradiction is traced to the tree node that introduced the claim, evidence is replaced, summaries regenerated, and "affected branches" pruned; accuracy gains up to 25.6 points over full-trajectory ReAct on four QA/search benchmarks (abstract only). — [ReTree, arXiv 2608.10676](https://arxiv.org/abs/2608.10676)
- RECON [pre, single author, Jul 2026]: benchmark of 24 long case files and 1,604 questions with a "cascade propagation" task (after an invalidation, which conclusions break and which survive through independent support); ground truth computed by reachability on a provenance DAG with typed edges. Overall accuracy: Supermemory 15.1%, Mem0-Graph 10.8%, Hindsight 10.2%, Mem0 9.7%; best long-context model 22.4%; an oracle given the dependency graph 54.6%; humans 63.0% on 60 questions. On cascade specifically, oracle 81.8% vs 18.2% best LLM accuracy. — [RECON](https://arxiv.org/html/2607.16716v1)

### Inferences
- "No existing system can prune a dependent subgraph" is no longer a safe claim as of late 2026. The safe claim is narrower: none of the widely used or peer-reviewed systems (Zep, Mem0, A-MEM, GraphRAG, HippoRAG 2, G-Memory, MemTree, AriGraph, LightMem, Letta, Cognee, Anthropic's wiki) records derivation edges, so none can; three unreviewed 2026 preprints (PACMI, MemTX, Kumiho) do part of it.
- The differences between those three and the target design are specific and checkable: PACMI gets its dependency edges from benchmark annotation rather than from the system's own writes; MemTX's records are (entity, attribute, value) beliefs inside a transaction protocol for multi-agent stores, not notes composed from nodes, and its root is a corrupted record rather than a decision; Kumiho reports impact but does not prune. None starts the trace from a decision node and none composes a note by traversal.
- RECON's oracle result (81.8% vs 18.2% on cascade when the dependency graph is supplied) is the strongest available evidence that recorded dependency structure, not model reasoning, is what makes cascade correctness achievable. PACMI's non-significant ablation is the main counter-evidence, weakened by its two-hop, six-memory setup where retrieval is nearly saturated.
- Both PACMI and MemTX name the same weak point: the cascade is only as complete as the recorded edges. A design whose code refuses a node without its required typed dependency edges attacks that weak point directly; whether writers then record correct edges remains an empirical question.
- Independent support is the open design issue. RECON scores "survives through independent support" explicitly; PACMI does not handle it. A pruning rule should say what happens to a node that depends on the pruned root and also on a surviving node.

### Gaps
- PACMI, MemTX and RECON were each read once from arXiv HTML; the last 15 to 20% of each page was truncated. No code was inspected and no independent replication exists.
- The STALE benchmark and CUPMem, which PACMI adapts as a baseline, were not read.
- Earlier foundations for dependency-directed retraction (truth maintenance systems, AGM belief revision, event sourcing) were out of this note's scope and not searched; I found no agent-memory paper other than Kumiho that maps its operations onto AGM.
- I found no production incident data or user study on wrong-root pruning in agent memory.

## Key question 5: Which 2025-2026 surveys and taxonomies classify graph memories, and what open problems do they name?

### Takeaway
Three surveys cover the space, and two are unreviewed preprints. They classify graph memory by shape (flat, planar, hierarchical; knowledge graph, tree, temporal graph, hypergraph) and by lifecycle stage, not by node or edge typing, mutability or dependency structure. The open problems they name that bear on the target design are graph quality with no intrinsic metric, schemas that do not transfer across domains, provenance for trust, and the lack of benchmarks that supervise memory updates.

### Cited Findings
- "Memory in the Age of AI Agents: A Survey" (Hu, Liu, Yue, Zhang et al., 47 authors) [pre; arXiv Dec 2025, v2 Jan 2026]: three axes, forms (token-level, parametric, latent), functions (factual, experiential, working), dynamics (formation, evolution, retrieval). Token-level memory is split into flat (1D: "Relationships among these units are not encoded directly in the memory"), planar (2D: tree, graph, hybrid; "The structure is explicit, but not layered") and hierarchical (3D: pyramid, multi-layer). Its Table 1 places A-MEM and MemTree as planar; Zep, HippoRAG/HippoRAG 2, GraphRAG, G-Memory, AriGraph, H-Mem, MAGMA as hierarchical; MIRIX as flat. — [arXiv 2512.13564](https://arxiv.org/html/2512.13564v2)
- Same survey: evolution is consolidation (local, cluster-level fusion, global integration), updating (external memory update, model editing) and forgetting (time-based, frequency-based, importance-driven); named frontiers are memory automation, reinforcement-learning integration, multimodal memory, multi-agent memory and trustworthiness. — [arXiv 2512.13564](https://arxiv.org/abs/2512.13564v2)
- "Graph-based Agent Memory: Taxonomy, Techniques, and Applications" (Yang, Zhou, Xiao et al., mainly Hong Kong PolyU) [pre; arXiv Feb 2026]: structures are knowledge graph (AriGraph, Mem0), hierarchical/tree (MemTree, SGMem, H-MEM, G-Memory, LiCoMemory), temporal graph (Graphiti/Zep, TReMu, MemoTime), hypergraph (HyperGraphRAG, HyperG), hybrid (Optimus-1, KG-Agent); lifecycle is extraction, storage, retrieval, evolution. — [arXiv 2602.05665](https://arxiv.org/html/2602.05665v1)
- Same survey, seven open challenges: (1) "The quality of the memory graph fundamentally constrains the performance, reliability, and adaptability", with a scarcity of intrinsic quality metrics; (2) scalability, with graph operations of "quadratic or worse complexity"; (3) privacy and security, including adversarial manipulation of memory contents; (4) dynamic schema learning: "Current graph schemas are often domain-specific with limited reusability"; (5) interpretability and trustworthiness, with "memory provenance tracking systems" as a direction; (6) theoretical foundations; (7) memory coordination in multi-agent systems. — [arXiv 2602.05665](https://arxiv.org/html/2602.05665v1)
- Same survey on typing: little explicit treatment; it mentions "schema evolution" under KG update and restricting retrieval to "compatible entity or relation types". Provenance-based or dependency-based invalidation is not discussed in the sections read. — [arXiv 2602.05665](https://arxiv.org/html/2602.05665v1)
- "Graph-Based Personalized Memory for LLM Agents: Representation, Evolution, Retrieval, and Evaluation" (Nguyen, Qiu, Chen, Liew) [PR: accepted at ICKG 2026 per arXiv comments; Sep 2026]: lifecycle view over representation, evolution, retrieval and evaluation for personalization; open problems not listed in the abstract. — [arXiv 2609.08599](https://arxiv.org/abs/2609.08599)
- Zep's paper itself notes that LLM-generated knowledge graphs mostly lack formal ontologies and lists domain ontologies as future work. — [Zep](https://arxiv.org/html/2501.13956v1)
- Anthropic's stated open questions: when to create memory, how to keep it current, and how to maintain wikis without accumulated errors or hallucinations given compute cost. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

### Inferences
- The two large surveys disagree on where systems sit (the Dec 2025 survey calls Zep, HippoRAG and GraphRAG "hierarchical" and A-MEM "planar"; the Feb 2026 survey files Zep under temporal graphs and G-Memory under trees), which shows the taxonomies describe topology, and topology does not separate the designs that matter here. A positioning table for the target design needs its own axes: node mutability, who assigns and checks types, presence of dependency edges, and scope of invalidation.
- The surveys' open problems match the target design's claims one for one: intrinsic graph quality (typed, code-checked writes are measurable for validity), schema reusability (a small fixed type vocabulary trades coverage for checkability), provenance for trust (immutable nodes and typed derivation edges), and unevaluated updating (amendment nodes and pruning need a benchmark; MemoryAgentBench's FactConsolidation and RECON's cascade task are the nearest existing ones).
- Because neither large survey has a category for append-only or immutable memory, a paper on the target design would have to introduce that axis itself and cite Zep's history-preserving edges, Kumiho's immutable revisions and Managed Agents' non-destructive dreams as the nearest prior points.

### Gaps
- The body of the Dec 2025 survey's sections on planar versus hierarchical trade-offs, memory evolution and trustworthy memory (its sections 3.1.2, 5.2 and 7.7) was not read; only headings, Table 1 placements and the abstract were confirmed.
- The Feb 2026 survey's memory-evolution section was read only through a summary of its first 100k characters; the last 16k characters of the page were not read.
- Other 2025 surveys ("Rethinking Memory in AI: Taxonomy, Operations, Topics, and Future Directions"; "From Human Memory to AI Memory"; "Graphs Meet AI Agents") were not fetched. I found no survey published in a top peer-reviewed venue (NeurIPS, ICLR, ICML, ACL, TMLR) that classifies graph memories; that absence is from limited search, not confirmed.
