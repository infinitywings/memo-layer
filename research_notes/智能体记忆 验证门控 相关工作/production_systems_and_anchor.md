# How production and practitioner agent-memory systems decide what memory an agent may trust (anchored on Anthropic, "The components of agent memory", 2026-11-06)

Research date: 2026-11-13. All URLs were fetched or surfaced by search on that date. "Vendor claim" marks numbers a vendor reports about its own product; "independent" marks work by parties other than the vendor. Short quoted phrases only.

## Anchor: what the article and its companion material say

### Takeaway
Anthropic frames a memory note as a prediction that the note will matter (and be relied on without re-checking) later, lets strong models judge salience freely rather than follow fixed write rules (a "record only failures" rule cut the memory gain by up to 0.234 mean reward), and relies on an offline, model-run "dreaming" pass that checks notes against the original session transcripts to correct, merge and promote them. Nothing in the article or its companions gates memory on evidence the agent did not author; correction is by model judgment against transcripts, and promotion is to an always-loaded top layer that the article itself flags as risky ("a wrong note propagates everywhere"). CL-Bench is public (arXiv 2606.05661, GitHub repo), but the CL-Bench 1.0 numbers in the article are Anthropic's own runs.

### Cited Findings

**Article metadata and framing**
- "The components of agent memory", by Lance Martin (Anthropic Engineering, with editorial contributors), published Nov 6, 2026; topics Agents, Context engineering, Agent memory. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Definition: agent memory is knowledge Claude gains from experience and keeps between sessions as readable context; it explicitly excludes weight changes, in-context learning, and compaction. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- The article draws a hippocampus/consolidation analogy: agents log work, and a background "dreaming" process reflects on logs to fix mistakes and produce new notes; it cites Letta / UC Berkeley "sleep-time compute" (arXiv 2504.13171, April 2025, older) as precedent. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory); [sleep-time compute paper](https://arxiv.org/abs/2504.13171)

**Memory as a prediction**
- Writing a rule is a prediction that the pattern will matter again; recording a verified fact predicts the future agent will rely on it without re-checking. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- The open question on salience: how Claude can judge what is important before it knows what comes next. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**CL-Bench 1.0 setup and numbers (as run by Anthropic; vendor-run measurement)**
- Setup: Claude answers database-lookup questions, is then shown the correct answer, and may write memory; each question starts a fresh session but a persistent memory directory carries over. Intended loop: record failures, form and test theories, turn findings into rules. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Mean reward, stateless baseline -> with memory: Opus 5.5 0.655 -> 0.838; Sonnet 5.5 0.644 -> 0.833; Opus 5 0.564 -> 0.828; Opus 4.7 0.383 -> 0.700; Sonnet 5 0.306 -> 0.610; Sonnet 4.6 0.330 -> 0.364. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Qualitative behavior: Sonnet 4.6 produced untested theories; Opus 4.7 consolidated notes and marked confirmed vs unconfirmed facts; Sonnet 5 marked answers confirmed and wrote corrections; Opus 5 was the first to "close the loop" (rules with justification, prior answers, warnings). — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- The article's only CL-Bench link is the CL-Bench 1.0 news page (dated May 4, 2026, credited to "The Continual Learning Bench Team"); that page gives no setup or results. — [CL-Bench 1.0 news](https://continual-learning-bench.com/news/cl-bench-1-0/)
- CL-Bench is public: the site links a GitHub repo and an arXiv paper. Paper: "Continual Learning Bench: Evaluating Frontier AI Systems in Real-World Stateful Environments", Asawa, Glaze, Orlanski, Ramakrishnan, Xu, Biswal, Chen, Sala, Zaharia, Gonzalez; submitted June 4, 2026; six domains (software engineering, signal processing, disease outbreak forecasting, database querying, strategic game-playing, demand forecasting); a "gain" metric (reward minus the same system's stateless baseline) separates learning from prior capability. — [CL-Bench site](https://continual-learning-bench.com/); [arXiv 2606.05661](https://arxiv.org/abs/2606.05661); [GitHub repo](https://github.com/pgasawa/continual-learning-bench)
- Independent headline finding of the CL-Bench paper: agents often overfit to immediate observations or fail to reuse knowledge, and dedicated memory systems do not fix this; naive in-context learning outperforms systems built for memory management. — [arXiv 2606.05661](https://arxiv.org/abs/2606.05661)

**Salience judged by the model (Pokémon Red)**
- At ~10,000 steps, Sonnet 3.7 wrote 413 files across 225 folders (~977,930 characters), earned one badge, and its detailed records "went stale quickly"; around step 10,000 it spent 17 steps creating six files and deleting nine with no in-game actions. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Fable 5 wrote 10 files (~43,406 characters), including a `global.md` dashboard with goals, gym plans and memory rules, and earned four badges; the difference was storing only what the screen does not show (strategy, tested rules) vs Sonnet 3.7 storing visible state (money, position). Opus 5.5 kept a small goal/next-step note set and beat the game. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Steering by purpose vs fixed rules**
- Telling Claude what memory is for, without prescribing procedure, worked well; merely noting that a memory folder existed boosted Opus 4.7 and Opus 5 on CL-Bench. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- A fixed "record only failures" rule reduced the memory gain by 0.234 (Opus 5), 0.150 (Opus 4.7) and 0.020 (Sonnet 4.6); for stronger models, free salience judgment beat preset rules. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Older models benefit from procedural steering: prompting Sonnet 4.6 to read memory first and test theories explicitly raised it from 0.364 to 0.641; Sonnet 5 reads memory on its own about 9 in 10 times vs under half for Sonnet 4.6. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Dreaming corrects memory against transcripts**
- Notes written in-session can be wrong from the start or drift; a later session may trust them. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Mt. Moon case: a wrong note (PokéCenter on the east side) led Claude off a one-way ledge back onto the route it came from; a dreaming pass checked the note against the transcript, found the error and rewrote it; the corrected run reached Cerulean City at action 1,935; the uncorrected run looped back three times, said it would stop rather than keep looping, was auto-prompted to continue, and ended in Pewter City; the no-memory run never reached Cerulean. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Dreaming builds representations (wikis)**
- Stainless corpus (~350,000 files, ~420M tokens), 25 questions, 128 sessions of Opus 5 agents writing/correcting/merging pages: wiki-only accuracy rose from 13% to 48% of graded criteria as dreaming scaled from 2 to 128 sessions; wiki+search 54% -> 61% vs 53% for search alone; wiki+search saved ~20,000 tokens per question. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Harvey LAB merger task (24 questions): 87% with wiki vs 73% search-only; on a LAB task answerable from a single document, no clear gain. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Over-building failure: one wiki grew to 203 KB from a 115 KB corpus (1.77x), 68 pages, 255 links, some orphan pages; it "effectively abstracted nothing." — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Memory hierarchy and promotion**
- Dreaming can promote notes into injected context loaded at the start of every session; risks named: token cost, a wrong note propagates everywhere, and longer instruction files reduce adherence; dreaming's job is partly to keep this layer small by moving details down and leaving links. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Goal-focused dreaming (contract terms): with generic instructions, agents overwrote a shared terms table and only 41 of 57 graded facts (72%) survived; after a reflect-propose-rebuild loop with one page per contract and terms quoted verbatim, all 57 survived. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Cross-session gap filling: a second pass repointed nine links to a missing page and added three pages; wiki went from 38 entries/225 links to 41/278. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Stated open problems**
- When to write: writing during a task pulls attention; dreaming moves work to the background but its outputs may not be immediately available. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Keeping memory current: Claude can make wrong predictions or write incorrect rules, and memory drifts as environments change; dreaming fixes this but costs compute; checking all memories continuously may be impractical; suggested directions are focusing on volatile information or tuning dreaming cadence (e.g., by access frequency). — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Transcript search is called a sound foundation; wikis plus search help but need compute to maintain and to prevent accumulated errors or hallucinations. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Companion: Dreams API (Claude Managed Agents)**
- Status: research preview; beta headers `managed-agents-2026-04-01` and `dreaming-2026-04-21`. A dream takes an existing memory store plus 1 to 100 past sessions and produces a new, separate output store: duplicates merged, "stale or contradicted entries replaced with the latest value," new insights surfaced. The input store is never modified, so output can be reviewed and discarded. — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)
- Optional `instructions` steer synthesis (focus areas, content to preserve), but the pipeline is "a synthesis pass," not a line editor; targeted edits go through the Memory Stores API. Runs take minutes to hours; billed at standard token rates, cost roughly linear in number/length of sessions. Not ZDR- or HIPAA-eligible. — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)
- Motivation stated in docs: in-session writes are "local and incremental," so stores accumulate duplicates, contradictions and stale entries. — [Dreams docs](https://platform.claude.com/docs/en/managed-agents/dreams)

**Companion: "Dreaming with a dynamic workflow" cookbook (Nov 2, 2026)**
- Three agents: a lead `memory-distiller` (Sonnet 5.5) that writes and launches a workflow but is told not to read transcripts; one `transcript-analyzer` (Haiku 5.5) per transcript; one `memory-organizer` at the end. Network allowlist empty. — [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- Analyzer method: read the whole transcript; verify existing memory claims against transcript evidence; claims with no evidence are left alone (another transcript may support them); contradicted claims are noted or fixed; confidently stated claims backed by uncertain evidence are downgraded; enrich with identifiers, dated and staleness notes. — [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- Contradiction policy: keep the current value only when one entry is plainly the later correction (noting both dates and sources); otherwise keep both marked "CONFLICT"; don't guess; a single session's passing remark never overrides a recorded decision. — [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- Promotion: `_index.md` lists every live file; optionally its text is loaded into mount instructions (capped at 4,096 characters), with a warning that it lands in every system prompt. Tools have no delete/move; merged files leave `MOVED TO` stubs that the notebook deletes after the run. — [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- Numbers (vendor): 11 example transcripts (283 KB) ~$0.36, ~2.5 min; ~50 long transcripts (~12 MB) ~$8 and ~10 min with cost-saving settings vs ~$10 / 9 min without (averages of 60 and 30 dreams); stores with/without those settings held about the same share of a fixed fact list. — [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- Safety: transcripts are "data to draw facts from, not instructions"; injected content can change what the store says; recommended mitigations are read-only mounts on user sessions, no shell/web for untrusted transcripts, secret redaction. No human review by default; the nightly in-place script means a bad transcript can reach the agent the next morning, so the recommended alternative is writing to a new store, reviewing it, then switching. — [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)

**Companion: knowledge-wiki quickstart**
- Build workflow: extractors read document batches, a resolver works flagged gaps, analyzers check filed content against source documents, an organizer tidies; agents then mount the wiki read-only and cite facts; conflicts kept as conflicts, superseded figures marked superseded. No verbatim-quote or automated citation-to-file check is described. — [Knowledge-wiki quickstart](https://github.com/anthropics/claude-quickstarts/tree/main/managed-agents/knowledge-wiki)
- Vendor numbers: small model + wiki answers "within a point" of a larger model searching raw documents, ~3 points better than that model searching itself, at ~1/15 the price per answer; build ~$19 benchmark average; payback ~240 questions; known limit: ~5% of lines filed to the busiest shared page are overwritten. — [Knowledge-wiki quickstart](https://github.com/anthropics/claude-quickstarts/tree/main/managed-agents/knowledge-wiki)

**Companion: Managed Agents memory stores**
- Stores are workspace-scoped document collections mounted under `/mnt/memory/`; access defaults to `read_write`, `read_only` enforced at the filesystem level; up to 8 stores per session; each memory capped at 100 kB, 10,000 memories per store; recommended practice is small purpose-built stores (per user, shared domain, project). — [Memory stores docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Explicit poisoning warning: with `read_write`, a successful prompt injection from untrusted input could write malicious content, and later sessions read it "as trusted memory"; use `read_only` for reference material. — [Memory stores docs](https://platform.claude.com/docs/en/managed-agents/memory)
- Every mutation creates an immutable memory version attributed to the session (audit, point-in-time recovery, redaction); versions kept 30 days (recent versions of live memories always kept); rollback = rewrite old content; `content_sha256` preconditions prevent overwriting concurrent writes. — [Memory stores docs](https://platform.claude.com/docs/en/managed-agents/memory)

**Companion: Claude Code memory (linked twice from the article)**
- Two systems: CLAUDE.md (written by the user; project/user/org scope; loaded every session) and auto memory (written by Claude; per repository, shared across worktrees; first 200 lines or 25KB of `MEMORY.md` loaded). Both are "context, not enforced configuration"; to block an action, use a PreToolUse hook. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Auto memory saves four typed notes (`user`, `feedback`, `project`, `reference`) and skips anything derivable from the codebase (architecture, file paths, debugging fixes) or already in CLAUDE.md; Claude decides what is worth remembering. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Storage: `~/.claude/projects/<project>/memory/`, machine-local, `MEMORY.md` index plus topic files read on demand; memory files are excluded from transcript retention cleanup and persist until edited/deleted. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Code-side check on the index: after a write to `MEMORY.md`, Claude Code measures it against the 200-line/25KB limits, reminds Claude to merge or drop stale entries when near the limit, and returns an error telling Claude to rewrite the index when over it (the check is on size, not truth). — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Guidance on wrong/stale instructions: target under 200 lines per CLAUDE.md ("longer files ... reduce adherence"); contradictory instructions may be resolved "arbitrarily"; `/doctor prompt-audit` (v2.1.283+) has Claude look for outdated instructions, references to files or commands that don't exist, and contradictions, producing proposed edits applied only on request. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)

**Companion: Claude memory tool (API)**
- Client-side tool (`memory_20250818`, stable, on all Claude 4+ models): Claude issues view/create/str_replace/insert/delete/rename on `/memories`; the application executes them. The API auto-injects a system prompt to view memory first and to "ASSUME INTERRUPTION." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Security guidance (all application-side): path-traversal validation, strip sensitive data before writes, cap file sizes, and "periodically delete memory files that haven't been accessed in a long time." Multisession pattern: mark a feature complete only after end-to-end verification, to keep the progress log accurate. — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

### Inferences
- The anchor's correction mechanism is model judgment against transcripts, i.e., against a record that mixes the agent's own text with tool output and user turns. It does not distinguish agent-authored from externally produced evidence; the cookbook's "downgrade confidently stated claims with uncertain evidence" is the nearest analogue to a trust tier, and it is prompt-level, not code-enforced.
- The cookbook explicitly leaves claims with no supporting evidence untouched. A design that demotes or withholds unsupported claims is stricter than Anthropic's reference implementation.
- The "record only failures" result is about restricting what gets written, and it hurt strong models. A gate that restricts what is trusted (reaches the agent) while still letting the model write freely is a different intervention; the anchor offers no data on gating trust, only on gating writes. A design whose gate also narrows writes risks the same loss.
- Anthropic's promotion target (always-loaded injected layer / `MEMORY.md` index / `_index.md` in mount instructions) is chosen for access frequency and size, not for verification status. The article's own risk list ("a wrong note propagates everywhere") is the argument for gating promotion on verification.
- The CL-Bench paper's independent finding (dedicated memory systems do not beat naive ICL) cuts against assuming that more memory machinery helps; Anthropic's numbers show large gains for frontier Claude models with a plain memory directory.

### Gaps
- The arXiv CL-Bench paper's database-querying environment details, task counts and leaderboard numbers were not read (abstract only), so I could not confirm that Anthropic's "CL-Bench 1.0" runs use the identical protocol or whether Anthropic's numbers appear on the public leaderboard. Author affiliations were not shown on the arXiv page.
- None of the Anthropic numbers (CL-Bench runs, wiki accuracies, Pokémon results) are independently reproduced; the article gives no variance, seeds or run counts for CL-Bench.
- No Anthropic document found states whether Claude Code auto memory is ever consolidated by a dreaming-like pass, or measures how often auto-memory notes are wrong.

## Production systems: who writes memory, what checks it before use, expiry/correction, scope, measured effect

### Takeaway
GitHub Copilot Memory is the only shipping product found that checks a memory against ground truth before use: each memory carries code citations, and the agent checks them against the current branch, upvoting valid memories (resetting a TTL, now 90 days by default) and downvoting or rewriting wrong ones. Even there, the check is performed by the model, and GitHub's docs say it "isn't guaranteed." Every other product surveyed (Claude Code auto memory, the Claude memory tool, Managed Agents stores, ChatGPT, Codex, Cursor, Windsurf, Gemini, Jules, Letta, LangMem) admits memories on model or user judgment with no evidence check; correction is by user editing, model-run consolidation, recency, or (Zep/Graphiti) LLM-detected temporal invalidation that keeps history. Published effect sizes are all vendor-reported.

### Cited Findings

**GitHub Copilot Memory (agentic memory)**
- Timeline: early access for Pro/Pro+ Dec 19, 2025; public preview Jan 15, 2026 (coding agent, code review, CLI share memories); on by default for Pro/Pro+ Mar 4, 2026; user preferences May 15, 2026; deletion/scope controls and CLI `/memory` May 26, 2026; engineering blog updated Nov 12, 2026 to call memory "generally available." — [Changelog 2025-12-19](https://github.blog/changelog/2025-12-19-copilot-memory-early-access-for-pro-and-pro); [Changelog 2026-01-15](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/); [Changelog 2026-03-04](https://github.blog/changelog/2026-03-04-copilot-memory-now-on-by-default-for-pro-and-pro-users-in-public-preview/); [Changelog 2026-05-15](https://github.blog/changelog/2026-05-15-copilot-memory-supports-user-preferences-for-pro-pro-users); [Changelog 2026-05-26](https://github.blog/changelog/2026-05-26-copilot-memory-has-more-controls-for-deletion-scope-and-the-copilot-cli/); [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Who writes: agents call a `store_memory` tool when they find something likely to have actionable implications for future tasks; each memory has `subject`, `fact`, `citations` (file:line, e.g. `server/routes/api.go:8`) and `reason`. — [GitHub blog, Tiferet Gazit, Jan 15, 2026](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Design choice: store with citations and verify just-in-time rather than curate offline, on the argument that verifying a fact is easier than retrieving it; offline curation (dedupe, conflict resolution, expiring stale data) was considered and rejected for cost and complexity. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Check before use: at session start the most recent repository memories are added to the prompt; before applying one, the agent checks the cited locations against the current branch; if the code contradicts it or citations are invalid, it stores a corrected version; if valid and useful, it re-stores it to refresh the timestamp. GitHub reports no significant added latency (no figures). — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Current docs: Copilot upvotes memories it can validate and downvotes wrong/outdated ones; downvoted memories past a threshold stop being used and are eventually deleted; "Copilot makes this judgment itself, so it isn't guaranteed." — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Expiry changed over time: the Jan 15, 2026 changelog said memories expire after 28 days. Current docs (fetched 2026-11-13) give a 90-day default for both repository facts and user preferences; owners can set repository-fact expiry between 7 and 180 days; an upvote resets the period, but retrieval alone does not. — [Changelog 2026-01-15](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/); [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Scope and permissions: repository facts (shared with collaborators, not inherited by forks) can be created only from actions by users with write access and used only on tasks in that repository by users with read permission; user-level preferences apply across repositories but are never applied by code review or Autofix; the `store_memory` prompt now states at capture time which scope an entry gets. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory); [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/); [Changelog 2026-05-26](https://github.blog/changelog/2026-05-26-copilot-memory-has-more-controls-for-deletion-scope-and-the-copilot-cli/)
- Surfaces creating/using memories: Copilot app, CLI, code review, cloud agent, Agentic Autofix, GitHub Mobile, Slack, Teams; memories cross surfaces. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Other admission filters: memories containing detected secrets are rejected; Copilot is instructed not to store sensitive personal/confidential information or short-lived task instructions. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Adversarial test (vendor, no numbers): repositories seeded with memories contradicting the code and citing irrelevant or nonexistent locations; agents "consistently verified citations," found contradictions and updated incorrect memories ("self-healed"); a realistic-pool simulation overrepresented memories from abandoned/unmerged branches. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Measured effect (vendor A/B tests, p < 0.00001): code review precision +3% and recall +4%; coding-agent PR merge rate 90% with memory vs 83% without; code-review positive comment feedback 77% vs 75%. — [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Residual risks GitHub states: facts can come from pull requests closed without merging; Copilot may not catch every outdated fact; memories are not guaranteed to be followed, so mandatory rules belong in custom instructions. — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Since Sept 25 (2026 per secondary report), agentic security autofix uses Copilot Memory when enabled. — [DevOps.com (secondary)](https://devops.com/githubs-security-autofix-agent-now-remembers-what-it-fixed/)

**Claude Code auto memory / CLAUDE.md**
- Writer: Claude (auto memory) or the user (CLAUDE.md). Check before use: none for truth; both load as context, auto memory's index truncated at 200 lines/25KB; size checked by code. Correction: user edits (`/memory`), Claude edits, or `/doctor prompt-audit` proposals. Expiry: none; memory files exempt from transcript cleanup. Scope: per git repository (shared across worktrees), machine-local; CLAUDE.md at managed/org, user, project, local scopes; subagents can have separate memory directories. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Measured effect: none published in the docs; the anchor article cites the docs for the adherence-vs-length claim. — [Claude Code memory docs](https://code.claude.com/docs/en/memory); [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)

**Claude memory tool and Managed Agents memory stores**

**OpenAI ChatGPT memory**
- Two controls: saved memories (details the user asked ChatGPT to remember) and reference chat history (draws on past chats); deleting a chat does not delete a memory derived from it; turning off saved memory does not delete existing memories; Temporary Chats neither use nor create memories; deleted-memory logs may be retained up to 30 days. **LangMem (LangChain)**
- Memory types: semantic (collections or profile), episodic (situation, reasoning, action, result of successful interactions), procedural (instructions refined by prompt optimizers). Formation in the hot path (agent saves during conversation, adds latency) or in the background (LLM reflects after conversations). An LLM reconciles new information by deleting/invalidating or updating/consolidating; recall weighs similarity, importance and "strength" (recency and frequency of use); multi-level namespaces such as org/user/app. No ground-truth verification and no metrics published on the page. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)

### Inferences
- Copilot Memory is the closest production analogue to an evidence-gated design: memories must carry citations, are checked at read time, refreshed on successful validation and decayed by TTL. Differences from the compared design: (a) the evidence is a code location, a pointer the writing agent chose, not an artifact the agent did not author (test result, exit code, user statement); (b) the check is done by the model in-prompt, not by code, and GitHub says it is not guaranteed; (c) memories reach the prompt before validation (recent memories are injected at session start, then checked before being applied); (d) there is no ladder beyond use/non-use plus vote counts.
- Claude Code auto memory takes the opposite stance from Copilot on codebase facts: it skips anything derivable from the code, so its notes (user, feedback, project, reference) are mostly not checkable against the repository at all. That makes user statements (the `feedback` type) the main external evidence source in that system, and the design's "explicit user statements" category maps onto it directly.
- Codex's `disable_on_external_context` is the only shipping control found that filters memory admission by provenance (excluding chats that touched MCP, web or tool search), which is a coarse, session-level version of the "not authored by the agent / not from untrusted input" distinction, applied in the opposite direction (it excludes external tool content rather than requiring it).
- Expiry practice splits three ways: TTL with refresh on validated use (Copilot), no expiry plus model-run consolidation (Claude Code, Managed Agents + Dreams, Letta, Codex), and temporal invalidation that keeps history (Graphiti). Only Copilot ties lifetime to successful verification.
- Scope practice is converging on per-repository/workspace for coding agents (Copilot repo facts, Claude Code, Jules, Windsurf), with a separate user-preference tier (Copilot user prefs, ChatGPT, Claude app, Gemini). Copilot's rule that user preferences are never applied in code review or Autofix is an example of scoping by consumer, not only by writer.
- Two products (Cursor, Windsurf/Devin Local) retreated from auto-generated memories toward user-maintained rules/skills, which suggests vendors found unverified auto-memory hard to make trustworthy, but neither vendor published a reason or data.

### Gaps
- No vendor publishes the rate of wrong or stale memories in production, nor how often validation fails; GitHub's adversarial "self-healing" result has no numbers.
- I could not find the official GitHub GA changelog or the date the default expiry moved from 28 to 90 days; the change is inferred from the Jan 15, 2026 changelog vs the current docs.
- OpenAI help-center pages returned 403; ChatGPT memory details rest on search snippets of official pages and secondary coverage. No OpenAI statement on memory accuracy was found.
- Cursor's 2025 approval flow for background-generated memories (memories proposed by a sidecar model and requiring user approval) is from recollection and was not verified; Cursor's current status is contradictory across staff replies.
- Windsurf's primary memories page could not be fetched (redirect to a rules page); details rest on search snippets.
- Claude app memory pages were not fetched directly. Mem0 and Microsoft 365 Copilot memory were not examined.

## Vendor statements and data on wrong or stale memories causing harm, and memory poisoning in production

### Takeaway
Vendors document wrong-memory harm mainly through their own experiments (Anthropic's Mt. Moon loop, stale Pokémon records, overwritten shared pages losing 28% of contract facts; GitHub's adversarial seeding) and through warnings in docs, not through production incident data. The one production-scale poisoning dataset found is Microsoft's (Feb 10, 2026): over 50 prompts from 31 real companies in 14 industries, seen in 60 days of email traffic, trying to plant "trusted source" entries in assistant memories; Microsoft documents attempts, not confirmed user harm.

### Cited Findings
- Anthropic (own experiments): an incorrect location note caused repeated looping and a wrong destination until a dreaming pass corrected it against the transcript; Sonnet 3.7's detailed records went stale quickly; generic multi-agent wiki writing overwrote a shared table so only 41/57 graded facts (72%) survived. — [Anthropic](https://www.anthropic.com/research/components-of-agent-memory)
- Anthropic quickstart: about 5% of lines filed to the busiest shared wiki page are overwritten. — [Knowledge-wiki quickstart](https://github.com/anthropics/claude-quickstarts/tree/main/managed-agents/knowledge-wiki)
- Anthropic docs warn that with read-write stores a successful prompt injection can write malicious content that later sessions read as trusted memory; the dreaming cookbook warns a bad transcript can reach the agent the next morning when the nightly script updates a store in place. — [Memory stores docs](https://platform.claude.com/docs/en/managed-agents/memory); [Cookbook](https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
- GitHub: facts can come from closed-unmerged pull requests, Copilot may not catch every outdated fact, and validation "isn't guaranteed"; adversarial memories seeded into test repos were corrected by agents (no numbers). — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory); [GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- OpenAI Codex: memories may lag behind a chat and must not be the only source for required rules. — [Codex Memories docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)
- Microsoft Defender Security Research Team (Noam Kochavi et al., Feb 10, 2026), "AI Recommendation Poisoning": "Summarize with AI" links pre-fill prompts via URL parameters (e.g. `?q=`) that tell the assistant to remember a company as a trusted source; over 50 unique prompts from 31 companies across 14 industries, found over 60 days while reviewing AI-related URLs in email traffic; URL patterns listed for Copilot, ChatGPT, Claude, Perplexity and Grok; public tooling (npm package, URL generator) makes it trivial; harm scenarios are explicitly hypothetical; Microsoft's mitigations are prompt filtering, separation of user instructions from external content, user-visible memory controls, monitoring; mapped to MITRE ATLAS AML.T0080 (Memory Poisoning) and AML.T0080.000. — [Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2026/02/10/ai-recommendation-poisoning/); [The Register](https://www.theregister.com/2026/02/12/microsoft_ai_recommendation_poisoning/)
- OWASP Top 10 for Agentic Applications (Dec 2025 release) lists Memory and Context Poisoning as ASI06 (per secondary sources; primary not fetched). — [Roval AI blog (secondary)](https://roval-ai.pages.dev/research/blog/agent-memory-poisoning-asi06)
- Secondary reports (not verified against primaries): Radware's "ZombieAgent" (Jan 2026) against OpenAI Deep Research/Connectors; Palo Alto Unit 42 attack chain against Amazon Bedrock Agent with memory enabled; "eTAMP" cross-session attacks reportedly validated against ChatGPT Atlas and Perplexity Comet. — [Christian Schneider blog (secondary)](https://christian-schneider.net/blog/persistent-memory-poisoning-in-ai-agents/); [Akto (secondary)](https://www.akto.io/blog/memory-poisoning-ai-agents)

### Inferences
- The Microsoft dataset shows that the dominant observed poisoning vector is an external party getting text into the user turn (a pre-filled prompt) so it is stored as if it were a user preference. An evidence gate that treats "explicit user statements" as trusted external evidence would need to tell a user-typed statement from a URL-prefilled or tool-injected one; none of the products surveyed draws that line in code.
- Vendors' own mitigations are access control (read-only stores, repository write permission for Copilot), audit/rollback (Managed Agents versions), secret filters, and user review. None found uses evidence provenance as an admission criterion for memory content.

### Gaps
- No documented production incident was found in which a wrong or poisoned memory caused measurable user harm; Microsoft reports attempts and reproductions only.
- The Unit 42, Radware, OWASP ASI06 and eTAMP items were seen only through secondary sources; their exact claims and dates should be checked against the primary reports before citation.
- No vendor reports the share of memories later found wrong, the false-positive/negative rate of validation (GitHub), or the downstream error cost of stale memories in production.
